## 一、框架与架构优化

### Q1：Microsoft GraphRAG 索引进度慢、成本高、能力过剩，怎么办？

**问题**：文档检索最初使用 Microsoft GraphRAG。构建索引需要 LLM 抽取实体/关系/社区，**每次 5-30 分钟**，Token 消耗大；内嵌源码 80+ 文件，依赖 `graphrag==2.1.0` 难以管理。而业务场景是电商客服事实查询（价格、库存、售后），Global Search/DRIFT 多跳推理等高级能力极少用到，且实体关系已在 Neo4j 中管理，GraphRAG 的实体抽取完全冗余。

**解决**：整体迁移为标准 RAG 管道（✅ 已解决）：
- `文档解析（PyPDF2/python-docx）→ 清洗 → RecursiveCharacterTextSplitter 分块（500/50，中文标点作分隔符）→ Embedding → pgvector 入库 → 相似度检索`
- 删除 `app/graphrag/` 内嵌源码（80+ 文件）与 `graphrag` pip 依赖
- 查询侧用 `VectorStoreQuery`（约 20 行）替代 `GraphRAGAPI`（约 100 行 + 6 个 parquet 初始化），结果仍流入原有的混合检索 + 相关性评分管道
- 向量库选型演进：初版用 ChromaDB（persist 模式零运维）；后统一技术栈迁移到 **pgvector**——与业务库共用 PostgreSQL 实例，官方 `pgvector/pgvector` Docker 镜像一条 compose 服务解决，HNSW 索引余弦检索，且 LangGraph 检查点（PostgresSaver）复用同一实例

**结果**：索引从分钟级降到秒级；删除 80+ 维护负担文件；事实查询效果持平；混合检索、语义缓存全部保留；Neo4j（Text2Cypher/PredefinedCypher）后于 2026-08-16 随技术栈精简一并移除。

**复盘要点**：技术选型要与业务场景匹配——"能力过剩"的框架带来的是隐性成本（时间、Token、维护面）。裁掉用不到的能力，收益立竿见影。

### Q2：Embedding 维度配置与实际模型不一致，检索结果全错，如何排查？

**问题**：配置中 `EMBEDDING_DIMENSION=384`，但实际 Embedding 模型是 bge-m3（**1024 维**）。向量维度不匹配会导致向量检索/缓存相似度计算异常，且多个组件（HybridRetriever、pgvector、Ollama、语义缓存）各自为政，容易互相不一致。

**解决**（✅ 已解决）：
- 将 `EMBEDDING_DIMENSION` 修正为 1024，并在 `.env` 补齐缺失的 Embedding 配置段
- 所有检索组件统一到 bge-m3 一个模型，消除跨组件维度漂移
- 进一步抽象出统一 **EmbeddingProvider**（local / ollama / qwen 三种后端，工厂模式），任何组件只面向 Provider 取向量，后端切换零代码改动

**复盘要点**：向量系统里"模型-维度"是全局契约，一处变更必须全链路同步。发现此类问题不要只改一个调用点，要全局检索所有关联文件统一修正。

### Q3：硬编码配置散落各处，改一个参数要翻几十个文件，怎么治理？

**问题**：chunk 参数、检索参数、LLM 温度、缓存阈值等散落在各服务文件里硬编码，环境切换（本地/开发/生产）靠手工改代码，极易漏改出错。

**解决**（✅ 已解决）：分两阶段治理——
- 第一阶段：提取高频调优参数到 `.env`（chunk、检索、LLM 温度）
- 第二阶段：全部硬编码配置提取到 `config.py`（pydantic-settings），统一类型校验、默认值、注释说明；`.env.example` / `.env.docker` 同步维护

**复盘要点**：配置治理要小步迭代（先高频后全量），一次大重构风险高。配置项要"一处定义、处处引用"，`.env` 与代码默认值保持同步。

---

### Q4：依赖清单漂移——requirements.txt 和 uv.lock 各自为政，Docker 与本地环境不一致

**问题**：
- 本地用 uv 管理（pyproject.toml + uv.lock 锁定 207 包），Docker 却用 `pip install -r requirements.txt`（未锁版本），两套清单逐渐漂移
- 基础镜像 `python:3.11-slim` 与本地 `.python-version`（3.13）、`requires-python >=3.13` 不一致
- 后果：Docker 里装出的依赖组合与本地从未一致过，环境差异类 bug 难以复现

**解决**（✅ 已解决）：
- Dockerfile 改为安装 uv 后执行 `uv sync --frozen --no-dev --no-install-project`（`UV_PROJECT_ENVIRONMENT=/usr/local`），与本地共用同一份 uv.lock
- 基础镜像对齐 `python:3.13-slim`
- 删除 requirements.txt，pyproject.toml + uv.lock 成为唯一依赖来源，全部文档同步更新

**复盘要点**：一个项目只允许一个依赖事实源。锁定文件必须进版本控制（此前 uv.lock 甚至未入库）。Docker 构建环境与本地环境不一致是"运行环境型 bug"的头号来源。

### Q5：LangGraph 会话状态存在内存里，服务重启全部丢失

**问题**：当前 checkpointer 使用 `MemorySaver()`（进程内存）。任何重启/发布都会清空所有进行中的多轮会话状态，Agent 无法续聊——本地调试可以，生产不可接受。

**解决**（📋 已设计，待实施）：
- Checkpointer 换 `RedisSaver`（项目已有 Redis 基础设施），thread_id 驱动会话快照自动持久化与恢复
- 职责分离：Redis 存 Agent 运行快照（禁止业务查询）；PostgreSQL 业务库存前端可见对话 + 新增 `agent_tool_log` 工具日志表（审计/排查/RAGAS 评测）
- Redis 故障兜底：从业务库读历史对话重建新会话（降级，会丢工具上下文）
- 配套要求：Redis 必须开 RDB/AOF 持久化 + TTL 防膨胀

**复盘要点**：内存态组件（InMemorySaver/内存缓存）要明确标注"仅调试"。生产化改造核心是"状态可恢复 + 故障有降级路径"。

## 二、功能流程优化

### Q6：多轮对话中"那个有货吗"这种指代/省略消息，语义缓存命中率塌陷

**问题**：语义缓存只对最后一条用户消息做 Embedding。"那个有货吗"与"iPhone 15 256G 多少钱"的余弦相似度约 0.2，远低于 0.90 命中阈值，**本应命中的缓存全部 MISS**。指代/省略消息占真实对话约 15-20%，直接拉低整体缓存收益。

**解决**（📋 已设计，待实施）：分级指代消解——
- **检测先于消解**：三层规则引擎（显性指代词典 / 省略主语启发式 / 纯语气词过滤），80% 正常消息零开销透传，纯语气词跳过缓存（不查不写，避免污染）
- **LLM 消解**：仅对 15% 含指代消息，携带最近 5 轮对话调用 LLM 补全为独立问题（temperature=0 保证确定性）
- **铁律**：lookup 与 update 必须用同一套消解逻辑，缓存 Key 基于消解后消息的 MD5——否则写入和查找的向量永远对不上
- **降级透传**：消解超时（2s）/失败时用原始消息继续走缓存流程，绝不阻塞主链路
- 收益模型：消解后含指代场景命中率 5% → 60-80%，盈亏平衡点仅需 17.6% 命中率

**复盘要点**：缓存优化的本质是"让同一语义的消息生成同一向量"。检测用便宜手段（规则），消解用贵手段（LLM），且贵的部分必须可降级——增强功能永远不能变成阻塞点。

### Q7：长会话 Token 膨胀，压缩策略该按轮次还是按 Token？

**问题**：当前实现是**纯轮次驱动**压缩（>5 轮开始压缩，6-15 轮中等摘要、16 轮+高层摘要）。问题：消息长短不一，短消息场景白白浪费 LLM 压缩调用，长消息场景可能超出预算；每轮都做三层压缩，50 轮对话约 45 次 LLM 压缩调用，Token 消耗巨大。

**解决**（📋 已设计，待实施）：改为 **Token 阈值驱动 + 增量摘要**——
- 触发条件：输入 Token > 模型窗口 × 0.4（预留输出与工具调用 Buffer），不做轮次兜底
- 保留最近 N 轮完整原始消息（含 tool_call/tool_result，保证工具链路正常）
- 首次从零生成摘要，后续**增量压缩**：`已有摘要 + 新增旧消息 → LLM 更新摘要`，`last_compressed_index` 追踪增量起点
- 摘要存独立 `state.summary` 字段，**不插入 messages**；`state["messages"]` 只读，过滤/切分只在内存临时副本上做（禁止 `RemoveMessage`，会破坏断点恢复）
- 压缩前过滤老旧 ToolMessage 与含 tool_calls 的 AIMessage（工具结果噪声大、膨胀快）

**结果（测算）**：50 轮对话场景，压缩 LLM 调用 45 次 → 3 次，压缩 Token 消耗节省约 **98.5%**。

**复盘要点**：压缩触发条件要跟着实际瓶颈走（Token 预算），而不是跟着计数走（轮次）。增量更新模式（旧结果 + 新输入）是 LLM 长链路场景省成本的核心技巧。

### Q8：LLM 相关性评分 + 自动重检索的策略设计，为什么最后被砍掉了？

**问题**：曾设计"LLM 逐条评分过滤不相关结果 → 不足 N 条时自动切换检索策略重试（RELEVANCE_MAX_RETRIES）"的完整闭环。运行后发现：重试路径触发条件苛刻、多策略切换的代码分支膨胀（54 行评分+重试逻辑），实际业务场景极少命中，复杂度与收益不成比例，还引入失败重试的延迟风险。

**解决**（✅ 已解决）：**简化回退**——删除 `grade_and_ensure_min_results`、策略切换与重试逻辑，保留单次 LLM 相关性评分过滤（结果不足时直接如实返回，不兜底重试）；随后清理残留配置（RELEVANCE_THRESHOLD/MAX_RETRIES）与未使用导入。

**复盘要点**：不是所有闭环都值得做。功能设计要有"砍掉"的勇气——当兜底逻辑的复杂度超过其覆盖的场景价值时，简化即优化。回退时记得连配置项、导入、文档一起清理干净。

### Q9：LLM 生成的 Cypher 语句不可靠（语法错误、幻觉、注入风险），怎么让自然语言查库安全可用？

**问题**：Text2Cypher 场景中 LLM 直接生成 Cypher 查询，存在三类风险：语法错误导致查询失败；幻觉出的实体/关系名查不到数据；恶意输入注入危险语句。

**解决**（✅ 已解决；该功能已于 2026-08-16 随 Neo4j 退役，此处保留作为历史技术复盘）：构建 Text2Cypher **闭环流水线（责任链模式）**：
- 生成 → 正则校验（拦截危险关键字/非法模式）→ LLM 二次校验（语义与 schema 一致性）→ 自动修正（错误时带错误信息回炉重生成）→ 执行
- 配合 PredefinedCypher：高频固定模式（价格、库存查询）不用现生成，直接按模板填参 + 向量匹配选模板，更快更稳
- 最后一道：生成回答前做**幻觉检测**（LLM 校验回答是否基于事实数据）

**复盘要点**：LLM 输出进入"有副作用"的执行层（数据库/代码）前，必须有不依赖 LLM 的硬校验（正则/白名单），LLM 校验只能作为第二道软校验。责任链让每步职责单一、可独立替换。

### Q10：单一向量检索召回不足、结果有噪音，如何提升检索质量？

**问题**：纯向量检索对关键词精确匹配（型号、SKU）召回弱；检索结果里混入不相关内容时，会污染 LLM 生成回答。

**解决**（✅ 已解决）：三层检索增强——
- **RRF 混合检索**：BM25（关键词）+ 向量（语义）双路召回，Reciprocal Rank Fusion 融合排序，互补两种匹配模式
- **LLM 相关性评分**：对融合结果逐条评分过滤，低于阈值的文档不进 prompt
- 配合**查询改写**：多轮对话先做 context-aware 改写再检索（"它"补全为实体名）

**复盘要点**：检索系统没有银弹——关键词与语义是正交的匹配维度，RRF 融合是低成本高收益的标准组合；检索后的过滤比检索前的调参更可控。

## 三、工程与运维踩坑

### Q11：配置改了不生效，排查半天发现是路径基准问题

**问题**：`config.py` 的 `ROOT_DIR` 基准被设为 `llm_backend/`，`.env` 文件实际在项目根目录，导致 `.env` 从未被加载，所有配置静默使用代码默认值（本地能跑，环境一变全乱）。

**解决**（✅ 已解决）：`ROOT_DIR` 基准改为项目根目录，`.env` 正确加载。配合日志输出"加载 .env 文件路径"便于后续快速定位同类问题。

**复盘要点**：路径基准是配置系统第一根桩。静默回退到默认值比报错更可怕——配置加载失败必须打日志/报警，而不是悄悄用默认值。

---

### Q12：Windows 下升级依赖失败（拒绝访问），是什么在锁文件？

**问题**：`uv sync` 升级 matplotlib 时报 `failed to remove file ... 拒绝访问 (os error 5)`。原因：**正在运行的 uvicorn 服务把旧版 .pyd 文件加载进了进程**，Windows 不允许删除被占用的 DLL。

**解决**（✅ 已解决，实操经验）：
1. 先定位占用进程：`tasklist` + `wmic process get CommandLine` 确认是服务进程
2. 停服务 → `uv sync` → 重启服务 → 轮询 /docs 验证 200
3. 遗留物清理：中断的同步可能留下空的 `*.dist-info` 目录（缺 RECORD），用 `uv pip check` 检测重复安装后手动删除

**复盘要点**：Windows 上"升级失败+拒绝访问"九成是进程锁文件。升级依赖前先停掉加载了该库的进程；升级后用 `uv pip check` 验证环境一致性，别信"装完了"。

---

### Q13：项目里存在"永远导入不了的模块"，要紧吗？

**问题**：全模块导入扫描发现 4 个模块导入失败：3 个是缺少 `streamlit` 依赖的 UI 组件，1 个是缺 `utils` 子包的 guardrails 提示词模块。它们**没有被任何代码引用**——是随原项目迁移遗留的孤儿代码，运行时不可达。

**解决**（✅ 已处理）：确认不可达后不修也不删（不影响稳定运行），记录在案。判断标准：全局 grep 模块名，无人 import 的模块对运行零影响；若是有人 import 但懒加载的模块，则属于"定时炸弹"，必须修或删。

**复盘要点**：模块导入失败 ≠ 系统故障，先判断可达性再动手。清扫项目时用"全模块导入扫描"做体检，比肉眼翻代码可靠。

## 附：高频复盘金句（面试速记）

1. 框架选型先问业务需要什么，能力过剩 = 隐性成本（Q1）

3. 一个项目只允许一个依赖事实源，锁文件必须入库（Q4）
4. 内存态组件只能用于调试，生产必须有持久化 + 降级路径（Q5/Q6）
5. 贵操作（LLM）必须可降级，增强功能不能阻塞主链路（Q6）

7. 复杂度超过场景价值的闭环，砍掉就是优化（Q8）
8. LLM 输出进执行层前，必须有无 LLM 的硬校验（Q9）
9. 关键词与语义正交，RRF 融合是标准答案（Q10）
10. 配置静默回退默认值比报错更可怕（Q11）
11. Windows 依赖升级失败先查进程锁文件（Q12）
