## 一、检索召回问题

### 1. 商品名 + 售后主题混合 query 召回失败
- **现象**："我要退货小米智能门锁pro" 召回商品块（XMZNMS04LM 等）而非退货政策块，政策块掉出 top-3
- **根因**：query 含商品名时，商品块（含商品名）在 BM25/向量两路竞争中天然占优，reranker 精排后政策块出局
- **方向**：售后 Agent 接入时配合实体识别（识别商品名 → 定向查该商品售后政策 + 通用政策）

### 2. 同品牌多型号竞争导致错召回
- **现象**："米家智能晾衣机Pro怎么升降的" top-2 召回无关乐歌块；"米家智能窗帘2支持小爱控制吗" 被窗帘1S 顶掉，窗帘2 自己的块未进 top-3
- **根因**：query 命中品牌/品类泛化词时，同品牌多型号块互相竞争
- **方向**：检索后按商品名二次过滤 / 实体识别归一化

### 3. 自然内容下商品文档跨商品混合块（66%）
- **现象**：500 字符贪心切分下，33 块中 22 块跨商品（相邻商品内容拼一块），reranker 相关度被稀释（实测 E30、鹿客x1 等型号召回不稳定）
- **背景**：内容量随机是生产环境常态，**已明确不做内容约束规避**（450 字符约束已移除）
- **方向**：索引管道切分策略演进——章节感知切分（尊重 H 标题边界，块 = 商品/章节单元）

### 4. 政策文档自然内容章节合并
- **现象**：售后政策文档 1401 字符 → 4 块，"价格保护+售后流程"等章节被贪心合并
- **影响**：B3"按摩椅坏了怎么维修" 命中政策但章节错位（价格保护而非售后流程）
- **方向**：同问题 3，切分策略演进

## 二、链路问题

### 5. 纯售后意图 query 不检索知识库
- **现象**：真实意图识别链路中，"这个芝华仕沙发怎么退货" 判定为 aftersale → 走 `aftersale_placeholder` 占位节点（静态话术），**不触发 RAG 检索**
- **影响**：售后政策文档知识库就位，但纯售后意图 query 拿不到答案
- **方向**：售后 Agent 接入占位节点（替换 aftersale_placeholder），让售后意图 query 检索知识库 + 商品动态表

### 6. 意图识别对"商品参数级售后咨询"的归类依赖 LLM
- **现象**："芝华仕50611B沙发金架保用几年" 被判定为 presale（售前）→ 走 RAG 可答；同类售后咨询归类不稳定
- **影响**：同类问题可能被路由到售后占位节点而不可答
- **方向**：售后 Agent 接入后统一收敛

### 7. 多轮对话省略句不进指代消解（"需要充电吗"漏补全）
- **现象**：多轮对话中，第二轮"需要充电吗"（无代词、无主语）透传消解层 → 检索/缓存拿到残缺 query，结果泛化错误；换问法（"要充电吗""带充电口吗""需不需要充电"）全部漏检——`ELLIPSIS_TRIGGERS` 触发词表（22 词）不含"需要/要/带"等，补词是打地鼠，用户问法无穷（"可以充电吗"因"可以"在词表内可命中）
- **根因**：入口消解层 1 只认显性代词（它/这款/那个）；层 2 省略主语判定依赖触发词穷举，词表不完备。"语义完整性判断"本质是语义任务——免费规则判别器无法同时满足召回≈1 与零维护：长度闸门判别力低（多轮 query 长度普遍相近）；疑问句判定漏"看下价格"类非问句；POS 名词检测漏"多少钱"（钱/n）；商品词典（品牌/品类）判别力强但随上新维护
- **方向**（2026-09-01 更新，方案已定）：
  1. **入口统一 LLM 消解**（`SPEC_ENTRY_LLM_RESOLUTION.md`）：多轮消息进系统时一次 LLM 调用完成指代消除 + 省略补全 + 自包含判定（主流 LangChain/LlamaIndex 做法），正则判定层（代词表/触发词）整体删除——本问题的完整解法
  2. 成本控制：消解模型可配置降档（`RESOLVE_MODEL`）+ 三态日志观测
  3. 保留闸门：纯语气词跳过缓存、无历史直通
- **状态**：方案已定；main 入口部分已实施（2026-09-02，`SPEC_ENTRY_LLM_RESOLUTION.md`——多轮消息无条件 LLM 消解落地 main.py 入口，图内 query 侧闭环）；缓存入口遗留见 #11

### 12. 语义缓存无条件命中/回写价格类动态 query（失败态固化 + 动态价格过期）
- **现象**（2026-09-06，方案 A 动态补全接入后暴露）：
  1. **失败态固化**：动态查询临时失败/商品未收录 → summarize 按口径回答"该商品动态信息暂未收录" → main.py 缓存回写仅"非空才写"门控 → 该失败回答进缓存；DB 恢复后同问仍命中缓存，**永久返回"暂未收录"**
  2. **动态价格过期**：价格类 query 正常回答（含 DB 现价）进缓存 → 价格是动态数据，更新后缓存仍是旧价（¥783.33 变 ¥799 仍答旧值）——违背"价格出 docx 入 DB"的动态性初衷，在缓存层绕回
- **根因**：main.py 语义缓存 lookup/update **无条件执行**，只挡空回答（`if complete_response`）；缓存键与 TTL 未区分"含动态信息的回答"
- **方向**（最小止血二选一，待定）：
  1. **价格意图跳过缓存**：query 含价格/库存意图（Router 判定或关键词门控）→ 跳过 lookup 与 update，该类每轮走全链路
  2. **回写质量门控**："非空才写"升级为"非空且非失败态才写"（检测"暂未收录/稍后再试/暂不可用"等信号）；仍遗留动态过期问题需 TTL 或动态版本键（如 `max(updated_at)` 纳入 key）根治
- **状态**：待实施（2026-09-06 记录；当前 .env `SEMANTIC_CACHE_ENABLED=false` 缓存链路关闭，不影响线上，方案落地需先评估缓存开关恢复场景）

### 13. 消解 max_tokens 被推理 token 吃满 → 返回空静默降级（省略主语场景失效）
- **现象**（2026-09-18 实测发现）：`RESOLVE_MAX_TOKENS` 硬编码 200（`pronoun_resolver.py:32`，不在 config/.env，不可调）。本 provider `deepseek-v4-flash` 为**推理模型**，`reasoning_tokens` 计入 `completion_tokens`；同一 query 推理消耗实测 47~162 token 间波动，200 预算被间歇性吃满 → `finish_reason=length` 且 `message.content` 为**空字符串** → `resolve_pronouns` 按"返回空"降级回原始残缺 query。生产日志真实流量 10 次消解中 **4 次"error 返回空"**，含 `还有多少库存`、`可以上门安装吗`——**恰好都是省略主语场景**，用户侧表现为答非所问，日志仅一条 WARNING、不报错
- **根因**：① `max_tokens` 对推理模型卡的是 reasoning + content 总和，200 系统性不足；② 该值硬编码在模块常量，无法按 provider 调整；③ **空返回与"模型判定自包含原样返回"在日志与返回值上不可区分**——排查时极易误判为 LLM 消解质量问题（本次即先误判为 prompt 规则太宽松）
- **方向**（已实施）：
  1. `RESOLVE_REASONING_EFFORT=none` 关闭消解推理（消解是实体替换+补全，无需推理链）——实测 12 用例 A/B：推理开 9/12 且 3 条空返回；推理关 **12/12 且 0 空返回**，3 次重复结果一致（此前"同输入不同输出"实为间歇性空返回）
  2. `RESOLVE_MAX_TOKENS=1024` 兜底——若 API 将来忽略 `reasoning_effort`，配额仍够（实测推理预算 103~162）
  3. 两个常量 + `RESOLVE_MAX_CHARS_PER_MSG` 收进 config/.env；`RESOLVE_*` 9 项归拢到 .env 单一分节
- **附带修复（同类隐患）**：`.env` **空值行不能接行内注释**——dotenv 不剥离注释，`KEY=  # 注释` 解析出的值就是 `'# 注释'`（非空值时正常剥离）。命中 3 处：`RESOLVE_MODEL`（本次改造引入后立即被端到端验证抓到：model 名变成注释串，消解全链路失败）、`OLLAMA_BASE_URL`、`EMBEDDING_MODEL`（均预存在、潜伏态，当前链路不走）。三处注释均改为独立成行
- **证伪的路线**：降档到非推理模型不可行——可用模型仅 `deepseek-flash` / `deepseek-v4-pro`，实测**同为推理模型**（reasoning=174/147），`RESOLVE_MODEL` 解决不了本问题
- **状态**：✅ 已完成（2026-09-18；test_pronoun_resolve.py 新增 8 条断言，42 通过/11 失败——11 条为 `SEMANTIC_CACHE_ENABLED=false` 导致的既有缓存层失败；全量 pytest 125 通过/1 失败=#8 既有；端到端实测生产降级过的两条已正确补全）

### 14. 知识库文档归属失配 → 前端知识库面板恒为"暂无文档"
- **现象**（2026-09-18 实测发现）：前端知识库面板始终空白。实测 `GET /api/documents?user_id=5` → `total: 0`，而 `?user_id=1` → `total: 2`（两份知识文档 38+4 块）；`users` 表只有 id 3/4/5，**无 id=1**
- **根因**：种子脚本 `scripts/ingest_knowledge.py` 默认 `user_id="1"`，对应当年旧前端**硬编码的 `user.id`**；`SPEC_FRONTEND_VUE3_REFACTOR.md` §24 将前端改为登录态动态取 id（真实 id 3/4/5），**种子数据未同步重挂** → 列表接口按 user_id 过滤恒空
- **为何长期未暴露**：**检索侧完全不按 user_id 过滤**——向量路（`rag_retriever_service.py:82-88` 全表 `order_by(distance).limit(top_k)`）与 BM25 路均无 user_id 谓词，知识库问答始终正常，**故障面仅限列表 UI**
- **加重项**：重跑种子脚本会**重复入库**而非命中去重——查重键是 `(user_id, md5)`（`indexing_service.py:108-116`），归属不一致则整批重灌，污染检索索引（同一内容两份块同时进 RRF 召回）
- **附带发现**：`/api/documents` 不校验 token（无 Authorization 实测返回 HTTP 200），`user_id` 由客户端传入即可任意查询；与 PROJECT_ANALYSIS §10.1"业务端点除 users/me 外均不校验令牌"同源，属既有缺陷
- **方向**（已实施）：
  1. 注册专用账号 `admin_test`（id=6）承接平台公共知识库（`users` 表无 role/is_admin 字段，无真正管理员概念，故以专用账号代替）

  3. `ingest_knowledge.py` 默认归属改为 `DEFAULT_OWNER_ID="6"` 并注明失配后果
- **状态**：✅ 已完成（2026-09-18；端到端实测 登录→`/api/users/me`(id=6)→`/api/documents` 返回 2 份文档，其他 user_id 不受影响；重跑种子脚本汇总 `success=0 duplicate=2 failed=1`、计数不变=2 文档/42 块，幂等性确认）
- **未处理**：① `knowledge_data/` 下的 Word 临时锁文件 `~$…docx` 会被扫描并报 `parse_error`（无害但噪声，建议清理 + 加忽略规则）；② 知识库"平台共享"目前靠**约定**（都挂 admin_test）而非机制，多账号上传的文档仍互相不可见

### 15. 浏览器实测批次：时区恒差 8 小时 / 列表不刷新 / 续聊丢上下文 等 4 项
- **来源**（2026-09-18 真实浏览器操作，Edge + 1004×603 视口，admin_test 登录）
- **a. 相对时间恒差 8 小时**（用户报告，已修）：列表刷新后新建会话显示"8 小时前"。链路：库 `TimeZone=Etc/UTC` 存 UTC → 接口 `isoformat()` **不带时区标记**（`2026-09-18T12:24:51`）→ JS 规范规定无时区的日期时间按**本地时间**解析 → 浏览器实测 `{"JS解析为本地时间":"12:24:51","当前本地":"20:26:35","相差小时":8}`。未刷新时显示正常，因为那一刻用的是前端本地 `new Date()`，未经过服务端
- **b. 首条 query 不立刻进列表**（用户报告，已修）：会话本身**立刻**入列（实测 1.5s），但标题停留在占位名"新对话"——后端 `save_message` 存完才把 title 改成首条 query，而**前端存完消息从不回拉列表**，要整页重载才更新
- **c. 续聊历史会话丢上下文**（排查中发现，已修）：`App.vue:200` 读 `conv.langgraphId`，但该字段**全项目无任何赋值点**；`langgraphConversationId` 仅存内存、取自服务端随机 UUID 的响应头，刷新即丢 → 每次续聊都新起 LangGraph 线程，**AI 对前文零记忆**。实测修复后 `checkpoints` 表出现 `thread_id='41'`（= DB 会话 id），第二条消息使该线程检查点数 4→8 且未新增线程
- **d. 消息顺序不确定**（排查中发现，已修）：一问一答在同一事务写入，`created_at` 取 `func.now()`（事务时刻）→ **两条完全相同**（实测会话 38 的 8 轮全部成对同值），而查询是 `ORDER BY created_at`，问答顺序未定义、可能颠倒
- **e. 密码复杂度校验在登录侧也生效**（排查中发现，已修）：`LoginView.validate()` 未区分 mode，登录也要求"大小写字母+数字、≥8位"。后端认的密码前端直接不给提交——**存量账号会被这条规则永久挡在门外**（本次改密码为 `admin` 后即复现）
- **附带发现（未修）**：① `users`/`conversations`/`messages` 时间列全为 `timestamp without time zone`，本次靠"约定库时区为 UTC"修在序列化层，**改库时区即失效**，根治需迁 `timestamptz`；② `LoginView` 的"记住账号密码"把**密码明文**写进 `localStorage`（`remembered-credentials`）；③ `run.py` 的 `reload=True` 实测**完全不生效**（worker PID 25 分钟未变，touch 亦不触发；已确认非 watchfiles 缺失所致，StatReload 兜底本应工作），改后端后需手动重启才生效——**此前很可能一直在跑旧代码**
- **状态**：a/b/c/d/e 已修并端到端验证（2026-09-18；浏览器实测：侧边栏 `27 分钟前`/`刚刚` 正确、发消息后标题即时更新、续聊线程复用）

### 16. 管理端已引入 role/require_admin，但客户端上传与文档端点仍不校验令牌（既有缺陷，本次未修）
- **来源**（2026-09-22 管理端实施中确认）
- **现象**：`POST /api/upload`、`GET /api/documents`、`DELETE /api/documents/{md5}` 三个端点**完全不校验 `Authorization`**——任何人拿到 URL 就能上传文件进知识库、或列出/删除任意 `user_id` 的文档。管理端上线后，`POST /api/admin/*` 19 个端点都有 `require_admin` 把关，但客户端这三个端点仍是裸的。
- **为什么本次没修**：给它们加鉴权会**连带屏蔽客户端现有的上传/知识库面板**（前端虽带 token，但端点是公开语义，改契约属客户端行为变更），超出管理端模块范围。且现在的安全边界是"内网演示"。

### 17. 管理端已知限制合集（均为有意取舍，非缺陷）
- **来源**（2026-09-22 管理端实施与浏览器验收中确认）
- **a. 文档「停用」不影响检索**：`documents.status='disabled'` 只改管理端展示，向量路与 BM25 路仍会召回该文档的 chunks。加 `WHERE status='enabled'` 要改 `bm25_sql_retriever.py` + `rag_retriever_service.py` 两处 SQL，属检索链路改动，超出管理端范围。前端状态列已加 tooltip 注明。
- **b. 新增商品没有静态知识**：`CLAUDE.md` 知识分层原则禁止把动态信息写进 docx，且新商品本来就没有 docx。管理端只能录价格/库存，智能客服查不到它的参数与售后。
- **c. 改商品名/删商品会打坏 RAG 对齐**：`product_name`/`sku` 是检索对齐键，改名后 docx 里的旧名对不上；删商品后静态知识块仍在库里但价格库存查不到（接口刻意不做级联删除，以保住静态知识）。前端已加二次确认文案。
- **d. 索引进度的「解析文档」阶段在页面上看不到**：服务端确实发出该事件（直连 SSE 实测 6 个阶段全发、百分比 `[5,50,55,60,95,99]` 单调不倒退），但 `.md` 解析近乎瞬时，50% 与 55% 落在 Vue 同一次响应式批处理里，DOM 只画最后一帧。属渲染细节，不是丢事件。

- **f. 刷新浏览器会中断索引**：服务端会取消索引任务（`process_file` 是"最后一步单事务写入"，取消发生在写入前 = 零写入，不留半成品，重传即可）。不做断线重连——那要引入 job 注册表 + 状态存储 + 过期清理三样新东西，为"管理员偶尔刷新"不值。
- **状态**：a~f 为设计取舍，已记入 README 与 spec 归档说明

### 18. 意图识别迭代：规则判定层前置 + 售后二级场景恢复（2026-09-26）

- **背景**：意图识别原为纯 LLM 单次调用，全部 query 走一遍模型。本次在前置加零延迟规则判定层，并恢复售后二级场景维度。
- **规则层**（`app/lg_agent/intent_rules.py`）：明确意图（售前 / 售后含二级 / 闲聊）关键词直接短路，省一次 LLM 往返；未命中降级 LLM。**四道让行闸门**——风险信号词命中 / 未命中场景词 / 多意图 / 售后二级场景多命中，任一触发即交回 LLM。
- **安全设计**：规则层**不判 risk**。含风险信号词（投诉/改装/破解/打款等）的消息一律交回 LLM 判风险，故不产生新的漏拦面；风险词表维护方向与其余词表相反（宁可多收——多收只少省一次调用，永不致错）。
- **词表判据**：**宁可漏不可错**。漏了只是降级 LLM（行为等同改造前），错了则短路走错分支、是真实回归。实测校准拒绝了三个看似增益的加词方案：泛词"怎么样"（把本该 clarify 的"这个怎么样"吃成 presale）、二级场景补词（触发多命中闸门反而降覆盖 30%）、`order_query` 收裸词"订单"（与退货/物流词撞车）。
- **二级场景**：`logistics_query` / `return_refund` / `exchange` / `reship` / `order_query` / `other`（投诉语义不设二级，一律走顶层 complaint）。**本次只落 state + 日志 + 评测，`route_query` 分支未改**——用户可见行为零变化，纯为售后 Agent 预留接口。
