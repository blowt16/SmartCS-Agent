> 核查日期:2026-08-21
> 核查范围:文件上传 → 解析(元数据) → 清洗 → 文本分块 → Embedding → pgvector 入库的完整索引构建链路
> 核查方式:代码走读 + 数据库实查(已启动 Docker,postgres/redis 实测)

## 链路真实结构

```
/api/upload (llm_backend/main.py:193)              ← 唯一上传入口
  └─ 落盘 uploads/{uuid5(user_id)}/{时间戳}/{原名}_{时间戳}.{ext}
  └─ IndexingService.process_file (llm_backend/app/services/indexing_service.py:58)
       ├─ 1. 解析 _parse_document (:33)
       │     .pdf → PyPDF2     .docx → python-docx(仅段落)    其他 → UTF-8 纯文本
       ├─ 2. 清洗 _clean_text (:45)    仅:统一换行符 / 3+ 连续换行压成 2 / strip
       ├─ 3. 分块 (:80)     RecursiveCharacterTextSplitter
       │     CHUNK_SIZE=500 / CHUNK_OVERLAP=50 (.env 配置)
       ├─ 4. Embedding (:84)   embed_in_batches (embedding_provider.py:198)
       │     EMBEDDING_TYPE=qwen → text-embedding-v4, 1024 维, 每批 10 条, L2 归一化
       │     API 失败返回全 0 向量 → 调用方显式抛错, 防静默投毒
       └─ 5. 入库 (:91) → document_chunks 表 (pgvector)
             content_tsv: DB 生成列(pg_jieba jiebacfg), 自动维护
             HNSW 余弦索引 + GIN 全文索引 (scripts/init_db.py:35-48)
```

## 问题清单(按严重度排序)

### P0-1. 商品知识文档没有自动导入入口

- **现状**:`knowledge_data/` 被 gitignore,全仓库(代码/脚本)无任何读取它的逻辑。当前库内 10 条 chunk 是一次性手工索引的产物,仓库里没有对应脚本,无法复现。
- **影响**:换环境 / 重新初始化后,没有任何机制能重建商品语料;RAG 直接退化回空库。
- **证据**:`git check-ignore` 命中;全库 grep 无 `product_knowledge` 引用。

### P0-2. init_db.py 会清空全库数据

- **现状**:`scripts/init_db.py:31` 执行 `Base.metadata.drop_all` → `create_all`,每次初始化删除所有表(含 document_chunks)。
- **影响**:任何人重跑一次初始化,现有 10 条商品知识即永久丢失,且无法自动重建(见 P0-1)。
- **证据**:scripts/init_db.py:30-33。

### P1-3. "库为空"结论已过时,但语料严重不足

- **现状**:项目问题.txt 记载"库为空是当前最大风险";实查库内已有 10 条 chunk(非空),但仅覆盖单一文档 212 行。
- **影响**:检索链路目前"有货但货极少",覆盖面不足;同时项目问题.txt 里的结论需要更新,避免误导后续排查。
- **证据**:DB 实查 TOTAL_CHUNKS=10, BY_SOURCE 仅 1 个来源。

### P1-4. 2026-08-20 上传的 PDF 从未入库

- **现状**:`uploads/adf3796a-f736-572d-a593-33a9a7f89e46/20260820_185958/` 内有一份《1.第一章 计算机操作系统概述.pdf》(840KB, 18:59 上传),但库内无任何记录(全表仅 1 个 source,无 uploads 路径行)。
- **影响**:该次上传失败(Embedding API 失败 / 服务当时未运行 / 解析异常,原因无日志可查)。用户可能以为已上传成功。
- **证据**:DB 实查 BY_SOURCE 仅 1 个来源;`file_path LIKE '%uploads%'` 计数为 0。

### P1-5. 索引链路无任何元数据

- **现状**:解析阶段只输出纯文本,不做任何结构化提取;`DocumentChunk` 表无 metadata / JSONB 列。
- **影响**:商品属性(型号 / 价格 / 库存 / 保修等)无法按元数据过滤或展示来源,检索只能全文相关性;后续若要按品类 / 商家隔离检索,需要回填整表。
- **证据**:llm_backend/app/models/document_chunk.py(仅 source/file_path/user_id/chunk_index/content/embedding/content_tsv/created_at 八列)。

### P2-6. 重复上传无去重

- **现状**:`/api/upload` 每次上传即全量解析入库,不检查同文件是否已存在(文件名 / 内容哈希均未比对)。
- **影响**:同一商品文档上传两次 → 全表重复 chunk,检索重复召回,评分失真。
- **证据**:llm_backend/main.py:193-249 无去重逻辑;indexing_service.py:91-104 直接 add_all。

### P2-7. 上传无类型 / 大小校验

- **现状**:任意扩展名、任意大小文件均可上传;非 pdf/docx 一律按 UTF-8 文本硬读。
- **影响**:二进制文件按文本读取会产生乱码块入库;超大文件无限制。
- **证据**:llm_backend/main.py:193(仅接收 UploadFile);indexing_service.py:41-43 else 分支直接 `open(..., encoding='utf-8')`。

### P2-8. docx 解析丢失表格内容

- **现状**:`_parse_document` 仅遍历 `doc.paragraphs`,不提取 `doc.tables`。
- **影响**:商品参数表(型号对照 / 价格表 / 保修政策表)全部丢失,商品文档表格占比高时语料损失严重。
- **证据**:indexing_service.py:38-40。

### P2-9. 非 UTF-8 编码文本解析失败

- **现状**:纯文本分支固定 `encoding='utf-8'`,无编码探测 / 回退。
- **影响**:GBK 等编码的 txt/csv 上传后解析异常,直接返回 error 状态。
- **证据**:indexing_service.py:42。

### P3-10. 遗留死代码 embedding_service.py

- **现状**:`app/services/embedding_service.py` 仍直接加载本地 SentenceTransformer,全项目无任何 import(与 qwen 切换不同步)。
- **影响**:误导后续维护者以为有两条 embedding 路径;属已知遗留(项目问题.txt 第 2 条),此处仅登记。
- **证据**:全库 grep 无 `embedding_service` 引用(除文件自身)。
