## 1. 问题定性

**这不是 bug，是"指代本身真的有歧义"。**

助手一次列出多款商品后（实测场景）：

```
用户: 你们有智能门锁吗
助手: 我们这边有智能门锁的哦～给您整理了几款在售的：
      · 小米智能门锁2 指静脉版：¥1099.00（有货）
      · 鹿客 S50F：¥1299.00（有货）
      · 小米智能门锁 XMZNMS04LM：¥899.00（有货）
用户: 多少钱          ← "这款"指哪一款？三种理解都成立
```

系统现状：**消解器擅自选一个**。实测危害有三：

| 危害 | 证据（2026-09-26 端到端） |
|---|---|
| 答非所问 | 用户问"这款保修多久"，被消解成"8H 智能电动床保修多久"，回了电动床的保修政策 |
| **选择不稳定** | 同一条对话两次运行，分别选中"鹿客 T1 pro"与"小米智能门锁2 指静脉版" |
| 用户无从察觉 | 系统从不告知"我按 X 理解"，猜错了用户也不知道 |

**为什么不能简单禁止助手列多商品**：导购场景下列多款是**正常且必要**的（用户问"推荐几款"就是要多款）。矛盾必须在**指代环节**化解，不能靠限制助手输出。

## 2. 方案选型

| 方案 | 结论 | 理由 |
|---|---|---|
| **① 追问 + 候选带信息** | ✅ **采纳（用户确认）** | 不猜错；且助手上一条回复里**本来就有**这些商品的价格/型号，追问时直接搬运，用户即使不回答也已拿到信息——不白等一轮 |
| ② 纯追问（只列候选名） | 否 | 用户还得再问一次价格，多一轮且没给信息 |
| ③ 告知式（继续猜 + "我按 X 理解"） | 否 | 只把不确定性摆上台面，没解决；且实测"猜"本身不稳定 |
| ④ 编号式（助手列商品带序号） | 暂缓 | 治本但只覆盖"第 N 个"的说法（"那个小米的"仍歧义）；与 ① 不冲突，可后续叠加 |

**关键设计依据**：候选的关键信息（型号/价格/库存）**已存在于助手的上一条回复中**，澄清节点拿到的是完整 history（经 `MemoryManager`），因此**不需要为候选重新检索**——只做话术组织。这让 ① 的成本远低于"对每个候选各查一次 RAG"。

## 4. 详细设计

### 4.1 消解器：多候选检测（`app/services/pronoun_resolver.py`）

#### 4.1.1 返回契约

```python
@dataclass
class ResolveResult:
    query: str                                  # 消解后文本；歧义时 = 原消息（不擅自选定）
    candidates: list[str] = field(default_factory=list)   # 指代的多个同等候选；空 = 无歧义
```

#### 4.1.2 新增 `resolve_pronouns_ex`，旧函数变薄包装

```python
async def resolve_pronouns_ex(llm_service, messages, raw_query) -> ResolveResult:
    """消解主入口（结构化版）。失败/超时/空一律降级 ResolveResult(query=raw_query, candidates=[])"""
    ...

async def resolve_pronouns(llm_service, messages, raw_query) -> str:
    """兼容包装：只取 query。既有 3 个生产调用点无需改动。"""
    return (await resolve_pronouns_ex(llm_service, messages, raw_query)).query
```

**为什么新增而非改现有签名**：`resolve_pronouns` 有 3 个生产调用点（`main.py:297`、`redis_semantic_cache.py:148`、`evaluation/runner.py:47`）+ 多处测试。新增 `_ex` 版本让这些调用点**零改动**，只有 `main.py` 切到 `_ex`。

#### 4.1.3 输出格式：JSON + **纯文本向后兼容兜底**

prompt 末段由"只输出消解后的完整问题文本"改为：

```
输出 JSON（不要任何解释、不要 markdown 围栏）：
{"resolved": "消解后的完整问题", "candidates": ["候选1", "候选2"]}
```

解析函数：

```python
def _parse_resolve_output(text: str, raw_query: str) -> ResolveResult:
    """解析消解输出。

    兼容纯文本：模型未按 JSON 输出（或旧格式）时，整体作为 query、candidates 为空
    —— 保证既有消解行为在任何解析失败下都不劣化。
    """
```

解析须处理：① ```json 围栏；② candidates 元素非字符串/空串 → 过滤；③ `resolved` 缺失或为空 → 回落 `raw_query`；④ 任何异常 → 整体纯文本兼容。

> ⚠️ **不要新增必填占位符**：本项目刚因 `CLARIFY_SYSTEM_PROMPT` 的 `{question}` 缺参、`str.format` 抛 KeyError 被吞而静默降级的事故（`项目问题.md` #22）排查过同类问题。本节的 JSON 输出格式**直接写死在 prompt 常量文本里**，不经 `str.format` 注入；§4.4 的候选段同理走**独立常量 + 字符串拼接**。

#### 4.1.4 prompt 新增规则 10

在现有规则 1–9（含 2026-09-26 新增的防助手话术泄漏 6/7/8）之后追加：

```
10. **多候选检测**：如果用户当前问题使用了指代词或省略，而上文中有**多个同等合理**的候选
    对象（典型场景：助手上一条回复里列了多款商品），无法唯一确定指代目标——**不要擅自
    选定一个**，把这些候选放入 candidates；其余情况 candidates 必须为空数组。
    · 候选必须是**助手回复里确实出现过的具体对象**（商品名/型号），不得编造、不得臆测
    · 用户已指明目标时（如"小米那款保修多久"），candidates 为空，正常消解
    · 有多候选歧义时，resolved 直接**原样返回用户消息**（不锁定任何对象），
      下游会据此反问用户，不会用 resolved 去检索
```

**与规则 6 的关系**：规则 6 允许"用户没说时，从助手回复里取商品实体"——那是**候选唯一**时的正常消解。规则 10 是**候选多个**时的例外出口。两者不冲突，规则 10 在检测到多候选时优先。

### 4.2 状态传递（`app/lg_agent/lg_states.py`）

```python
@dataclass(kw_only=True)
class InputState:
    messages: Annotated[list[AnyMessage], add_messages]
    # 多候选指代：入口消解检测到用户指代有 ≥2 个同等候选时填入（SPEC_MULTI_CANDIDATE_REFERENCE）
    # 空 = 无歧义。AgentState 继承本字段，route_query 与 clarify_node 均读取。
    ref_candidates: list[str] = field(default_factory=list)
```

**为什么加在 `InputState` 而非 `AgentState`**：图构建为 `StateGraph(AgentState, input=InputState)`（`lg_builder.py:613`），入口只能传 `InputState` 声明的字段；`AgentState` 继承自它，故加在此处一处生效。

**旧 checkpoint 兼容**：`route_query`/`clarify_node` 读取时用 `getattr(state, "ref_candidates", [])` 或 `.get` 风格兜底，避免续聊改造前的会话时 `AttributeError`（同 `sub_type` 的处理，见 `SPEC_INTENT_RULE_LAYER` §11.1 D-c）。

### 4.3 路由分支（`lg_builder.py` `route_query`）

在 `risk` 两级之后、图片分支之前插入：

```python
    # 多候选指代：消解阶段检测到用户指代有 ≥2 个同等候选 → 不猜，问用户
    # 位置在 risk 之后：违规/高风险消息不因指代歧义改道（安全优先）
    candidates = getattr(state, "ref_candidates", None) or []
    if len(candidates) >= 2:
        logger.info("意图路由: 多候选指代({} 个: {}) → 节点=clarify_node | query: '{}'",
                    len(candidates), "、".join(candidates[:3]), query)
        return "clarify_node"
```

**优先级理由**：安全（risk）> 不猜（多候选）> 图片 > 场景 type。

### 4.4 澄清话术（`lg_prompts.py` + `lg_builder.py` `clarify_node`）

> ⚠️ **本节设计已被实测推翻，以下为定稿形态**。原设计（"候选段拼进 system prompt 让 LLM 列出候选"）
> 两轮实测均失败——模型看到上一条助手回复已列过商品，便只写"帮您把刚才提到的两款列出来"
> 而**不列**，第二次还换用词绕过了 prompt 里的禁用表述。完整证据与根因见 **§9.4**。

**定稿：该路径为确定性模板，完全不调 LLM。** 候选列表是确定性数据，不该交给模型重新生成。

`lg_prompts.py`：

```python
# ⚠️ 确定性模板，不走 LLM（理由见 spec §9.4）
CLARIFY_MULTI_CANDIDATE_REPLY = """亲～您问的是哪一款呢？😊
{candidate_lines}
回复序号或型号都可以哦～"""
```

`lg_builder.py`：

```python
_PRICE_RE = re.compile(r"¥\s*([\d,]+(?:\.\d+)?)")
_PRICE_WINDOW = 60   # 候选名之后多少字符内找价格


def _render_candidate_lines(candidates: list, last_assistant_text: str) -> str:
    """把候选渲染成带序号的列表行（确定性，不经 LLM）。

    价格尽力从助手上一条回复里提取：取得到就带上，取不到只写型号——**宁缺毋滥，绝不编造**。
    """
```

```python
# clarify_node 内
candidates = getattr(state, "ref_candidates", None) or []
if len(candidates) >= 2:
    last_assistant = ""            # 取最近一条有内容的 AIMessage
    ...
    return {"messages": [AIMessage(content=CLARIFY_MULTI_CANDIDATE_REPLY.format(
        candidate_lines=_render_candidate_lines(candidates, last_assistant)))]}
# —— 以下为既有 LLM 路径，仅在无候选时执行
system_prompt = CLARIFY_SYSTEM_PROMPT.format(logic=..., question=...)
```

**实际输出**（端到端实测）：

```
亲～您问的是哪一款呢？😊
1️⃣ 小米智能门锁2 指静脉版 —— ¥1099.00
2️⃣ 小米全自动智能门锁Pro —— ¥1358.00
回复序号或型号都可以哦～
```

**注意**：`CLARIFY_SYSTEM_PROMPT` 的 `{logic}`/`{question}` 占位符**未改动**，普通澄清路径不受影响（避免重蹈 #22）。

## 5. 边界情况处理表

| # | 场景 | 期望行为 |
|---|---|---|
| 1 | 助手列 3 款，用户"多少钱" | `candidates=[A,B,C]` → clarify → 列出 3 款及其价格 |
| 2 | 助手列 1 款，用户"多少钱" | 候选唯一 → `candidates=[]` → 正常消解 → presale（**行为不变**） |
| 3 | 助手列 3 款，用户"小米那款保修多久" | 用户已指明 → `candidates=[]` → 正常消解 |
| 4 | 用户消息本身完整、无指代 | `candidates=[]`（不触发） |
| 5 | 多候选 + `risk=violation/high_risk` | **risk 优先**，不因多候选改道（安全优先） |
| 6 | 消解超时/异常/返回空 | 降级 `ResolveResult(query=raw_query, candidates=[])`，**不触发**（保持现有降级语义） |
| 7 | 模型未按 JSON 输出 | 整体作为 `query`，`candidates=[]`（向后兼容，行为同改造前） |
| 8 | 候选 ≥2，但助手上一条没给价格 | 只列候选名，不编造信息 |
| 9 | 首条消息（无历史） | 不消解 → `candidates=[]` |
| 10 | 纯语气词（`_is_filler`） | 跳过消解 → `candidates=[]` |
| 11 | 续聊改造前落盘的 checkpoint | `getattr` 兜底取空列表，不抛 `AttributeError` |
| 12 | 候选 ≥2 但用户消息是售后/投诉等 | 仍走 clarify（指代不明与场景无关）；`ref_candidates` 与 `type` 判定互不影响，但**路由以候选优先**——因为消解未锁定对象，任何场景判定都建立在错误的 query 上 |
| 13 | **澄清一轮后用户仍不指明对象**（如回"能便宜点吗"） | **仍会再次触发澄清**（该句是省略主语，规则 10 同样覆盖）。这是**已知局限**，与"不做澄清上限"的既有决策一致（`项目问题.md` #22）；第二轮的澄清话术因带上候选列表而**不与第一轮雷同**，用户至少知道系统卡在哪 |

### 7.3 端到端验收

复跑 `e2e_multi.py` 的对话1（助手列多款门锁 → "多少钱"）与对话2（推荐扫地机器人 → "这款保修多久"）：

> ⚠️ **本项验收不要写成"T3 应正常消解、不再追问"**——那是我初稿里的想当然。只要用户始终不指明对象，澄清就会持续触发，这正是 §8 R1（触发频率）风险的具体形态。真实流量下若观测到该循环过长，再评估"澄清 N 轮后降级"策略（与 `项目问题.md` #22 同源）。

## 8. 风险与已知局限

| # | 风险 | 说明与缓解 |
|---|---|---|
| R1 | **触发频率可能过高** | 助手列多商品很常见，"列多款 → 用户用指代"就意味着反问。缓解：仅在 `candidates ≥ 2` **且**用户确实用了指代时触发（规则 10 已限定）；用户指明型号时不打扰。**但真实频率当前无法判断**——只有端到端一组样本，需上线后由日志观测（`意图路由: 多候选指代` 的出现比例） |
| R2 | **prompt 改 JSON 输出可能劣化既有消解质量** | 缓解：纯文本向后兼容兜底（解析失败=整体作为 query，行为同改造前）+ #20 的 6 项防泄漏/回归用例作为硬门槛 |
| R3 | 候选可能不完整或编造 | 缓解：prompt 明确限定"必须是助手回复里确实出现过的对象"；澄清话术要求"不重新检索、不编造"，只引用上文已有信息 |
| R4 | 澄清回答被语义缓存命中 | 澄清话术依赖上下文（用户原话 + 候选），被缓存复用会答非所问。当前 `.env` `SEMANTIC_CACHE_ENABLED=false`，缓存链路关闭；**缓存开关恢复前须评估**（另见 `项目问题.md` #11/#12） |
| R5 | **澄清可能连续触发**（主要局限） | `ref_candidates` 是**单轮状态、不跨轮保留**，故不会"记着旧候选追问"；但只要用户新一轮**仍不指明对象**（"能便宜点吗""那个长的"），规则 10 会重新检测到多候选并再次澄清。用户越迟疑、轮次越多。缓解：澄清话术带上候选与信息，用户看到具体选项后指明对象的概率高于面对泛问；且每轮话术不雷同。**根治需"澄清轮次上限"，与 `项目问题.md` #22 同源，用户已决策暂不做**。上线后由日志中该分支的出现比例判断是否需要 |

## 9. 实施记录（2026-09-26）

### 9.1 端到端实测发现的两个缺陷（均已修）

首轮端到端（20 轮）暴露两个单元测试**测不到**的问题：

| # | 缺陷 | 实测证据 | 修复 |
|---|---|---|---|
| E-1 | **候选滚雪球** | 对话1 连续三轮候选数 **3 → 6 → 7**：助手在澄清回复里又列出更多型号，被下一轮当作候选源，越滚越多 | 规则 9 增加"候选**只取自助手最近一条回复**"+"最多 5 个"；并在 `resolve_pronouns_ex` 里**代码兜底截断**（prompt 是请求，不能只靠模型自觉），截断打 WARNING 不静默 |
| E-2 | **澄清话术没真列出候选** | 回答只有"上面给您列了好几款，麻烦您回复一下对应的序号"——**前面根本没有序号**，用户无从回复。原 section 写"直接引用上文"，被模型读成"不必重复列出" | 重写 `CLARIFY_MULTI_CANDIDATE_SECTION`：明确"**序号必须出现在本条回复里**"+ 给出示例格式 + 禁用"请看上面"类表述 |

**教训**：E-2 是典型的"prompt 写了但没生效"——`clarify_node` 没有降级（无 ERROR 日志）、section 确实拼进了 system prompt、回答风格也确实变了（出现了"回复序号"字样），**每一层检查都过，唯独最后用户看到的列表是空的**。只有端到端能看到。

### 9.2 澄清频率实测（用户重点关注项）

| 对话 | 轮数 | 多候选触发 | 实际澄清 | 备注 |
|---|---|---|---|---|
| 对话1·指代与省略密集 | 4 | 3 | **3（连续三轮）** | 用户始终不指明对象 |
| 对话2·售前转售后 | 4 | 0~1 | 0~1 | **两次运行不一致**（见下） |
| 对话3·情绪升级 | 4 | 0 | 0 | 不含指代 |
| 对话4·从澄清中恢复 | 4 | 0 | 3 | 普通澄清（非多候选），`type=clarify` |
| **对话5·已指明主体再用指代（反例）** | 4 | **0** | **0** | ✅ 符合预期 |
| 合计 | 20 | 3~4 | 6 | |

> ⚠️ **检测结果受上游影响、非严格确定**：对话2 的"这款保修多久"在两次运行中一次判多候选（候选 `8H 智能电动床`/`芝华仕 50611B`）、一次按唯一候选正常消解。原因是**助手上一条回复本身每次生成的内容不同**（RAG 检索结果与措辞有波动），候选源随之不同——不是检测器抖动。评估该功能的线上触发率时须考虑这一点。

**对话5 是本 spec 最关心的反例，结果完全符合预期**：用户 T1 自己锁定"小米智能门锁2 指静脉版"后，T2"那个保修多久"、T3"有货吗"均**未被判为多候选**，正常消解并答对（"关于小米智能门锁2 指静脉版的保修问题…"）。**"上一轮已指明商品主体、下一轮用指代会频繁澄清"这一顾虑经实测不成立。** 单元级的真实 LLM 用例 M-5/M-6 同样覆盖该场景并稳定通过。

**但对话1 的连续澄清确实发生了**（用户三轮未指明对象 → 三轮追问），这正是 §8 R5 预警的形态。E-1 修复后候选不再滚雪球，但"用户始终不指明"时仍会连续追问——属已知局限，根治需澄清轮次上限（用户已决策暂不做）。

### 9.3 一处测试期望修正

§7.2 原定 M-3「助手列 3 款 + 用户说"小米那款保修多久"」期望 `candidates == []`——**实测发现是我写错了**：助手列的是**两款小米**（门锁2 指静脉版、全自动 Pro），"小米那款"确实仍有歧义。已拆为两条：
- M-3「鹿客 S50F 保修多久」（唯一型号）→ `candidates == []`
- M-3b「小米那款保修多久」（两款同品牌）→ `candidates` 长度 2，**应追问**（缩窄到品牌是有价值的澄清，不是误判）

### 9.4 设计变更：多候选话术改为**确定性模板，不走 LLM**（实测迫使）

§4.4 原设计是"LLM 生成 + 候选段拼进 system prompt"。**两轮实测均失败**：

| 轮次 | 做法 | 实测结果 |
|---|---|---|
| 第 1 版 | 候选段写"直接引用上文，不要重新检索" | 模型输出"上面给您列了好几款，麻烦您回复一下对应的序号"——**前面根本没有序号** |
| 第 2 版 | 改写为"**序号必须出现在本条回复里**"+ 给示例格式 + 禁用"请看上面"类表述 | 模型换用词绕过禁用表述，输出"帮您把刚才提到的两款列出来"，**然后照样不列** |

**根因（探针实测定位）**：模型并非不会格式化——脱离历史单独调用时，它输出的正是理想格式
（完整列出候选与价格）。但在真实多轮中，**它认为上一条助手回复已经列过商品，于是引用而不重复**。
让模型复述它自认已给过的内容，是逆着其倾向做事。

**改为**：候选列表由 `lg_builder._render_candidate_lines` **代码生成**（含尽力从助手上一条回复
提取的价格，提取不到只写型号、绝不编造），模板 `CLARIFY_MULTI_CANDIDATE_REPLY` 确定性拼接，
该路径**完全不调 LLM**。收益：100% 可靠、可单测、更快更省；代价：话术固定，不随场景变化
（该场景本就是"请您确认哪一款"，固定话术足够）。

**教训**：候选列表是**确定性数据**，一开始就不该交给模型重新生成。这与本次迭代的主线一致——
能确定的事就别让模型猜（对照规则层短路、`sub_type` 跨字段校正、置信度只记录不路由）。

### 9.5 长对话实测（12 轮）暴露的回归 —— 单候选与"缩窄后仍多个"的张力

§9.2 的 5 组对话各只有 **4 轮**，覆盖不到长历史。补测**对话6（12 轮，串联：多候选澄清 →
回复序号 → 指代承接 → 话题切换 → 再次澄清 → 序号 → 场景切换 → 反复 → 情绪升级 → 投诉转人工）**。

**长对话正常项**（此前从未验证）：

| 轮次 | 用户 | 结果 |
|---|---|---|
| T3 | "第2个" | → 消解成"鹿客 x1 智能门锁多少钱" ✔ **序号跨轮可用**——`ref_candidates` 不跨轮保留，靠消解器从历史里那条带 1️⃣2️⃣ 的澄清消息自行解析 |
| T7 | "第一个" | → 正确解析 ✔ |
| T4 / T10 | "这个支持米家吗" / "算了不退了，有货吗" | → 正确承接上文具体型号 ✔ |
| T11→T12 | 情绪升级 → 投诉 | complaint → `high_risk` 转人工 ✔ |

12 轮里仅澄清 1 次，**无澄清风暴**。

**但暴露一处由本 spec 改动引入的回归**（T6）：

```
助手(T5): 关于摄像头，找到这款：小米智能门锁M20 大屏猫眼版 ¥1999.00
用户(T6): 这个多少钱
消解结果: query='这个多少钱'（**未消解**）  candidates=['小米智能门锁M20 大屏猫眼版']（1 个）
→ 残缺 query 进检索 → 答非所问（问摄像头却列出智能门锁与按摩椅）
```

模型给出了"**resolved 未消解 + candidates 只有 1 个**"的自相矛盾输出。按契约，1 个候选不构成歧义，
应正常消解——但改动前的 prompt 没有把这条写死。

**修复与二次教训（本次最值得记的一点）**：
1. 加写"只有 1 个候选不算歧义、应正常消解"→ T6 场景修复 ✔
2. **但该措辞过度泛化**：模型随即对"用户缩窄到品牌、但助手列了两款小米"也直接选定一款
   （M-3b 从通过变失败）——**等于退回本 spec 要消灭的"擅自选定"老毛病**
3. 收紧为"范围缩到**恰好 1 个**才正常消解；缩窄后仍有 ≥2 个**依然是歧义**"，并将两条**并列写成
   互相制衡的规则**，8 项 M 组用例才全部恢复通过

**教训**：prompt 规则之间会互相稀释。修一个边界时若不显式写明"另一条边界不受影响"，
模型会把新规则泛化到邻近case。**修 prompt 必须同时回归相邻边界**，这也是 M 组用例的价值所在。

**补充覆盖**：新增 M-2b（单候选 + 话题切换历史）——原 M-2（单候选 + 简单历史）**通过了却抓不到该 bug**，
说明"看似覆盖"的用例在上下文复杂度上可能不够。

### 9.6 prompt 精简（2026-09-26，1721 → 933 字符，降 45%）

**动机**：`RESOLVE_SYSTEM_PROMPT` 经多轮修补已堆到 9 条规则 + 9 个子项（1721 字符 / 41 行 / 约 1150 token），
维护成本与模型注意力负担都在上升。

**做法与结果**：

| 精简点 | 说明 |
|---|---|
| **"（实测教训：…）"括号注释 ×2** | 那是写给维护者的，模型读到只是噪声 → 挪到 prompt 上方的**代码注释**（含"改本 prompt 前先读这里"的警示与回归用例指路），信息不丢 |
| `candidates 非空 ⟺ 歧义` 与"有多候选歧义时 resolved 原样返回" | 同一条说两遍 → 合并 |
| "用户上一轮已指明" 与"用户当前问题里已指明目标" | 语义重叠 → 合并 |
| 冗余措辞、重复示例 | 压缩 |

结果：**1721 → 888 字符（降 48%）**，9 条关键约束经脚本核对全部保留。

**但纯精简版有一处过度裁剪，被端到端抓到**：

```
旧: 候选只取自助手最近一条回复里列出的对象，不要从更早的对话里翻找
    ——否则候选会随轮次越滚越多（实测 3→6→7），澄清一次比一次更没法回答
新: 候选须是助手最近一条回复里确实出现过的对象（不翻更早历史），不得编造，最多 5 个
```

约束还在，**但"为什么"被删了**。后果（对话6 T7「第一个」，最近一条助手回复无列表时）：
模型去翻 5 轮前那条带 1️⃣2️⃣ 的澄清消息，把**已经翻篇的旧列表**当作候选 → 澄清话术把旧列表又摆给用户。
对比上一轮端到端（旧 prompt），同一位置解析正常。

**恢复该条的理由说明后**（933 字符，降 45%）：T7 不再翻出旧列表；14 条真实 LLM 用例全过；端到端对话5 反例仍 0 误澄清。

**教训**：**prompt 里有两类内容，压缩时要分开对待**——
· **给维护者的**（实测教训、后果推演、历史背景）→ 移到代码注释，模型侧是纯噪声，删了双赢；
· **给模型的"为什么"**（后果说明、反例警示）→ 属于**约束效力的一部分**，不是冗余。删掉约束字面仍在不等于行为不变。
判断办法：只保留"命令"，跑回归看是否劣化；劣化了就把原因加回来。

**已知不稳**：T7「第一个」这类"序号指代但最近一条回复无列表"的输入，三次运行分别出现
「正常消解 / 翻旧列表 / 既不消解也不标歧义」三种结果——**输入本身歧义，模型行为不稳**。
当前 prompt 已消除最差的那种（翻旧列表），其余两种都可接受，未再收紧。
