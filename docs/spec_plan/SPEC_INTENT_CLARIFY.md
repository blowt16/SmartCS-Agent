# 意图澄清功能实施规格（方案 B · clarify 类别 + 澄清节点）

> **用途**: 当用户 query 表达不清晰、意图不明确时，意图识别输出 `type=clarify`，路由到澄清节点——以项目中电商回复的统一风格向用户询问其真实意图（对应福客 SPIIN"信息收齐再处理"精神 F3、§16.3"信息不足时追问而非硬答"）
> **技术栈**: 与既有意图识别模块同构（LangGraph 主图 + 低温结构化输出 + 静态/LLM 生成节点），无新依赖
> **状态**: 待实施（2026-08-27 设计定稿，方案 B 经用户确认：clarify 类别 + 独立澄清节点，非 router 直接反问）
> **关联文档**: [[SPEC_INTENT_RECOGNITION_OPTIMIZATION.md]]（本功能为其增量扩展：Router type 五值 → 六值）

## 1. 背景与目标

### 1.1 背景

1. 现状：Router 单次合并输出 type 五值（presale/aftersale/complaint/general/image）+ risk，模型**总是强制输出一个 type**——意图不明时按"宁放行不误拦"（准则 3）硬猜默认场景（如无上文"这个怎么样"→presale，2026-08-27 实测校准记录）
2. 追问能力（原 additional-query + get_additional_info 节点）已随意图识别重构删除（追问下沉业务 Agent），但业务 Agent 未就位——意图不明消息目前只能硬答或闲聊化，体验不佳
3. 福客参考（§9.3 SPIIN/F3）："信息收齐后再推荐"——意图/信息不明确时先追问而非硬答，是电商客服体验标准做法

### 1.2 目标

| 目标 | 量化指标 |
|---|---|
| 意图不明消息识别 | Router type 增加 clarify 类别，语义上无法确定用户问什么时输出 clarify |
| 澄清话术 | 澄清节点以电商统一风格（"亲～"）针对性询问用户意图，静态模板兜底 |
| 可评测 | golden set 新增 clarify 用例，总条数扩展，二维准确率可复现 |
| 不误伤明确意图 | "你们能便宜点吗""东西坏了"等语义明确的模糊消息**不**触发澄清（边界见 §3） |

### 1.3 明确不做（MVP 边界）

- 连续澄清轮次限制（如"连续 2 轮澄清后转 general"）——后续如有滥用问题再加
- 澄清内容多选项按钮/前端交互——纯文本话术
- 澄清后业务 Agent 联动——业务 Agent 就位后澄清节点可被其"信息收集"环节取代

## 2. 方案选型决策记录

### 2.1 触发机制：clarify 类别 vs 直接反问

| 候选 | 结论 | 理由 |
|---|---|---|
| **新增 type=clarify + 独立澄清节点（方案 B）** | ✅ 采纳（用户确认） | 结构化输出兼容（type 五值→六值）；分类（低温确定性）与生成（澄清话术）职责分离；golden set 可测；话术可独立调整 |
| router LLM 直接反问用户 | 否决 | 破坏 `with_structured_output(Router)` 的 JSON schema（输出变文本即抛异常）；分类与生成混叠导致同输入不同输出；不可路由、不可评测 |
| confidence 阈值 | 否决 | 模型自评分数可靠性存疑；多一个字段增加出错面，收益不如 clarify 类别直接 |

### 2.2 澄清内容生成：LLM 针对性 vs 静态模板

| 候选 | 结论 | 理由 |
|---|---|---|
| **LLM 针对性生成 + 静态模板兜底** | ✅ 采纳 | 澄清节点结合用户原话/`logic` 生成针对性询问（"亲～您是想了解这款灯的哪些信息呢？价格、参数还是使用问题？"），贴合用户语境；生成失败/超时降级静态模板（"亲～请问您想咨询商品信息、售后问题还是其他呢？"） |
| 纯静态模板 | 备选 | 实现最简，但无针对性，模糊消息多时体验同质化 |

### 2.3 与已删除 additional-query 的关系

| 维度 | 原 additional-query（已删） | 本次 clarify |
|------|---------------------------|-------------|
| 触发 | 缺订单号等**私有信息** | 意图**本身不明**（无法归类） |
| 所在层 | 独立技术路由 | 场景路由内的一类 |
| 回答 | 护栏检查 + 追问引导 | 统一风格澄清询问 |
| 定位 | 追问下沉业务 Agent 时删除 | 澄清是识别层职责（识别不了就问），与业务 Agent 的信息收集不冲突 |

## 3. 触发边界定义

### 3.1 触发 clarify（语义上无法确定"用户在问什么"）

| 消息形态 | 示例 |
|---------|------|
| 无上文指代 | "这个怎么样""那个呢"（首条消息无历史可消解时） |
| 无主题词纯语气/碎片 | "嗯…""看看""就是那个" |
| 无法归入任何场景 | "你能帮我吗""你好我想问个事" |

### 3.2 不触发 clarify（语义明确，仅缺细节——由业务 Agent 收集）

| 消息形态 | 示例 | 路由 |
|---------|------|------|
| 正常议价 | "你们能便宜点吗" | presale（不澄清，价格在售前链回答） |
| 语义明确的售后 | "东西坏了" | aftersale（细节/子场景由售后 Agent 信息确认环节收集） |
| 模糊但有主题词 | "你们那个扫地机器人怎么样" | presale（主题词明确） |
| 多意图 | "这灯多少钱？另外怎么退货？" | 取主导意图（准则 4），不澄清 |
| risk 命中 | "怎么改装…（模糊表述）" | risk 优先拦截（violation/high_risk 永远优先于 clarify） |

### 3.3 核心原则

1. **宁澄清不硬猜**：意图不明时不再默认 presale（取代 2026-08-27"这个怎么样→presale"的旧校准，见决策记录 #4）
2. **risk 优先于 clarify**：违规/高风险消息即使表述模糊也先拦截
3. **多意图不澄清**：有任一意图可判即取主导，澄清只在"零意图"时触发
4. **clarify 只判场景，不判风险**：risk 独立判断（意图不明 + 无风险 → clarify + none）

## 4. 目标架构

### 4.1 Router 变更（`lg_states.py`）

type 五值 → 六值（新增 `clarify`）：

```python
class Router(TypedDict):
    """Classify user query: scenario + risk."""
    logic: str                      # 分类理由（供回答生成参考）
    type: Literal[
        "presale",                  # 售前：商品咨询/参数/价格活动/推荐导购
        "aftersale",                # 售后：退货退款/物流异常/订单查询
        "complaint",                # 投诉安抚：情绪不满/投诉（情绪主导）
        "general",                  # 闲聊（原 general-query）
        "image",                    # 图片（原 image-query）
        "clarify",                  # 意图不明：语义上无法确定用户问什么 → 澄清节点
    ]
    risk: Literal[
        "none", "violation", "high_risk",
    ]                               # violation=违规咨询拦截；high_risk=高风险操作转人工
```

`AgentState.router` 默认值不变（`type="general"`）。

### 4.2 路由表更新（主图）

```
意图识别输出（risk 优先级最高）
   │
   ├─ risk=violation   → 风险拦截节点（不变）
   ├─ risk=high_risk   → 转人工节点（不变）
   ├─ type=image       → 图片节点（不变）
   ├─ type=general     → 闲聊节点（不变）
   ├─ type=presale     → RAG 子图（不变）
   ├─ type=aftersale   → 售后占位节点（不变）
   ├─ type=complaint   → 投诉安抚占位节点（不变）
   └─ type=clarify     → 澄清节点【新增】
```

### 4.3 澄清节点（`clarify_node`，新增）

```
进入澄清节点
   │
   ├─ LLM 生成针对性澄清（CLARIFY_SYSTEM_PROMPT + 用户原话 + logic）
   │    电商统一风格："亲～"问候，一次只问一个核心问题（对应福客"提问要具体，一次只问一个问题"）
   │
   └─ 生成失败/超时 → 静态模板兜底
         "亲～请问您想咨询商品信息、售后问题还是其他呢？"
```

- 复用 MemoryManager 历史管理（澄清需结合对话上下文判断问什么）
- 澄清后用户回答 → 下一轮正常重新识别（state.messages 含澄清问答，自然流转，无特殊处理）

## 5. Prompt 设计

### 5.1 ROUTER_SYSTEM_PROMPT 增量（`lg_prompts.py`）

type 分类新增：

```
- clarify 意图不明：语义上无法确定用户在问什么（无主题词、无上文可指代、纯碎片语气词）
  注意：语义明确但缺细节的不在此类（"东西坏了"→aftersale，"你们能便宜点吗"→presale），
  细节信息由业务处理环节收集，不要在意图不明时硬猜场景
```

分类准则新增（或并入准则 1）：

```
- 意图不明时输出 clarify，不要硬猜一个场景；宁澄清不硬答
```

### 5.2 CLARIFY_SYSTEM_PROMPT（新增）

```text
你是一个电商领域的智能客服。用户的问题表达不清晰，需要你友好地询问用户真实意图。

风格要求（统一电商客服风格）：
1. 以"亲～"或"顾客您好～"开头
2. 温和礼貌，适当使用 emoji（😊），结尾表达继续服务的意愿
3. 一次只问一个问题，避免让用户困惑
4. 提问要结合用户的原话针对性询问（如用户提到"灯"→"亲～您是想了解这款灯的哪些信息呢？价格、参数还是使用问题？"）

系统对用户问题的困惑点说明（供参考，不要直接复述）：

<logic>
{logic}
</logic>

用户消息：
{question}
```

静态模板兜底常量：

```python
CLARIFY_FALLBACK_REPLY = "亲～请问您想咨询商品信息、售后问题还是其他呢？"
```

## 7. golden set 更新

现有 42 条调整 + 新增 clarify 用例，总计 **46 条**：

| 调整 | 用例 | 期望（变更） |
|------|------|-------------|
| 变更 | "这个怎么样"（无上文） | presale → **clarify**（宁澄清不硬猜，取代旧校准） |
| 不变 | "你们能便宜点吗" | presale（正常议价不澄清） |
| 不变 | "东西坏了" | aftersale（语义明确，细节售后 Agent 收集） |
| 新增 ×4 | "嗯…""那个呢"（无上文首条）"你能帮我吗""你好我想问个事" | clarify + risk=none |

多轮 5 条不变（"那个呢"有上文时仍判 presale——**上文的指代可消解不算意图不明**；仅无上文可消解时才 clarify）。

> 边界说明："那个呢"首条消息（无历史）→ clarify；"那个呢"承接上文（history 有商品讨论）→ presale。两条用例都入 golden set 验证。

## 8. 影响面分析

| 面 | 影响 | 处理 |
|----|------|------|
| 既有识别行为 | "这个怎么样"等无上文模糊消息从 presale 变 clarify——行为变更 | golden set 期望同步；README/PROJECT_ANALYSIS 记录 |
| 语义缓存 | 澄清回答是否回写缓存：缓存 key 为消解后消息，clarify 消息多为碎片词，与正常查询相似度低，命中概率极低 | 维持现状（回写逻辑不变），后续观察 |
| 指代消解 | 入口消解对"那个呢"（无历史）直接透传（现状），与 clarify 判断衔接自然 | 无改动 |
| 业务 Agent 占位 | 售后/投诉占位节点不受影响 | 无改动 |
| pytest | 现有 9 项不受影响（不涉及 router 新值） | 回归跑一遍 |
| 评测脚本 | golden set 46 条重跑，期望含 clarify | §7 更新后重测 |

## 12. 风险与避坑清单

| # | 风险 | 对策 |
|---|------|------|
| 1 | 澄清滥用：意图其实明确却被反问，体验伤害 | 触发边界严格化（§3）：只有"零意图"才 clarify；golden set 边界用例盯防；后续可加"连续 2 轮澄清转 general"兜底 |
| 2 | 模型把 clarify 当万能出口（信息不足也判 clarify） | prompt 明确"语义明确但缺细节不在此类"；golden set 覆盖议价/损坏用例防回归 |
| 3 | clarify 与指代消解衔接："那个呢"有/无上文的判定差异 | 入口消解对无历史消息透传（现状）；golden set 两条对照用例 |
| 4 | 澄清节点 LLM 失败 | 静态模板兜底（try/except） |
| 5 | 语义缓存命中模糊消息返回旧缓存 | 概率极低（碎片词 vs 正常查询相似度 <0.90），MVP 接受 |
