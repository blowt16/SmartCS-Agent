## 关键操作约定（每个 Task 都适用）

### 工作目录与路径

Archify 的入口固定在技能目录。**所有命令都从这里跑**，输入输出用**绝对路径**：

```bash

```

### meta 字段的硬性约定（**每一张图都适用**）

`meta` 里**只能出现**这四项：

```json
{ "title": "...", "locale": "zh-CN", "quality_profile": "showcase", "output": "<绝对路径>.html" }
```

**必须省略**（出现即为偏离设计）：

| 字段 | 为什么省略 |
|---|---|
| `visual_preset` | 省略才保持默认 `classic`；明暗切换时预设不漂移 |
| `subtitle` | 避免复述标题 |
| `animation` | 本次全部静态，不开 trace 动效 |
| `legend` | 用 `auto` 默认 |

`title` 按 spec §5 各节的图名；`output` 必须是 `D:/SmartCS-Agent/docs/diagrams/<同名>.html` 绝对路径。

### 每张图的三道验收闸门（**缺一不可**）

**`deliver` 通过 ≠ 交付合格。** 实测确认：`deliver` 完全不检查浏览器视口适配，`visual-check` 才会。

```bash
cd "C:/Users/lihansheng/.claude/skills/archify"

# 本机没有 Chrome，但 Edge 是 Chromium 内核且被接受 —— 必须设这个环境变量，否则 visual-check 直接 skip
export ARCHIFY_CHROME="C:\Program Files (x86)\Microsoft\Edge\Application\msedge.exe"

# 闸门 1：改图期间反复用
node bin/archify.mjs validate <type> <json> --quality showcase --json

# 闸门 2：每张图最终一次
node bin/archify.mjs deliver  <type> <json> <html> --quality showcase --json

# 闸门 3：**必须每张图都跑**，不是只到最后统一跑
node bin/archify.mjs visual-check <html> --json
```

| 闸门 | 通过判据 |
|---|---|
| `validate` | `checks[]` 9/9 全 `ok`，`composition.status == "pass"`，退出码 0 |
| `deliver` | `ok: true`，`checksPassed == 9 && checkCount == 9`，`compositionStatus == "pass"`，`errors == 0`，`warnings == 0`，退出码 0 |
| `visual-check` | `status == "pass"`，且**无 `viewer/viewport-overflow` 诊断** |

**`visual-check` 即使失败也可能退出码为 0**——必须读 `status` 字段，不能看退出码。

### 第四道：控制者看图（**三道闸门都查不到构图质量**）

**已实测**：一张全部闸门通过的图，可能构图很糟。第一版 `10-presales-orchestration` 三道闸门全过，但实际渲染出来**主路径在泳道之间斜向穿插、泳道内大片空白**，读起来是"散点斜线"而不是流程。`deliver` 和 `visual-check` 都不评估这个。

**流程要求**：每张图交付后，控制者读取 `docs/diagrams/<name>.visual-check.1440x900.light.png` **亲眼看构图**，并按下列判据检查：

| 判据 | 不合格表现 |
|---|---|
| 主链是否**单条水平线** | 主路径在泳道间反复上下穿插，走成斜线 |
| 泳道是否**内容充实** | 泳道框很高但节点挤在顶部，框内大片空白 |
| 与同批已交付图对比 | 明显比同批其他图散乱 |

不合格 → 打回重排（**保持节点、边、标签不变，只调 lane/col**），不能因为闸门通过就收。

**对照基准**：`00b-dialogue-dispatch` 是合格样板——主链一条水平线、四个分支同泳道横向排开。

> 底部约 120px 的空带在**所有**图里都有（查看器行为），不是缺陷，不要为此改动。

### 通过判据（实测样本确认，非推测）

`deliver --json` 输出中必须同时满足：

```json
"ok": true,
"validation": {
  "checksPassed": 9,
  "checkCount": 9,
  "compositionProfile": "showcase",
  "compositionStatus": "pass",
  "errors": 0,
  "warnings": 0
}
```

且**进程退出码为 0**。

- `checksPassed` 只有 4 项 = 基础校验，**不算通过**
- 非零退出码**一律不得描述为成功**
- `deliver` 失败会**保留上一版 HTML**，此时**禁止**对该路径跑 `visual-check`（那会检查到旧的陈旧产物）

### 修复协议（诊断驱动，禁止盲改）

1. 一次只改**诊断指向的那一处**（`subject`）
2. 只从该诊断给出的 `supportedFixes[]` 里选
3. 改完重跑同一条命令
4. **持续修复直到错误数达到新的最小值**
5. **连续两轮未改善最好成绩 → 停止，如实汇报未解决的诊断**（不得绕过、不得降 `--quality`）

### 几何参数的使用纪律

- **先不加** `via` / `channelX` / `channelY` / `labelAt`——这些是绝对硬钉，加错会直接 `explicit-pin-conflict`
- 优先用路由预设：`drop` / `outside-right` / `return-left` / `bottom-channel` / `up-channel`
- **每轮修复最多加一个几何控制**
- 关系标签是语义数据：标签碰撞时先挪位置、再调间距、**最后**才在同一含义下换更短措辞；**删除语义标签不是几何修复手段**
- 节点标签过宽时优先**加宽节点**（`width`），不要把标识符截断

### 版面布局经验（Task 1 实测得出，**Tasks 2–8 必读**）

1. **同列不要堆节点——优先拆泳道。** 实测代价极大：
   - 3 个节点堆在同一 (lane, col) 让整个文档 viewBox 从 `1106` 涨到 `1906`（**+800，即每个约 +267px**，而非直觉上的 60px）——某一层变高会非线性地撑大全文档的竖向节奏（层距从 190 涨到 342/470）。
   - 5 个分支堆一列还会让扇出边只能绕右侧通道，`routesOverSuggestedBends` = 5（建议上限 2）、`maxStretch` = 3.386（建议上限 1.35）。这些是 advisory 指标（不计入 errors/warnings），但意味着走线绕行严重。
   - Archify 自带的 showcase 示例里**没有任何一张图**在同列堆叠——堆叠没有成功先例。
   - **例外**：spec §5.x 若明确写了同列多节点（如 00b 的业务落点），那是设计选择；此时优先**把它们分散到不同泳道**，而不是竖向堆叠。跑到视口不达标就按 §7.1 上报。
2. **`yOffset` 会削弱直连走线**：编译器对两端 `yOffset` 不同的边会跳过直连净距约束，导致带标签的边绕远路。能靠拆泳道解决就别用 `yOffset`。
3. **`mainPath` 里连续两个 id 必须有真实边**，否则报 `layout/constraint`。写 mainPath 前先对着 `edges` 逐条核。
4. 以下尝试实测**无效**，不要重复：给扇出边加 `route: "bottom-channel"` / `"drop"` / `"outside-right"`（报 `workflow/route-preset-conflict`）、加 `fromSide`/`toSide`/`channelX`（报 `workflow/explicit-pin-conflict`）。
5. `workflow/node-overlap` 的 `supportedFixes` **可能是空数组**。此时由实现者判断最小改动，并在回报里说明——这不算绕过，但要如实记录。

### 视口适配：两条硬约束（**Tasks 2–9 必读**）

Archify 查看器把 SVG 放大到阅读宽度渲染，由此产生一夹一卡：

| 约束 | 阈值 | 触发报错 |
|---|---|---|
| **不能太宽** | viewBox 宽 ≤ **约 1240**（图内最小字号为 8px 副标题时） | `composition/desktop-readability` |
| **不能太高** | 高/宽 ≤ **0.625**（即宽高比 ≥ 约 1.6） | `viewer/viewport-overflow` |

**可行区间约 `1240 × 775`。** 实测公式：`scrollHeight ≈ viewBox高 × 1440 / viewBox宽`；字号投影 `= 源字号 × (930 / viewBox宽)`，下限 6px。

| 样本 | viewBox | 宽高比 | 结果 |
|---|---|---|---|
| 自带 showcase 示例 | `1096 × 684` | 1.60 | **pass** |
| 00a（拆分后） | `1200 × 534` | 2.25 | **pass** |
| 最小五泳道（自然尺寸） | `804 × 776` | 1.04 | fail |
| 最小三泳道（自然尺寸） | `788 × 528` | 1.49 | fail |
| 原五泳道合图 | `1085 × 1906` | 0.57 | fail（四档全溢） |

**已实测排除的无效手段**（不要再试）：减到 4 泳道、去掉 8px 副标题并进主标签、设超宽 viewBox（字缩到 3.1px 被挡）、加宽节点。

**唯一有效手段**：**拆图**，让每张图的自然宽高比 ≥ 1.6。

**做法**：

1. 先按内容自然布局，`deliver` 通过后跑 `visual-check`
2. 若不达标：**先拆图或减节点**，而不是硬调 `meta.viewBox`
3. 只有当自然宽高比已经 ≥ 1.6 但仍差一点时，才用 `meta.viewBox` 微调，且宽度不超过自然内容宽度的 1.6 倍
4. 到不了就**停下上报**——继续拆图是设计决定，不由实现者自决

### 提交边界

每张图交付通过后**单独提交一次**，不攒批。提交信息格式见各 Task。

**提交前必须三道闸门全过**（`validate` → `deliver` → `visual-check`，见上文）。下文各 Task 的步骤只写了 `validate` → `deliver` → 提交，**中间的 `visual-check` 闸门对每个 Task 都成立**，不要因为某一步没写出来就跳过它。任一道不过就继续修，不进下一个 Task。
