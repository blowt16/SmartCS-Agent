# SmartCS-Agent 系统运行流程图（Archify 图集）— 设计文档

**归档状态**：⏳ 待实施（2026-09-26 立项）

**目标**：用 Archify 生成一套可交互、可离线双击打开的 HTML 流程图，覆盖系统整体运行主线与各功能模块细节，放在 `docs/diagrams/` 下。

---

## 1. 背景

项目已有 `docs/PROJECT_ANALYSIS.md`（1391 行，内含约 25 张 mermaid 图）描述系统。本图集与它的关系是**互补而非替代**：

| | PROJECT_ANALYSIS.md | 本图集 |
|---|---|---|
| 载体 | Markdown 内嵌 mermaid | 独立 HTML（可缩放/搜索/切换主题） |
| 措辞 | 业务语言（"向量检索"、"结果汇总"） | **开发视角**（真实文件名、函数名、接口路径、表名） |
| 组织 | 按报告章节（§4.1、§4.4.2…） | 按**运行主线**组织，主图 → 子图两级 |
| 状态标注 | 部分章节有 ⚠️ 同步注 | 未接入/未启用的路径**在图上直接标注** |

## 2. 需求确认结论（与用户逐条确认）

| 项 | 结论 |
|---|---|
| 主图定位 | 端到端主线（不是模块鸟瞰、不是部署拓扑） |
| 标签粒度 | **开发视角**：文件 / 函数 / 接口路径 / 表名 |
| 分支范围 | 正常路径 + **关键兜底**（不做全量异常穷举） |
| 整体结构 | **双主线**：客服对话端到端 + 管理端端到端 |
| 输出位置 | `docs/diagrams/`，含手写 `index.html` 导航页 + `spec/` JSON 源 |

**两处拆分理由**：

1. **售前拆 10 / 11**：编排（planner → Send 并行 → summarize）与检索管线（向量 ∥ BM25 → RRF → 精排）是两套独立结构，挤在一张图里泳道过深、节点过密。
2. **主图拆 00a / 00b**（2026-09-26 实测后定）：Archify 查看器要求图在 1440×900 下**一屏放下且不纵向滚动**，即 **viewBox 宽高比 ≥ 约 1.6**。原 5 泳道 11 节点的合图**天生是竖版**（自然下限 1085 × 1106，宽高比 0.98），无论怎么调参都差 1.6 倍。拆成 00a（主路径，实测 `1200 × 534`，宽高比 2.25）+ 00b（扇出细节）后达标。

**主图概念的变化**：00a 即用户要的「系统整体运行流程图」（一条主线，6 个节点，看全流程）；00b 承接扇出细节。两者合起来覆盖原 00 的全部语义。

## 4. 全局约定

所有 JSON 统一：

```json
{
  "meta": {
    "locale": "zh-CN",
    "quality_profile": "showcase"
  }
}
```

- **不设** `meta.visual_preset`（保持默认 `classic`，明暗切换时预设不漂移）
- **不设** `meta.subtitle`（避免复述标题）
- **静态**：不设 `meta.animation`（不开 trace 动效）
- **不设** `meta.legend`（用 `auto` 默认）
- workflow 一律 `schema_version: 2`；dataflow / lifecycle 为 `schema_version: 1`
- 布局只声明**语义**（lane / col / 关系），不写像素坐标——几何交给 Archify 编译器

## 5. 逐图设计

> 以下节点表为**语义设计**，不是几何设计。创作时按 `validate --layout-json` 的编译器回执调整 col 与路由。

### 5.1a · 00a-dialogue-spine（客服对话端到端主路径）

**这张图就是用户要的「系统整体运行流程图」**：一条主线看完全流程，6 个节点。

| id | lane | col | type | label | sublabel | width |
|---|---|---|---|---|---|---|
| `user` | 接入层 | 0 | external | 用户提问 | 浏览器 Chat UI | 132 |
| `http_entry` | 接入层 | 1 | backend | `POST /api/langgraph/query` | `main.py:216` | 196 |
| `resolve` | 接入层 | 2 | backend | 入口指代消解 | `pronoun_resolver.py` | 168 |
| `router` | Agent 主图 | 3 | backend | 意图识别与路由 | `analyze_and_route_query` | 172 |
| `presale` | Agent 主图 | 4 | backend | 售前导购 | `create_research_plan` → 图 10/11 | 168 |
| `sse` | 出口与存储 | 5 | backend | SSE 流式出口 | `process_stream` | 148 |

`resolve` 可加 `tag: "多轮无条件 LLM"`。

**mainPath**：`user → http_entry → resolve → router → presale → sse`

**边**：

- `http_entry → resolve`：取 history + image_path
- `resolve → router`：消解后的问题
- `router → presale`：`type=presale`（`variant: emphasis`）
- `presale → sse`（`variant: emphasis`）

**cards**（1 张）：入口关键事实——`thread_id` 三态（新会话 / 多轮续聊 / 中断恢复）；入口消解的两个免费闸门（首条无历史直通、纯语气词跳过）。

> **本图已实测达标**：`viewBox 1200 × 534`（宽高比 2.25），`deliver` 9/9 pass、`visual-check` pass。**改动时不要增加节点**，否则宽度会越过 1240 的可读性上限。

### 5.1b · 00b-dialogue-dispatch（对话业务分派与出口）

承接 5.1a 未展开的部分：路由之后**扇出到各业务落点，再汇聚到 SSE 出口**。`cache` 节点也放这里（它带「当前未启用」标注）。

**泳道**：Agent 主图 / 业务落点 / 静态话术与兜底（`variant: exception`）/ 出口与存储

| id | lane | col | type | label | sublabel |
|---|---|---|---|---|---|
| `router` | Agent 主图 | 0 | backend | `analyze_and_route_query` | ScopeGuard + Router 双维识别 |
| `presale` | 业务落点 | 1 | backend | 售前 `create_research_plan` | → 图 10 / 11 |
| `general` | 业务落点 | 1 | backend | 闲聊 `respond_to_general_query` | |
| `clarify` | 业务落点 | 1 | backend | 澄清 `clarify_node` | → 图 20 |
| `image` | 业务落点 | 1 | backend | 图片 `create_image_query` | Qwen-VL |
| `static_replies` | 静态话术与兜底 | 1 | security | 风险拦截 / 转人工 / 售后占位 / 投诉占位 | 4 个静态话术节点合并 |
| `cache` | 出口与存储 | 1 | database | 语义缓存查找 | Redis · **当前未启用** |
| `sse` | 出口与存储 | 2 | backend | SSE 流式出口 | `process_stream` + `stream_filter.py` |

**边与标签**：

- `router → presale`：`type=presale`（`variant: emphasis`，主线）
- `router → general`：`type=general`
- `router → general`：**另一条，虚线**，`ScopeGuard 超范围`（超经营范围直接降级，不调 LLM）
- `router → clarify`：`type=clarify`
- `router → image`：`type=image`（或本条消息带图片）
- `router → static_replies`：`risk=violation` / `risk=high_risk` / 售后 / 投诉
- `cache → sse`：命中直接返回（`role: return`，**虚线**）
- `cache → router`：未命中
- 各业务节点 → `sse`

**必须保留的虚线语义**：`cache → sse` 与 `router → general`(ScopeGuard) 的虚线表示「当前不生效 / 不走 LLM」，**不可合并成实线**。

**cards**（2 张）：

1. 未启用的缓存：`.env:56` `SEMANTIC_CACHE_ENABLED=false`，查与写整体关闭
2. 出口闸门：`stream_filter.py` 拦截 `analyze_and_route_query` / `planner` 的内部推理 token，只放 `summarize` 等用户可见节点

> ⚠️ **本图的视口风险**：业务落点有 4 个节点同列，竖向堆叠会非线性撑高全图（实测每个约 +267px）。**优先把它们分散到不同泳道或不同列**；若仍不达标（宽高比 < 1.6），按 §7.1 上报，不得硬凑。

### 5.2 · 10-presales-orchestration（售前编排）

**泳道**：容器节点（主图）/ multi_tool 子图 / 兜底（exception）

| id | lane | col | type | label | sublabel |
|---|---|---|---|---|---|
| `entry` | 容器节点 | 0 | backend | `create_research_plan` | `lg_builder.py:458` |

| `fanout` | multi_tool 子图 | 3 | messagebus | `Send` 并行派发 | `edges.py` 每任务一个 Send |
| `tools` | multi_tool 子图 | 3 | backend | `customer_tools` 检索节点 | 每子任务一次检索 |
| `summarize` | multi_tool 子图 | 4 | backend | `summarize` | `_assemble_evidence` 单证据串 |

**mainPath**：`entry → planner → fanout → tools → summarize → final`

**标注要点**：

- planner 校验 `2 ≤ tasks ≤ MAX_TASKS`、非空、不重复；**任一不满足 → 回退单分支，任务文本 = 原 query 原文**（不采用 LLM 改写）
- 子图编译时 `__pregel_checkpointer: None`——Send map-reduce 与 PostgresSaver 序列化冲突，**子图内部不写主图检查点**
- 出口流式：`summarize` 逐 token 放行；容器节点整段回填**仅在无 token 流出时**兜底（避免重复）

**mainPath**：`q → vec → rrf → rerank → out`

**关键边与标签**：

- `q → vec`：问题向量化（qwen text-embedding-v4，1024 维）
- `q → bm25`：`jiebacfg ∪ jiebamp` 分词后 `to_tsquery`
- `vec → rrf` / `bm25 → rrf`：**两路独立，单条失败不阻塞**（`asyncio.gather`）

- `sku → dynstore`：批量查询
- `sku → render` / `out → render`：动态区 + 静态块同码配对
- **虚线**：零命中 / 无 sku 块（政策、通用）**不查**动态库 → 直接 `render`
- `tool_rag → q`：**虚线，标注"同一入口，未接入"**（全项目无 `bind_tools` 调用，仅存在于注释与 docstring）

- `scope → memory`（放行）

**流（label 必填）**：

- `form_modal → stage_api`：上传文件
- `stage_api → staging`：扩展名 / 大小校验通过 → 写暂存（**无解析、无 DB 行**，保证取消可逆）
- `staging → commit_api`：确认提交
- `commit_api → index_svc`：`user_id` 取 **JWT**（与 `/stage` 取 form 字段不对称）
- `index_svc → doc_parser`：按 `file_type` 分支
- `doc_parser → cleaner → splitter → embedder → documents/chunks`
- `index_svc → sse_progress`：`progress` / `done` / `error` 三类事件（封顶 99，100 只由 `done` 发）
- **兜底**：`DELETE /knowledge/{md5}` 级联删 chunks（避免孤儿块仍被检索）；暂存残留 TTL 24h 机会式清理
- **注意**：`documents.status='disabled'` **不影响检索**（向量/BM25 SQL 均不过滤）

### 5.8 · 60-order-lifecycle（订单状态生命周期，lifecycle）

**主轨状态**（4 个，对应 `ORDER_STATUSES`）：

| id | lane | col | type | label |
|---|---|---|---|---|
| `processing` | 订单状态 | 0 | start | 处理中（默认值） |
| `shipped` | 订单状态 | 1 | active | 已发货 |
| `delivered` | 订单状态 | 2 | active | 已送达 |
| `signed` | 订单状态 | 3 | success | 已签收 |
| `clear` | 签收日期 | 0 | decision | `status ≠ 已签收` ⇒ 强制 `signed_date = NULL` |
| `autofill` | 签收日期 | 1 | decision | `status = 已签收` ⇒ 传入值 → 保留原值 → 取当天 |

**迁移**：

- `processing → shipped`：发货
- `shipped → delivered`：送达
- `delivered → signed`：签收
- `processing → signed`：**虚线**，标签「管理员可直接改（**无状态机约束**）」——代码中无枚举类、无状态机，`PUT /api/admin/orders/{id}` 可设为任意四值
- `signed → autofill`：填签收日期
- 非已签收状态 → `clear`：强制清空

**必须如实呈现**：主轨是"常规推进"，虚线跳转是真实的放任行为，两者都要画。

## 7. 验证与验收

node bin/archify.mjs validate <type> spec/xx.json --quality showcase --json

**验收标准**（缺一不可）：

3. `deliver` 通过后**不再改动**该 JSON（交付会把当时字节冻结进快照）
4. 桌面尺寸 1440×900 / 1600×1000 / 1920×1080 / 2048×1320 均满足 `scrollWidth ≤ innerWidth` 且 `scrollHeight ≤ innerHeight`
5. 反复修复两轮仍无改善时，**停止并如实汇报**未解决的诊断

**执行注意**：`deliver` **不检查**第 4 条（视口适配），只有 `visual-check` 会。每张图都必须单独跑 `visual-check` 并确认 `status == "pass"`——该命令**即使失败也可能退出码为 0**，必须读 `status` 字段。

### 7.1 两条硬约束（2026-09-26 实测）

Archify 查看器把 SVG 放大到阅读宽度渲染，由此产生一夹一卡：

| 约束 | 阈值 | 触发报错 |
|---|---|---|
| **不能太宽** | viewBox 宽 ≤ **约 1240**（当图内最小字号为 8px 副标题时） | `composition/desktop-readability`（字投影 < 6px） |
| **不能太高** | viewBox **高/宽 ≤ 0.625**（即宽高比 ≥ 约 1.6） | `viewer/viewport-overflow` |

两者合起来，可行区间约 **1240 × 775**。

**实测依据**：`scrollHeight ≈ viewBox高 × 1440 / viewBox宽`；字号投影 `= 源字号 × (930 / viewBox宽)`，下限 6px。自带 showcase 示例 `1096 × 684`（宽高比 1.60）通过；原五泳道合图 `1085 × 1906`（0.57）四档全溢。

**已实测排除的无效手段**（不要再试）：减到 4 泳道（仍 1556 高）、去掉 8px 副标题并进主标签（高度纹丝不动）、设超宽 viewBox（字缩到 3.1px 被挡）、加宽节点（宽度只从 788 到 872）。

**唯一有效手段**：**拆图**，让每张图的自然宽高比落在 1.6 以上。

| 结论 | 由谁证明 |
|---|---|
| 产物确定性检查通过 | `deliver` |
| 真实浏览器有界行为 | `visual-check` |
| **好不好看（审美）** | **只能由人/图像审查者判断，不由我打勾** |
