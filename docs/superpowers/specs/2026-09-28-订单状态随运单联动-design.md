> **归档状态**：⏳ 待实施（2026-09-28 定稿，尚未落地）

> **本文档取代**：`docs/superpowers/specs/2026-09-27-管理端物流模块-design.md` §9③

> 物流模块其余部分（§4 的四个端点、§4.5 三条校验规则、轨迹格式）继续有效，不受影响。

## 1. 背景

### 1.1 现状

物流模块（2026-09-27 落地）刻意把订单状态与运单状态**解耦**：建运单时校验一次订单状态，之后两者各走各的、互不影响。实测确认（2026-09-28）：

- 运单状态改成「已签收」，订单状态纹丝不动
- 运单状态改成「异常」，订单状态纹丝不动
- 库里 ORD-015 是「订单已送达 + 运单已签收」—— 签收了订单却没签收，系统不报错也不纠正

当时的决策理由写在 §9③：「订单状态现在是任意跳转、无状态机约束的…这是有意的设计，不是遗漏。」

### 1.2 本次目标

**改为由运单状态控制订单状态**，并扩展两侧的状态集合，让订单状态成为物流推进的自然结果。

用户原话：「完全由运单状态控制订单状态吧，可以模拟真实的订单和运单就行了」。

### 1.3 一句话概括

订单状态从「管理员手填的字段」变成「运单状态的投影」。想推进订单 → 去改运单。

## 2. 决策记录

以下每一条都是与用户逐条确认过的，**含被否决的选项**（避免后来者重新提议）。

| # | 决策 | 被否决的选项与理由 |
|---|---|---|
| D1 | **纯派生**：订单状态完全由运单状态推出 | 否决「同步写入」：运单改动时写一次订单，但管理员仍可手改 → 两边仍可能不一致，等于没解决 ORD-015 那类问题 |
| D2 | **放宽建运单门槛**：允许给「处理中」订单建运单 | 否决「保留门槛」：那样「运单已生成但订单还没发货」这个状态在本系统不存在，用户表里第 1 行落不了地 |
| D3 | 运单「待揽收」→ 订单「处理中」 | 否决「新增订单状态『待发货』」：用户明确说不加，用「处理中」兼任 |
| D4 | 订单状态集 **5 个**：处理中 / 已发货 / 已签收 / 售后处理中 / 已退款·交易关闭 | 否决「新增『已完成』」：与「已签收」语义重复，用户选择只保留「已签收」 |
| D5 | **删除订单状态「已送达」** | 用户先选 D6 再确认删除。纯派生下每个订单状态都必须有运单状态能触发，而「派送中」已给了「已发货」，它成了死值 |
| D6 | 运单「派送中」→ 订单「已发货」 | 否决「派送中 → 已送达」（那会保住「已送达」）。用户选择忠实原始映射表 |
| D7 | 运单状态集 **8 个**：新增「退货中」「已退货」 | 否决「只加已退货」：退货走到一半（已寄回未到）没地方放 |
| D8 | **删除运单 → 订单回「处理中」** | 否决「订单状态冻结不变」：会出现「订单已签收、但一条运单都没有」的行，正是纯派生要消除的不一致 |
| D9 | **订单接口不再接受 status / signed_date** | 纯派生的必然结果。代价是订单页的状态下拉消失，用户已确认接受 |
| D10 | **本次不改客服 Agent**（`app/lg_agent/`） | 用户明确：客服的回复话术属于**后续售后 Agent 的开发范围**，不在本次。技术上也不需要同步改 —— `lg_agent/` 对状态值零引用（见 §9），本改动不会破坏它 |

### 2.1 状态映射表（唯一事实来源）

| 运单状态 | → | 订单状态 |
|---|---|---|
| 待揽收 | → | 处理中 |
| 已揽收 | → | 已发货 |
| 运输中 | → | 已发货 |
| 派送中 | → | 已发货 |
| 已签收 | → | 已签收 |

| 退货中 | → | 售后处理中 |

## 3. 单一事实来源

### 3.1 问题

状态常量当前散在三处，再加映射就是第四处：

- `app/schemas/admin.py:70` — `SHIPPABLE_ORDER_STATUSES`
- `app/api/admin/console.py:18` — `ORDER_STATUSES`（与 schemas 里的正则同值但独立）
- `app/schemas/admin.py:31,42` — 写死的正则 `^(处理中|已发货|已送达|已签收)$`
- `app/models/order.py:20` — 注释里写死状态集

2026-09-27 那份 spec 已经吃过这个亏（专门写过「两份同义集合必然漂移」），本次新增 2 个订单状态 + 2 个运单状态，不收敛必然漏改。

### 3.2 方案

新建 `llm_backend/app/services/order_status.py`，作为状态集与映射的唯一出处。

选 `app/services/` 的理由：该目录已是业务逻辑层（`user_service.py`、`product_dynamic_service.py`），而 `app/core/` 放的是基础设施（database / logger / security / config），`app/schemas/` 是校验层 —— 状态映射是业务规则，两处都不合适。

**依赖方向**：`services/order_status.py` 不 import 任何上层模块 → `schemas` / `api` / `scripts` 单向下行引用它，无循环导入。（已确认 `app/services/__init__.py` 为空，import 该包无副作用。）

```python
# llm_backend/app/services/order_status.py
"""订单状态 ⇄ 运单状态的唯一映射处。

订单状态不直接编辑,而是【纯派生】自运单状态:改运单 → 订单自动跟随。
本模块是两侧状态集与映射关系的单一事实来源 —— models / schemas / api / 种子脚本
一律从这里取,不得各自再写一份(2026-09-27 的物流模块 spec 已记录过
「两份同义集合必然漂移」这个教训)。
"""

from datetime import date
from typing import Optional

# 订单状态(5 个)。
# ⚠️ 顺序即控制台环形图的图例顺序,与前端 ConsoleView.vue 的 ORDER_COLORS 按下标绑定 ——
#    调整顺序必须同步改那个数组,否则颜色与图例错位。
ORDER_STATUSES = ["处理中", "已发货", "已签收", "售后处理中", "已退款·交易关闭"]

# 运单状态(8 个)。顺序即物流页状态下拉顺序。
SHIPMENT_STATUSES = ["待揽收", "已揽收", "运输中", "派送中",
                     "已签收", "异常", "退货中", "已退货"]

# 派生的唯一依据。8 → 5,多对一。
SHIPMENT_TO_ORDER = {
    "待揽收": "处理中",
    "已揽收": "已发货",
    "运输中": "已发货",
    "派送中": "已发货",
    "已签收": "已签收",
    "异常": "售后处理中",
    "退货中": "售后处理中",
    "已退货": "已退款·交易关闭",
}

# 没有运单时订单的落点(删除运单 / 建单初始值都用它)。
# 提成常量而不是散落的字面量:这个值在三个端点与种子脚本里都要用,
# 写错一个(比如写成「已发货」)会让"没运单却有状态"的洞重新出现。
NO_SHIPMENT_ORDER_STATUS = "处理中"


def derive_order_status(shipment_status: str) -> str:
    """运单状态 → 订单状态。

    入参必须来自 SHIPMENT_STATUSES(由接口层 schema 的正则保证)。
    用 [] 而不是 .get() —— 映射表缺少某个运单状态时应当立刻抛 KeyError,
    而不是静默返回 None 把订单状态写成空值(那会绕过 NOT NULL 变成 500)。
    """
    return SHIPMENT_TO_ORDER[shipment_status]


def sync_order_from_shipment(
    order, shipment_status: Optional[str], signed_at: Optional[date]
) -> None:
    """把运单状态投影到订单上 —— 状态与签收日期一起。

    shipment_status 为 None 表示该订单当前【没有运单】(刚被删除,或还没建):
    没有派生来源,订单回到 NO_SHIPMENT_ORDER_STATUS,签收日期清空。

    ⚠️ 签收日期【直接跟随运单】,不各算各的。
    两处独立计算必然生出自相矛盾的演示数据 —— 库里 ORD-015 曾经就是
    「订单已送达、运单已签收」这类不一致。运单是「已签收、日期不详」
    (signed_at 为 NULL,物流模块 §4.5 明说有意的可达状态)时,订单也跟着是 NULL,
    两边保持一致。

    ⚠️ 只改 ORM 对象属性,【不 flush】—— 调用方负责把它并进自己那次 flush 里,
    这样同步与运单写入在同一个事务,冲突回滚时两边一起回退。

    ⚠️ 入参用【值】而不是 Shipment 对象。调用方在 rollback 会让 session 里所有
    ORM 对象过期,之后读属性触发惰性刷新、异步下抛 MissingGreenlet
    (项目踩过的坑,orders.py:115 有同款注释)。传值就没有这个风险。
    """
    if shipment_status is None:
        order.status = NO_SHIPMENT_ORDER_STATUS
        order.signed_date = None
        return
    order.status = derive_order_status(shipment_status)
    # 非「已签收」时运单的 signed_at 本来就由规则 A 强制为 NULL,这里再兜一次,
    # 防的是"直接构造 Shipment 行"的脚本绕过接口写入不一致组合。
    order.signed_date = signed_at if order.status == "已签收" else None
```

## 4. 后端行为

### 4.1 建运单 `POST /api/admin/logistics`

**校验顺序**（沿用现有顺序，仅第 ③ 条换内容）：

1. 订单存在？ 否 → `400 "订单不存在: {order_no}"`
2. 该订单已有运单？ 是 → `409 "订单 {order_no} 已有运单，请勿重复创建"`
3. **订单状态必须是「处理中」** 否 → `400 "订单 {order_no} 当前状态为「{status}」，只有「处理中」的订单才能建运单"`

> **② 仍在 ③ 之前**：这是 2026-09-27 spec 的记录（`test_create_duplicate_beats_processing_status` 钉住）。订单已有运单时真实原因是"重复建单"，报"状态不对"会误导管理员。
>
> **③ 为什么是「处理中」**：纯派生下「非处理中」等价于「已有运单」，所以这条是给**脏数据**兜底的 —— 万一哪条订单状态是「已发货」却没有运单，② 放行、③ 拦住，给出能指导修改的文案。（正常数据下 ② 会先命中。）

**写入**：建完 `Shipment` 后调 `sync_order_from_shipment(order, shipment.status, shipment.signed_at)`。「待揽收 → 处理中」是恒等映射，所以此处订单状态不变 —— 但**仍要调用**，因为同步逻辑只有一个入口，特判"反正不变"会让这条恒等关系分散到两处。

### 4.2 编辑运单 `PUT /api/admin/logistics/{id}`

在现有三条规则（§4.5 规则 A/B/C）与 `setattr` 之后、`flush` 之前：

```python
    # 同步必须在 setattr 之后取运单的 effective 值(此时 shipment.status 已是新值)
    sync_order_from_shipment(order, shipment.status, shipment.signed_at)

    try:
        await db.flush()
    except IntegrityError as e:
        await db.rollback()
        raise _conflict_409(e, order_no, tracking_no)
```

需要新增一次 Order 查询（当前只查了 Shipment）：

```python
    order = (await db.execute(
        select(Order).where(Order.order_no == shipment.order_no)
    )).scalar_one()
```

> ⚠️ 这次查询必须在 `try` **之前**、`order_no` 取成局部变量**之后**。`rollback()` 会让 session 里所有 ORM 对象过期，`shipment.order_no` 在 rollback 后再读会抛 `MissingGreenlet`（`logistics.py:410-413` 已有同款注释）。

**签收日期的联动**：运单状态改成「已签收」时，`shipment.signed_at` 由规则 A 算出（传入 → 原值 → 补当天），订单的 `signed_date` 直接取这个值，不再走 `orders.py` 那套"传入→原值→今天"。改回非「已签收」时运单 `signed_at` 被规则 A 置 NULL，订单 `signed_date` 同步置 NULL。

### 4.3 删运单 `DELETE /api/admin/logistics/{id}`

```python
    order = (await db.execute(
        select(Order).where(Order.order_no == shipment.order_no)
    )).scalar_one()
    await db.delete(shipment)
    sync_order_from_shipment(order, None, None)
```

订单回「处理中」，签收日期清空（决策 D8）。

删掉运单后该订单在物流页回到「未录入」行，可以重新补录 —— 这让演示流程可循环。

> ⚠️ **这个端点现在会写两张表**（删 shipments 行 + 改 orders 行），原有那句「不显式 flush 是安全的，因为返回体是常量」的理由**只对一半成立**了。仍不加 flush 的判断依据是：本端点要写的是一个**合法常量**（`status = "处理中"`、`signed_date = None`），不存在 UNIQUE / FK 冲突的可能，也不会像建单那样依赖 flush 把 IntegrityError 收敛成 409。既然 `get_db` 在响应后必然 commit，多一次 flush 只是多一次往返。**若将来给删除端点加了任何可能冲突的写入，必须补上 flush 并接 `_conflict_409`。**

### 4.4 物流列表入选条件

**现状**：

```python
conds = [or_(Order.status.in_(SHIPPABLE_ORDER_STATUSES), Shipment.id.isnot(None))]
```

**新**：

```python
conds = [or_(
    Shipment.id.isnot(None),          # 已有运单的(含待揽收 → 订单是「处理中」)
    Order.status == NO_SHIPMENT_ORDER_STATUS,   # ∪ 还没建运单、需要补录的
)]
```

第二个分支仍然不可省 —— 它是「补录」入口的来源：没有它，任何还没建运单的订单都不会出现在物流页，也就永远无法为它创建第一条运单。这与旧结构里那条「孤儿不隐身」护栏是同一个位置，但**触发条件变了**：旧护栏防的是"订单状态被改回处理中"，现在防的是"还没建运单"。

其他查询参数（`keyword` / `status` / `order_status`）逻辑不变。`status == UNRECORDED` 的分支（`Shipment.id IS NULL`）继续有效。

### 4.5 订单接口 `app/api/admin/orders.py`

| 端点 | 改动 |
|---|---|
| `POST` | 删除 `status` / `signed_date` 入参。新建订单恒为 `status="处理中"`、`signed_date=None`。删掉原 L121-124 的"已签收则补当天"逻辑 |

### 6.2 `seed_shipments.py`

从"只覆盖已送达/已签收"扩展为**覆盖全部 8 种运单状态**，让物流页、订单页、控制台环形图都有数据。

**分配方案**（18 条订单，按 `order_no` 升序确定性分配）：

| 数量 | 运单状态 | 派生出的订单状态 | 说明 |
|---|---|---|---|
| 3 | **无运单** | 处理中 | 演示「未录入 + 补录」 |
| 4 | 待揽收 | 处理中 | 运单已建、未揽收 |
| 2 | 已揽收 | 已发货 | |
| 2 | 运输中 | 已发货 | |
| 2 | 派送中 | 已发货 | |
| 2 | 已签收 | 已签收 | 有签收日期 |
| 1 | 异常 | 售后处理中 | |
| 1 | 退货中 | 售后处理中 | |
| 1 | 已退货 | 已退款·交易关闭 | |

合计 3+4+2+2+2+2+1+1+1 = **18**，与 `ORDER_COUNT` 一致。订单侧得到 5 个状态：处理中 7 条（3 无运单 + 4 待揽收）、已发货 6 条、已签收 2 条、售后处理中 2 条、已退款·交易关闭 1 条 —— 控制台环形图 5 色都有非零数据。

**字段推导规则**：

| 运单状态 | `shipped_at` | `signed_at` | 轨迹 |
|---|---|---|---|
| 待揽收 | NULL（尚未发货） | NULL | 无（尚未揽收，空值合理） |
| 已揽收 | 下单日 +1 | NULL | 1 节点 |
| 运输中 | 下单日 +1 | NULL | 2 节点 |
| 派送中 | 下单日 +1 | NULL | 4 节点（沿用现有模板） |
| 已签收 | 下单日 +1 | 下单日 +2 | 5 节点（沿用现有模板） |
| 异常 | 下单日 +1 | NULL | 3 节点（末端为异常事件） |
| 退货中 | 下单日 +1 | NULL | 3 节点 |
| 已退货 | 下单日 +1 | NULL | 5 节点（末端为退回寄件人） |

**同步方式**：建完运单后调**同一个** `sync_order_from_shipment()`，不要在种子脚本里另写一份订单状态映射 —— 那是第四份同义集合。

**保留的既有约束**（`seed_shipments.py` 现有注释已记录，继续遵守）：
- 窗口不足一天则跳过该订单（`signed_at - shipped_at < 1`），不硬种出自相矛盾的轨迹
- 轨迹节点不得落到未来
- 日期一律 UTC，与 `seed_orders.py` / 图表日期轴同基准

### 6.3 在库数据

不写单独的迁移脚本。种子脚本本就是 upsert 覆盖语义（`seed_orders.py` 文档注明"重跑同时起到刷新演示数据的作用"），**重跑两个种子即完成校准**。

现有 18 条订单 / 8 条运单中，不合新规则的有：

- 4 条「已送达」订单 —— 该状态已删除，必须迁移
- 5 条「已发货」但无运单的订单 —— 纯派生下不可能，会被刷回「处理中」
- ORD-015「已送达 + 运单已签收」—— 状态不一致，会被校准为「已签收 + 已签收」
