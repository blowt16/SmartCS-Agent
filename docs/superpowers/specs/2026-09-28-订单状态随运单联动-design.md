## 1. 背景

### 1.1 现状

物流模块（2026-09-27 落地）刻意把订单状态与运单状态**解耦**：建运单时校验一次订单状态，之后两者各走各的、互不影响。实测确认（2026-09-28）：

- 运单状态改成「已签收」，订单状态纹丝不动
- 运单状态改成「异常」，订单状态纹丝不动
- 库里 ORD-015 是「订单已送达 + 运单已签收」—— 签收了订单却没签收，系统不报错也不纠正

当时的决策理由写在 §9③：「订单状态现在是任意跳转、无状态机约束的…这是有意的设计，不是遗漏。」

### 1.2 本次目标

**改为由运单状态控制订单状态**，并扩展两侧的状态集合，让订单状态成为物流推进的自然结果。

用户原话：「完全由运单状态控制订单状态吧，可以模拟真实的订单和运单就行了」。

### 1.3 一句话概括

订单状态从「管理员手填的字段」变成「运单状态的投影」。想推进订单 → 去改运单。

## 2. 决策记录

以下每一条都是与用户逐条确认过的，**含被否决的选项**（避免后来者重新提议）。

| # | 决策 | 被否决的选项与理由 |
|---|---|---|
| D1 | **纯派生**：订单状态完全由运单状态推出 | 否决「同步写入」：运单改动时写一次订单，但管理员仍可手改 → 两边仍可能不一致，等于没解决 ORD-015 那类问题 |
| D2 | **放宽建运单门槛**：允许给「处理中」订单建运单 | 否决「保留门槛」：那样「运单已生成但订单还没发货」这个状态在本系统不存在，用户表里第 1 行落不了地 |
| D3 | 运单「待揽收」→ 订单「处理中」 | 否决「新增订单状态『待发货』」：用户明确说不加，用「处理中」兼任 |
| D4 | 订单状态集 **5 个**：处理中 / 已发货 / 已签收 / 售后处理中 / 已退款·交易关闭 | 否决「新增『已完成』」：与「已签收」语义重复，用户选择只保留「已签收」 |
| D5 | **删除订单状态「已送达」** | 用户先选 D6 再确认删除。纯派生下每个订单状态都必须有运单状态能触发，而「派送中」已给了「已发货」，它成了死值 |
| D6 | 运单「派送中」→ 订单「已发货」 | 否决「派送中 → 已送达」（那会保住「已送达」）。用户选择忠实原始映射表 |
| D7 | 运单状态集 **8 个**：新增「退货中」「已退货」 | 否决「只加已退货」：退货走到一半（已寄回未到）没地方放 |
| D8 | **删除运单 → 订单回「处理中」** | 否决「订单状态冻结不变」：会出现「订单已签收、但一条运单都没有」的行，正是纯派生要消除的不一致 |
| D9 | **订单接口不再接受 status / signed_date** | 纯派生的必然结果。代价是订单页的状态下拉消失，用户已确认接受 |
| D10 | **本次不改客服 Agent**（`app/lg_agent/`） | 用户明确：客服的回复话术属于**后续售后 Agent 的开发范围**，不在本次。技术上也不需要同步改 —— `lg_agent/` 对状态值零引用（见 §9），本改动不会破坏它 |
| D11 | **种子重跑前先清掉种子范围内的运单** | 否决「只 upsert 不删」：upsert 无法表达"这条不该有运单"，库里已有的 8 条运单删不掉 → 「无运单」桶落不了地，重跑结果取决于库里现状 |
| D12 | **建运单时允许直接选任意状态**（含「已签收」「已退货」） | 否决「建单锁死为待揽收」：补录历史数据时两步就能造出已签收订单；锁死要改 5 次 |

### 2.1 状态映射表（唯一事实来源）

| 运单状态 | → | 订单状态 |
|---|---|---|
| 待揽收 | → | 处理中 |
| 已揽收 | → | 已发货 |
| 运输中 | → | 已发货 |
| 派送中 | → | 已发货 |
| 已签收 | → | 已签收 |
| 异常 | → | 售后处理中 |
| 退货中 | → | 售后处理中 |
| 已退货 | → | 已退款·交易关闭 |

8 → 5，多对一，无歧义。

## 3. 单一事实来源

### 3.1 问题

状态常量当前散在三处，再加映射就是第四处：

- `app/schemas/admin.py:70` — `SHIPPABLE_ORDER_STATUSES`
- `app/api/admin/console.py:18` — `ORDER_STATUSES`（与 schemas 里的正则同值但独立）
- `app/schemas/admin.py:31,42` — 写死的正则 `^(处理中|已发货|已送达|已签收)$`
- `app/models/order.py:20` — 注释里写死状态集

2026-09-27 那份 spec 已经吃过这个亏（专门写过「两份同义集合必然漂移」），本次新增 2 个订单状态 + 2 个运单状态，不收敛必然漏改。

### 3.2 方案

新建 `llm_backend/app/services/order_status.py`，作为状态集与映射的唯一出处。

选 `app/services/` 的理由：该目录已是业务逻辑层（`user_service.py`、`product_dynamic_service.py`），而 `app/core/` 放的是基础设施（database / logger / security / config），`app/schemas/` 是校验层 —— 状态映射是业务规则，两处都不合适。

**依赖方向**：本模块**自身只 import 标准库**（`datetime` / `typing`），上层引用它不会成环。

> ⚠️ 不要说成「`app/services/` 不依赖上层」—— **那是假的**。`app/services/user_service.py:4` 就有 `from app.schemas.user import UserCreate`。新模块安全是因为**它自己什么都不 import**，不是因为目录级规则。照抄一条不存在的规则，下一个往 services 放映射的人会踩坑。

```python
# llm_backend/app/services/order_status.py
"""订单状态 ⇄ 运单状态的唯一映射处。

订单状态不直接编辑,而是【纯派生】自运单状态:改运单 → 订单自动跟随。
本模块是两侧状态集与映射关系的单一事实来源 —— models / schemas / api / 种子脚本
一律从这里取,不得各自再写一份(2026-09-27 的物流模块 spec 已记录过
「两份同义集合必然漂移」这个教训)。
"""

from datetime import date
from typing import Optional

# 订单状态(5 个)。
# ⚠️ 顺序即控制台环形图的图例顺序,与前端 ConsoleView.vue 的 ORDER_COLORS 按下标绑定 ——
#    调整顺序必须同步改那个数组,否则颜色与图例错位(且没有任何测试会红)。
ORDER_STATUSES = ["处理中", "已发货", "已签收", "售后处理中", "已退款·交易关闭"]

# 运单状态(8 个)。顺序即物流页状态下拉顺序。
SHIPMENT_STATUSES = ["待揽收", "已揽收", "运输中", "派送中",
                     "已签收", "异常", "退货中", "已退货"]

# 派生的唯一依据。8 → 5,多对一。
SHIPMENT_TO_ORDER = {
    "待揽收": "处理中",
    "已揽收": "已发货",
    "运输中": "已发货",
    "派送中": "已发货",
    "已签收": "已签收",
    "异常": "售后处理中",
    "退货中": "售后处理中",
    "已退货": "已退款·交易关闭",
}

# 没有运单时订单的落点(删除运单 / 建单初始值都用它)。
# 提成常量而不是散落的字面量:这个值在三个端点、种子脚本、测试辅助里都要用,
# 写错一个(比如写成「已发货」)会让"没运单却有状态"的洞重新出现。
NO_SHIPMENT_ORDER_STATUS = "处理中"

# 唯一需要 signed_date 的订单状态。写成常量避免各处散落字面量。
SIGNED_ORDER_STATUS = "已签收"


def derive_order_status(shipment_status: str) -> str:
    """运单状态 → 订单状态。

    入参必须来自 SHIPMENT_STATUSES(由接口层 schema 的正则保证)。
    用 [] 而不是 .get() —— 映射表缺少某个运单状态时应当立刻抛 KeyError,
    而不是静默返回 None 把订单状态写成空值(那会绕过 NOT NULL 变成 500)。
    """
    return SHIPMENT_TO_ORDER[shipment_status]


def derive_order_fields(
    shipment_status: Optional[str], signed_at: Optional[date]
) -> tuple[str, Optional[date]]:
    """纯函数:算出一个订单应有的 (status, signed_date)。

    ⚠️ 判断逻辑【只在这里写一次】。接口层走 ORM(见 sync_order_from_shipment),
    种子脚本走 Core UPDATE —— 两条路形态不同,但必须共用这一份判断。
    在种子脚本里另写一遍映射,就是本模块开头要防的「第四份同义集合」。

    shipment_status 为 None 表示该订单当前【没有运单】(刚被删除,或还没建):
    没有派生来源,订单回到 NO_SHIPMENT_ORDER_STATUS,签收日期清空。

    签收日期【直接跟随运单】,不各算各的 —— 两处独立计算必然生出自相矛盾的
    演示数据(库里 ORD-015 曾经就是「订单已送达、运单已签收」这类不一致)。
    运单是「已签收、日期不详」(signed_at 为 NULL,物流模块 §4.5 明说是有意的
    可达状态)时,订单也跟着是 NULL,两边保持一致。
    """
    if shipment_status is None:
        return NO_SHIPMENT_ORDER_STATUS, None
    status = derive_order_status(shipment_status)
    return status, (signed_at if status == SIGNED_ORDER_STATUS else None)


def sync_order_from_shipment(
    order, shipment_status: Optional[str], signed_at: Optional[date]
) -> None:
    """把 derive_order_fields 的结果写到 ORM Order 对象上。

    ⚠️ 只改 ORM 对象属性,【不 flush】—— 调用方负责把它并进自己那次 flush 里,
    这样同步与运单写入在同一个事务,冲突回滚时两边一起回退。

    ⚠️ 入参用【值】而不是 Shipment 对象。调用方 rollback 会让 session 里所有
    ORM 对象过期,之后读属性触发惰性刷新、异步下抛 MissingGreenlet
    (项目踩过的坑,orders.py:115 有同款注释)。传值就没有这个风险。
    """
    order.status, order.signed_date = derive_order_fields(shipment_status, signed_at)
```

## 4. 后端行为

> 🔴 **本节的三处落点是硬约束，不是"建议位置"。**
> ORM 查询会触发 autoflush（`sqlalchemy/orm/context.py:359`），把 session 里未提交的
> 变更提前刷进库。若刷的是会违反唯一键的运单改动，`IntegrityError` 就在 try 之外抛出
> → **409 变 500**。既有代码 `logistics.py:340-342` 已经记录过这个坑，本次三处新增写操作
> 都在这个坑的半径内。

### 4.1 建运单 `POST /api/admin/logistics`

**校验顺序**（沿用现有顺序，仅第 ③ 条换内容）：

1. 订单存在？ 否 → `400 "订单不存在: {order_no}"`
2. 该订单已有运单？ 是 → `409 "订单 {order_no} 已有运单，请勿重复创建"`
3. **订单状态必须是「处理中」** 否 → `400 "订单 {order_no} 当前状态为「{status}」，只有「处理中」的订单才能建运单"`

> **② 仍在 ③ 之前**：2026-09-27 spec 的记录（`test_create_duplicate_beats_processing_status` 钉住）。订单已有运单时真实原因是"重复建单"，报"状态不对"会误导管理员。
>
> **③ 为什么是「处理中」**：纯派生下「非处理中」等价于「已有运单」，所以这条是给**脏数据**兜底的 —— 万一哪条订单状态是「已发货」却没有运单，② 放行、③ 拦住，给出能指导修改的文案。（正常数据下 ② 会先命中。）

🔴 **sync 的位置：必须在 `db.add(shipment)` 之前**（既有代码 `logistics.py:337` 之后、`:339` 之前）：

```python
    shipment = Shipment(order_no=..., tracking_no=..., carrier=...,
                        status=payload.status, shipped_at=..., signed_at=signed_at, trace=trace)

    # ⚠️ 必须在 db.add 之前 —— sync 会发出一条 orders 的 UPDATE。
    #    若放在下面那个 db.flush() 之后,订单 UPDATE 就脱出 try,挂在后续重取
    #    查询(`:349`)的 autoflush 上,失败时直接在 try 外抛 -> 500。
    sync_order_from_shipment(order, shipment.status, shipment.signed_at)

    try:
        db.add(shipment)
        await db.flush()
    except IntegrityError as e:
        await db.rollback()
        raise _conflict_409(e, payload.order_no, payload.tracking_no)
```

> ⚠️ **不要写"待揽收 → 处理中是恒等映射，所以此处订单状态不变"。那是错的。**
> `ShipmentCreate.status`（`schemas/admin.py:85`）接受全部 8 个值，前端建单弹窗
> （`LogisticsView.vue:174`）的下拉也是 8 个值任选。管理员建单时直接选「已签收」，
> 订单会被**真的推到「已签收」**并发出真实 UPDATE。只有不传 status（默认「待揽收」）时
> 才是恒等映射 —— 而且此时 SQLAlchemy 因无净变化不会发 UPDATE，但这属于实现细节，
> **不能当作"这次写不会失败"的依据**（决策 D12 明确保留建单选终态的能力）。

### 4.2 编辑运单 `PUT /api/admin/logistics/{id}`

🔴 **新增的 Order 查询必须在 setattr 循环之前**（既有代码 `logistics.py:417-418`）：

```python
    # 提前取好 order_no(既有的 rollback 安全做法,logistics.py:414)
    order_no = shipment.order_no
    tracking_no = data.get("tracking_no", shipment.tracking_no)

    # ⚠️ Order 查询必须在 setattr 之前。放在 setattr 之后会触发 autoflush,
    #    把未提交的运单改动(可能撞 tracking_no 唯一键)刷进库,
    #    IntegrityError 从这次 SELECT 抛出 -> 在下面 try 之外 -> 500 而不是 409。
    order = (await db.execute(
        select(Order).where(Order.order_no == order_no)
    )).scalar_one_or_none()
    if order is None:
        # FK 保证订单必在(order_no 指向 orders.order_no);走到这里说明数据被外力破坏,
        # 给可读的 400 而不是 NoResultFound -> 500
        raise HTTPException(status_code=400, detail=f"订单不存在: {order_no}")

    for field, value in data.items():
        setattr(shipment, field, value)

    # 同步必须在 setattr 之后取运单的 effective 值(此时 shipment.status 已是新值)
    sync_order_from_shipment(order, shipment.status, shipment.signed_at)

    try:
        await db.flush()
    except IntegrityError as e:
        await db.rollback()
        raise _conflict_409(e, order_no, tracking_no)
```

🔴 **concurrency 硬约束**：`except` 分支内**只允许读 try 之前取好的局部变量**。
`order` 与 `shipment` 在 `await db.rollback()` 之后一律视为不可读 —— rollback 会无条件
过期 identity map 里的全部对象（`sqlalchemy/orm/session.py:1126-1128`，
`expire_on_commit=False` 对 rollback 无效），再读属性会触发惰性刷新、异步下抛
`MissingGreenlet`。当前形状恰好安全（except 只碰 `order_no`/`tracking_no`/`e.orig.diag`），
但这是**位置带来的巧合，不是不变量** —— 一旦有人在 409 文案里带上订单状态就会踩雷。

**签收日期的联动**：运单状态改成「已签收」时，`shipment.signed_at` 由规则 A 算出
（传入 → 原值 → 补当天），订单的 `signed_date` 直接取这个值，不再走 `orders.py` 那套
"传入→原值→今天"。改回非「已签收」时运单 `signed_at` 被规则 A 置 NULL，订单 `signed_date`
同步置 NULL。

### 4.3 删运单 `DELETE /api/admin/logistics/{id}`

```python
    order = (await db.execute(
        select(Order).where(Order.order_no == shipment.order_no)
    )).scalar_one_or_none()
    if order is None:
        raise HTTPException(status_code=400, detail=f"订单不存在: {shipment.order_no}")

    await db.delete(shipment)
    sync_order_from_shipment(order, None, None)   # 订单回「处理中」,签收日期清空(D8)

    try:
        await db.flush()
    except StaleDataError:
        raise HTTPException(status_code=404, detail=f"运单不存在: {shipment_id}")
```

订单回「处理中」，签收日期清空（决策 D8）。删掉后该订单在物流页回到「未录入」行，
可以重新补录 —— 这让演示流程可循环。

> 🔴 **本端点必须加 `await db.flush()`，这一点与 2026-09-27 spec 的结论相反。**
>
> 原结论（"不显式 flush 是安全的"）建立在「失败会 500」这个前提上 —— **前提不成立**。
> `get_db` 的 commit 跑在响应**发出之后**（`fastapi/routing.py:140-151`：`response(scope,
> receive, send)` 先执行，`request_stack` 退出时才 commit），而 starlette 的兜底
> `if not response_started`（`middleware/errors.py:180-181`）不会再补一个 500。
> 于是隐式 commit 失败时，客户端拿到 **200 `{"id": N, "deleted": true}`，库里一行没动** ——
> 正是本项目在 `logistics.py:379-380` 明令禁止的「保存了但没生效」。
>

```python
conds = [or_(
```

```python
def test_derive_order_status_truth_table(shipment_status, expected):
    assert derive_order_status(shipment_status) == expected


def test_every_shipment_status_has_mapping():
    """加了运单状态却忘了补映射 → 这里红。"""
    assert set(SHIPMENT_TO_ORDER) == set(SHIPMENT_STATUSES)


def test_every_order_status_is_reachable():
    """纯派生下,没有运单状态能触发的订单状态就是死值 —— 不许存在。"""
    reachable = set(SHIPMENT_TO_ORDER.values()) | {NO_SHIPMENT_ORDER_STATUS}
    assert reachable == set(ORDER_STATUSES)


def test_signed_date_only_for_signed_status():
    """signed_at 只在订单落到「已签收」时透传,其余一律 None。"""
    d = date(2026, 9, 20)
    assert derive_order_fields("已签收", d) == ("已签收", d)
    assert derive_order_fields("运输中", d) == ("已发货", None)
    assert derive_order_fields(None, d) == ("处理中", None)
```

## 8. 并发与失败面

> v1 完全没提这一节。以下均为审计实测结论。

| 场景 | 后果 | 处理 |
|---|---|---|
| **PUT 对 PUT**（两人同时改同一订单的运单） | SQLAlchemy 的 UOW 按 FK 依赖排序（`Order` mapper 先于 `Shipment`），两个事务加锁顺序一致 → **不死锁**，最终两行自洽 | ✅ 可接受，无需行锁 |
| **删除端点隐式 commit 失败** | 客户端拿到 **200 + 库里没动**（不是 500） | §4.3 加 `await db.flush()` |
| **删除端点并发**（A 删订单 → CASCADE 删运单；B 在此之前载入该运单再调删除） | `UPDATE orders` 匹配 0 行 → `StaleDataError`，**接不住 `IntegrityError`** → 同样是 200 + 没删 | §4.3 显式捕获 `StaleDataError` → 404 |
| **PUT 对 DELETE**（B 的 flush 先 UPDATE orders 成功、再 UPDATE shipments 匹配 0 行） | `StaleDataError` → 不被 `except IntegrityError` 接住 → 500 | 建议把 `update_shipment` 的捕获面扩成 `except (IntegrityError, StaleDataError)`；`StaleDataError` 走 404「运单已被删除，请刷新」 |
| 行级锁（`with_for_update`） | 三个端点都没有 | ❌ **不引入**。上述两类问题用异常处理收敛即可；加锁会引入死锁面与等待超时，收益不成比例 |
