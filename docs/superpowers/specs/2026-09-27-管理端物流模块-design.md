## 1. 背景与目标

管理端目前有 5 个模块（控制台 / 商品 / 订单 / 知识库 / 工单），订单能改状态但**看不到物流**。本模块补上物流的录入与查看：管理员手工维护运单和轨迹，并在一个页面上看到「已发货订单现在到哪了」。

**成功标准**（可验收）：

1. 管理端出现第 6 个导航项「物流管理」，页面能分页列出运单
2. 能新增/编辑/删除运单，编辑时能增删轨迹节点
3. 只能给「已发货」及之后状态的订单开运单，给「处理中」的订单开会被拒绝并给出可读提示
4. 删订单时它的运单和轨迹一并消失，不留孤儿
5. `shipments.order_no` 上有可用索引（按订单号查物流不走全表扫）

## 3. 数据模型

### 3.1 关键前提：`orders` 表完全不动（已实测）

`orders.order_no` 已经满足外键目标的两个条件，**不需要加索引、不需要迁移**：

实测证据（连真实库 `smartcs_agent` 查询 `pg_constraint`）：

```
orders_order_no_key  | u | UNIQUE (order_no)
orders_pkey          | p | PRIMARY KEY (id)
orders_user_id_fkey  | f | FOREIGN KEY (user_id) REFERENCES users(id) ON DELETE SET NULL
```

`contype = 'u'` 说明它是 **UNIQUE 约束**（不只是唯一索引）—— PostgreSQL 的外键只能指向唯一约束或主键，所以这一列可以直接当外键目标。

实测验证（建带 FK 的临时探针表，成功后退掉）：

```sql
CREATE TABLE _fk_probe (
    id serial PRIMARY KEY,
    order_no varchar(32) REFERENCES orders(order_no) ON DELETE CASCADE
);
-- 结果：创建成功 → orders.order_no 可直接作为外键目标
```

> ⚠️ 用户原始需求里的「给订单表的 order_no 建索引」**已经存在**，重复建是多余的。真正缺索引的是**运单表引用侧的那一列**（见 §3.3）—— PostgreSQL 的外键**不会**自动给引用侧建索引。

### 3.2 `shipments` 运单表

新建 `llm_backend/app/models/shipment.py`：

```python
from sqlalchemy import Column, Date, DateTime, ForeignKey, Integer, String, func
from sqlalchemy.orm import relationship

from app.core.database import Base


class Shipment(Base):
    """运单表:一单可多运单(拆包裹),数据由管理端手工录入或 seed_shipments.py 生成"""

    __tablename__ = "shipments"

    id = Column(Integer, primary_key=True, index=True)
    tracking_no = Column(String(50), nullable=False, unique=True)  # 运单号,来自承运商,手工录入
    # 关联订单用业务单号而非 order_id:orders.order_no 已是 UNIQUE 约束,可直接当外键目标(§3.1 实测)
    # index=True 必须有 —— PostgreSQL 不给外键的引用侧自动建索引,漏了按订单号查物流就全表扫
    order_no = Column(
        String(32),
        ForeignKey("orders.order_no", ondelete="CASCADE"),
        nullable=False,
        index=True,
    )
    carrier = Column(String(50), nullable=False)                  # 8 选 1,见 §3.4
    status = Column(String(20), nullable=False, default="待揽收")   # 6 选 1,见 §3.4
    shipped_at = Column(Date, nullable=True)                      # 发货时间
    # 签收时间:仅 status='已签收' 时有值;其余状态由接口强制置 NULL(与 orders.signed_date 同款规则)
    signed_at = Column(Date, nullable=True)
    created_at = Column(DateTime, server_default=func.now())
    updated_at = Column(DateTime, server_default=func.now(), onupdate=func.now())

    # ORM 级联:走 db.delete(shipment) 时由 ORM 删轨迹
    # DB 级 ON DELETE CASCADE:走原生 SQL 或删订单时由数据库删(Order 模型没有反向 relationship,
    # 删订单时 ORM 不知道运单存在,只能靠 DB 级联 —— 这条不能省)
    tracks = relationship(
        "ShipmentTrack",
        back_populates="shipment",
        cascade="all, delete-orphan",
        order_by="ShipmentTrack.tracked_at",
    )
```

### 3.3 `shipment_tracks` 轨迹表

```python
class ShipmentTrack(Base):
    """运单轨迹节点:一条运单 N 个节点,按 tracked_at 升序"""

    __tablename__ = "shipment_tracks"

    id = Column(Integer, primary_key=True, index=True)
    # index=True 必须有:按运单查轨迹是列表页最热的查询路径
    shipment_id = Column(
        Integer,
        ForeignKey("shipments.id", ondelete="CASCADE"),
        nullable=False,
        index=True,
    )
    # DateTime 而非 Date:同一天的多个节点(上午揽收/晚上发车)必须能分出先后,见 §9 取舍①
    tracked_at = Column(DateTime, nullable=False)
    location = Column(String(100), nullable=True)        # 所在城市/网点,可空
    description = Column(String(255), nullable=False)    # 节点描述,如"已揽收"
    created_at = Column(DateTime, server_default=func.now())

    shipment = relationship("Shipment", back_populates="tracks")
```

**实现要点**：

```python
stmt = (
    select(Shipment, Order)
    .join(Order, Order.order_no == Shipment.order_no)   # 内连接安全:FK 保证订单必存在
    .options(selectinload(Shipment.tracks))
    .where(*conds)
    .order_by(Shipment.shipped_at.desc().nullslast(), Shipment.id.desc())
)
```

- **内连接安全**：`shipments.order_no` 是外键，不可能指向不存在的订单
- **`selectinload` 是本仓库首次使用**：`Conversation.messages` 虽有 relationship 但从未在异步路径里读过。异步 SQLAlchemy 下**惰性加载会直接抛 `MissingGreenlet`**，必须在查询里显式 eager load
- **排序**：`shipped_at` 降序、`nullslast()` 把「待揽收还没发货」的排最后；同日期用 `id` 兜底保证稳定分页
- ⚠️ **`total` 的 count 必须带同一个 join**。只写 `select_from(Shipment)` 会静默算错：

  ```python
  # ❌ where 里含 Order.product_name / Order.status 时不带 join:
  #    SQLAlchemy 把 orders 补进 FROM 形成笛卡尔积 —— 不报错,只发一条 SAWarning
  #    实测:1 条运单 + 18 条订单 → total = 18(而不是 1)
  # ✅ 正确写法
  total = (await db.execute(
      select(func.count()).select_from(Shipment)
      .join(Order, Order.order_no == Shipment.order_no)
      .where(*conds)
  )).scalar_one()
  ```

  同时也不能取 `len(items)`（分页下 total 恒等于 page_size，且不报错 —— `orders.py:76-77` 记着那个坑）。**两个坑都要防**

**序列化约定**（对齐 `orders.py:23-42` 的 `_serialize`）：

- `Numeric` → `float`（本模块没有 Numeric 字段，留作对照）
- `Date` → `isoformat()`，即 `"YYYY-MM-DD"`
- `DateTime` → **`isoformat(timespec="minutes")`**，即 `"2026-09-20T14:32"`
  - ⚠️ 这个 `timespec` 参数**不能省**。实测（Chromium 154，读 `<input type="datetime-local">` 的 `value`）：`2026-09-20T14:32:00` 会被浏览器自动规范化成 `14:32`、`14:32:30` 原样保留，**但带微秒（`…14:32:00.123456`）或带时区偏移的串会被直接置空** → 前端回填变空白。而 `isoformat()` 的默认输出**恰好带微秒**，所以省掉这个参数就会踩坑
  - 注意「带秒会变空」是**错的**说法（实测会被规范化），别拿这条去验证并顺手删掉 `timespec`
- `signed_at` 非「已签收」恒为 `null`（前端据此不显示）
- **列表项直接内嵌 `tracks`**，不额外开详情端点：数据量小（一页 12 个运单 × 几个节点），前端编辑弹窗拿到行数据就能直接用

### 4.3 `GET /api/admin/logistics/shippable-orders` — 订单下拉

```python
@router.get("/shippable-orders")
async def list_shippable_orders(db: AsyncSession = Depends(get_db)):
    """给「新增运单」的订单下拉用:只返回状态为已发货/已送达/已签收的订单。"""
    rows = (await db.execute(
        select(Order.order_no, Order.product_name, Order.buyer_name, Order.status)
        .where(Order.status.in_(SHIPPABLE_ORDER_STATUSES))
        .order_by(Order.order_no)
    )).all()
    return {"items": [{"order_no": r[0], "product_name": r[1],
                       "buyer_name": r[2], "status": r[3]} for r in rows]}
```

**为什么单开一个端点而不是复用 `GET /api/admin/orders`**：现有订单列表的 `status` 参数只收单个值，要拿三个状态得调三次；给 `orders.py` 加多值支持会动到订单模块（本模块明确不碰）。规则（哪些订单能开运单）属于物流模块，端点也放在物流模块里，归属干净。

**已经建过运单的订单仍然出现在下拉里** —— 一单可多运单（拆包裹），不做排除。

**不分页**：当前订单量级 18 条。订单量上到几千时需要改成分页或远程搜索，列入 §9 取舍③。

### 4.4 `POST /api/admin/logistics` — 新增运单

**请求体**：

```json
{
  "order_no": "ORD-005",
  "tracking_no": "JDV0000000005",
  "carrier": "京东物流",
  "status": "待揽收",
  "shipped_at": "2026-09-20",
  "signed_at": null,
  "tracks": [
    {"tracked_at": "2026-09-20T14:32", "location": "广州市", "description": "已揽收"}
  ]
}
```

**处理步骤**：

1. 查订单：`select(Order).where(Order.order_no == payload.order_no)`
   - 不存在 → `400 "订单不存在: {order_no}"`
2. 校验订单状态 ∈ `SHIPPABLE_ORDER_STATUSES`
   - 不满足 → `400 f"订单 {order_no} 当前状态为「{status}」，只有已发货及之后的订单才能建运单"`
3. 处理 `signed_at` 与 `status` 的绑定（§4.6 规则）
4. 校验 `shipped_at` / `signed_at` 的先后（§4.6 规则）
5. 插运单 + 插轨迹（轨迹按 `tracked_at` 升序写入）
6. 捕获 `IntegrityError` → `409 f"运单号已存在: {tracking_no}"`（并发下先查后插仍可能撞，必须有这层兜底；`orders.py:126-148` 是同款写法）

**响应**：与列表项同结构的完整对象（含 `tracks`、含 `order_status`/`product_name`/`buyer_name` 这些 join 出来的字段）。HTTP 200，与现有端点一致（项目不用 201）。

> ⚠️ **不要照抄 `products.py:105-106` 的 `await db.flush(); await db.refresh(row)` 再读 `tracks`** —— 实测这条路径会炸：
>
> ```
> POST: add + flush + refresh + 读 .tracks
>   → MissingGreenlet: greenlet_spawn has not been called; can't call await_only() here
> ```
>
> `refresh()` 会把 `tracks` 重置为未加载，接着读属性触发惰性加载，异步下必抛。`products.py` 是这个仓库里「create 端返回完整对象」的唯一先例，照抄就中。其余三种写法（flush 不 refresh / commit 后再读 / selectinload 加载）实测都能跑。
>
> **正确做法**：写入后用一次查询重取，顺带把 join 出来的订单字段一并拿到：
>
> ```python
> row = (await db.execute(
>     select(Shipment, Order)
>     .join(Order, Order.order_no == Shipment.order_no)
>     .options(selectinload(Shipment.tracks))
>     .where(Shipment.id == shipment.id)
> )).one()
> return _serialize(*row)
> ```
>
> **POST 和 PUT 都走这条**，不要直接在 ORM 对象上序列化。

### 4.5 `PUT /api/admin/logistics/{shipment_id}` — 编辑

**可改字段**：`tracking_no` / `carrier` / `status` / `shipped_at` / `signed_at` / `tracks`

**不可改**：`order_no`（schema 里根本没有这个字段，与订单页「编辑不给换商品」同理）

**处理要点**：

- 运单不存在 → `404 f"运单不存在: {shipment_id}"`
- `data = payload.model_dump(exclude_unset=True)` 区分「没传」与「传了 null」
- `tracks` 单独处理，**有三种输入形态**，漏掉第三种会 500：

  | 输入 | `exclude_unset` 结果 | 应有行为 |
  |---|---|---|
  | 字段没传 | `"tracks" not in data` | 轨迹**原样不动** |
  | 传了 `[]` | `data["tracks"] == []` | **清空**轨迹 |
  | 传了 `null` | `data["tracks"] is None` | **清空**轨迹（与 `[]` 同义） |

  ```python
  # ✅ 正确处理三种形态
  if "tracks" in data:
      await db.execute(delete(ShipmentTrack).where(ShipmentTrack.shipment_id == shipment.id))
      for t in (data["tracks"] or []):      # ← `or []` 兜住 None,少了它 NoneType 不可迭代 → 500
          db.add(ShipmentTrack(shipment_id=shipment.id, **t.model_dump()))
  ```

  > ⚠️ `null` 真会到后端：前端 `cleanBody` **保留 `null`**（只滤 `''` 和 `undefined`，`api.js:12-16`）。
  > ⚠️ 但**不能**写成 `if data.get("tracks"):` —— 那样空数组是假值，会被当成"没传"，轨迹永远清不掉（这正是 §4.8 里强调前端必须把 `tracks: []` 原样送出的原因，两边要配套）
- `signed_at` 用 `effective_status = data.get("status", shipment.status)` 走 §4.6 规则
- **不重复校验订单状态**：用户已确认「订单状态回退成处理中时，已有运单会变成孤儿，不报错」。理由见 §9 取舍②
- `tracking_no` 撞别人的号 → `409`

### 4.6 跨端点的两条校验规则

**规则 A：`signed_at` 与 `status` 强绑定**（与 `orders.signed_date` 完全同款，`orders.py:179-183` 是原型）

| `status` | `signed_at` 取值 |
|---|---|
| 非 `已签收` | **一律置 `NULL`**（状态改回其它即为清空） |
| `已签收` | 显式传了用传的 → 没传沿用原值 → 原值也没有则补当天（UTC，`datetime.now(timezone.utc).date()`） |

> 服务端兜底，直调接口也造不出「未签收却带签收时间」的数据。

**规则 B：时间先后**（手工录入的数据质量护栏）

若 `shipped_at` 与 `signed_at` **都有值**且 `signed_at < shipped_at` → `400 "签收时间不能早于发货时间"`。

> 手工录入是唯一数据来源，这条一行代码就能挡掉一类明显错数据。允许 `shipped_at` 为空（待揽收的运单还没发货）。

**⚠️ PUT 里两条规则都必须用「有效值」**，不能直接读 `data` —— 管理员最常见的操作是「只把状态改成已签收」，此时 `shipped_at` 根本没传：

```python
# ✅ PUT 里统一取 effective 值(没传就沿用库里的)
effective_status = data.get("status", shipment.status)
effective_shipped = data.get("shipped_at", shipment.shipped_at)
effective_signed = data.get("signed_at", shipment.signed_at)
# 规则 A 用 effective_status;规则 B 用 effective_shipped / effective_signed
```

照 `orders.py:179-183` 的 `effective_status` 写法。漏了 `shipped_at` 的 effective 取值，规则 B 在「只改状态」这条路径上形同失效。

### 4.8 前端空串约定（既有坑，新接口必须遵守）

`<input type="date">` / `<input type="datetime-local">` 留空时给的是 `''`，`JSON.stringify` 后是 `""`，pydantic 对 `Optional[date]` / `Optional[datetime]` 收到 `""` 一律 422（实测确认）。

**两端都要处理**：

- 前端：所有 body 走 `cleanBody()`（`api.js:12-16` 已有）把空串摘掉
- 后端：`Optional[date]` / `Optional[datetime]` 不额外加 validator（现有端点也没加，保持一致）

**⚠️「清空一个字段」必须显式送 `null`，不能送 `''`：**

`cleanBody` 会把 `''` 整个键**删掉**，而 PUT 端点的 `exclude_unset` 把它判定为「没传」= **保留旧值**。所以 `shipped_at` 一旦填过，用 `''` 是永远清不掉的。

```js
// ❌ 清不掉:'' 被 cleanBody 摘掉 → 后端认为"没传" → 保留旧值
shipped_at: form.shipped_at,
// ✅ 正确:cleanBody 保留 null(实测 cleanBody({shipped_at:null}) === {shipped_at:null})
shipped_at: form.shipped_at || null,
```

订单页正是靠这一点清空 `signed_date` 的（`OrderView.vue:411-413`），照抄。

**⚠️ `tracks` 空数组必须原样保留：**

`[]` 能通过 `cleanBody`（只滤 `''`/`undefined`），语义是「清空轨迹」，与 §4.5 的 `exclude_unset` 约定一致。**不要**写成 `tracks: tracks.length ? tracks : ''` —— 那会把「清空轨迹」变成「不动轨迹」，管理员永远删不掉轨迹。

**`tracks` 数组里的元素不走 `cleanBody`**（它是嵌套结构，`cleanBody` 只遍历顶层，实测确认），所以轨迹行的 `tracked_at` 为空串时会直达 pydantic → 422 → 而 `api.js:42` 把 `detail`（**数组**）塞进 `new Error()`，界面显示 `[object Object]`（实测）。因此轨迹行的必填校验**必须在前端预校验里兜住**，这是唯一防线。

## 6. 种子数据

新建 `llm_backend/scripts/seed_shipments.py`，照 `seed_orders.py` 的写法（`pg_insert` + `on_conflict_do_update` 幂等 upsert）。

**覆盖范围**：库里所有 `status ∈ {已发货, 已送达, 已签收}` 的订单（当前 6 + 4 + 3 = 13 条）。

**字段生成规则**：

| 字段 | 规则 |
|---|---|
| `tracking_no` | `JDV{order_no 的数字部分:010d}`，如 `ORD-003` → `JDV0000000003`。确定性生成，作为幂等键 |
| `carrier` | 京东物流为主（京东自营），按 index 轮转掺入顺丰/中通 |
| `status` | 按订单状态推导：已发货→`运输中`；已送达→`派送中`；已签收→`已签收` |
| `shipped_at` | `order_date + 1 天`，用 `min(..., today)` 兜住未来日期 |
| `signed_at` | 仅`已签收`时有值：**`order_date + 2 天`**，同样 `min(..., today)` |

> ⚠️ `signed_at` 必须跟 `seed_orders.py:73` 的订单签收日**取同一个偏移（+2 天）**。写成 +3 天会让同一条已签收订单出现「订单签收日 9-22、运单签收日 9-23」的自相矛盾演示数据。

**轨迹生成**：按运单状态生成递进的节点链

| 运单状态 | 轨迹节点 |
|---|---|
| 待揽收 | （无） |
| 运输中 | 已揽收 → 到达转运中心 → 运输中 |
| 派送中 | 已揽收 → 到达转运中心 → 运输中 → 派送中 |
| 已签收 | 已揽收 → 到达转运中心 → 运输中 → 派送中 → 已签收 |

节点时间从 `shipped_at` 起按小时递进（如 `+0h / +18h / +30h / +42h`），保证时间轴上顺序正确。

> ⚠️ **不能直接对 `shipped_at` 加 `timedelta(hours=N)`** —— `shipped_at` 是 `Date` 列，`date + timedelta(hours=N)` 返回的**还是 `date`，小时部分被直接截断**。实测：
>
> ```
> date(2026,9,20) + timedelta(hours=0)  = date(2026, 9, 20)
> date(2026,9,20) + timedelta(hours=18) = date(2026, 9, 20)   ← 和 +0h 撞了
> date(2026,9,20) + timedelta(hours=30) = date(2026, 9, 21)
> date(2026,9,20) + timedelta(hours=42) = date(2026, 9, 21)   ← 和 +30h 撞了
> ```
>
> 4 个偏移只会塌成 2 个不同值 → 轨迹时间并列 → 时间轴顺序错乱，且 §7 用例 10（tracks 升序）会因同值并列而变得不稳定。
>
> **正确做法**：先把 `Date` 升成 `datetime` 再加偏移：
>
> ```python
> from datetime import datetime, time, timedelta
> base = datetime.combine(shipped_at, time(hour=9))   # 9 点起揽收,比 0 点自然
> tracked_at = base + timedelta(hours=offset)
> ```

**多运单演示**：挑 **2 个**订单各造 2 个运单（第二个用 `JDX` 前缀区分、承运商换顺丰），用来验证「一单可多运单」在页面和详情弹窗里的表现。

**幂等策略**（与 `seed_orders.py` 同款「upsert 覆盖」而非「存在则跳过」）：

- 运单：`on_conflict_do_update(index_elements=[Shipment.tracking_no])`，覆盖 `status` / `shipped_at` / `signed_at`
- 轨迹：**先按 `shipment_id` 删光再插**。简单且可重复执行

> ⚠️ 代价要写明：重跑会**删掉手工加到这些种子运单上的轨迹**。这与 `seed_orders.py` 的「upsert 让重跑同时起到刷新演示数据的作用」是同一个取舍。手工录入的运单如果用 `JDV`/`JDX` 以外的运单号，不受影响。

## 9. 已知取舍与风险

**① 轨迹时间用 `DateTime`（本地墙上时间），与订单的 UTC 日期约定不一致**

订单侧全链路用 UTC 日期（`orders.py:119-120` 有明确注释）。轨迹时间改成本地时间，理由是：轨迹时间是**给人看的承运商报告时间**，不参与任何跨表计算或统计，用本地时间更贴合直觉（管理员录入「2026-09-20 14:32」时心里想的就是本地时间）。

代价：如果将来要把轨迹时间用于统计（如「平均运输时长」），需要先统一时区基准。

**② 订单状态回退后，已有运单成为「孤儿」**

用户明确选择「只在开运单时校验订单状态」。因此：订单建好运单后被改回`处理中`，运单仍然存在且可正常编辑，接口不报错。

理由：订单状态现在是任意跳转、无状态机约束的（`docs/diagrams/spec/60-order-lifecycle.json` 已记录这一点）。如果编辑运单时也校验，管理员会被「先改订单状态才能改运单」卡住，规则更绕。**这是有意的设计，不是遗漏。**

**③ `shippable-orders` 不分页**

当前订单量级 18 条，一次性返回无压力。订单量上到几千条时需要改成分页或远程搜索下拉，届时改这一个端点即可。

**④ 种子脚本重跑会删掉手工加到种子运单上的轨迹**

见 §6 幂等策略。手工录入的运单（运单号不是 `JDV`/`JDX` 前缀）不受影响。

**⑤ `selectinload` 是本仓库首次使用**

本项目已有 `relationship`（Conversation/Message/User），但从未在异步查询里读过关联对象。异步 SQLAlchemy 下**惰性加载会抛 `MissingGreenlet`**，所以列表查询必须显式 `.options(selectinload(Shipment.tracks))`。这是新代码里最容易漏、且漏了会在运行时报错而非启动时报错的一处。

**⑥ 编辑运单时轨迹「整体替换」，不做增量 diff**

轨迹提交后旧的全删、新的全插，轨迹行的 `id` 每次编辑都会变。对本场景（管理员手工维护几条节点）没有影响，但如果有外部系统引用轨迹 `id`，需要改成增量更新。

**⑦ 既有 bug：`OrderView.vue:339-342` 的签收日期 watcher 会在回填时覆盖库值**

**这是既有代码的 bug，不在本模块范围内，本次不修** —— 但本模块的签收时间联动**不能照抄它**（§5.2 已给出修正写法）。

- **成因**：`watch(() => form.status)` 无法区分「用户手动切换」与「`openEdit` 回填」，回填也会触发它。而 `prev` 拿到的是**上一次表单**的状态，不是这条记录的旧状态
- **触发条件**：上一次表单的 `status` 不是`已签收`（例如刚点过「新增」、或刚编辑过一条其它状态的记录），此时再编辑任意一条已签收记录 → 签收日期被改成今天
- **后果**：管理端界面上看不出异常（显示的就是"今天"），一保存就把错误的签收日期写进库；后端规则是「显式传了用传的」，会照单全收
- **实测复现**（`frontend/node_modules` 的 vue 包，逐字照抄那 4 行 watcher）：

  ```
  场景A 上次停在「处理中」→ 回填 signed_date 应为 2026-09-01,实际得到 2026-09-27  ★
  场景B 上次停在「已签收」→ 回填 signed_date = 2026-09-02                      正常
  ```

- **建议**：作为独立 bug 单处理（改动落在 `OrderView.vue`）。本模块的 `LogisticsView.vue` 从一开始就用 §5.2 的 `filling` 标记写法，不引入同样的坑

**⑧ `IntegrityError → 409` 会把外键违规也误标成「运单号已存在」**

实测：插一个不存在的 `order_no` 抛的是 `IntegrityError(ForeignKeyViolation)`，与撞号是**同一个异常类**。因为 §4.4 步骤 1 已经先查过订单，实际风险很低（只有「查完之后订单被并发删掉」这个极窄窗口）。

**处理**：`except IntegrityError` 里按约束名分流，或至少把 409 的文案写成中性一点（如「运单号冲突或订单已失效」）。本次按「低风险 + 简单优先」处理：保留现方案，仅在此记录。

**⑨ `min_length=1` 挡不住纯空格**

实测 `tracking_no = " "`、`order_no = " "` 都能通过 pydantic 校验 —— `min_length` 数的是字符数，空格算字符。

**处理**：不需要额外 strip（前端 `form.tracking_no.trim()` 已经预校验；纯空格是管理员手滑，不是攻击面）。若实现时顺手加了 strip，注意 `ShipmentCreate.order_no` **不要** strip —— 订单号来自下拉，加了也无害但不是必需
