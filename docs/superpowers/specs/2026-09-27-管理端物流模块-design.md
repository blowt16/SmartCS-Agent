## 1. 背景与目标

管理端目前有 5 个模块（控制台 / 商品 / 订单 / 知识库 / 工单），订单能改状态但**看不到物流**。本模块补上物流的录入与查看。

**页面视角是「订单」而不是「运单」**（v3 的关键决策）：管理员进这个页面想知道的是「哪些已发货的订单现在什么物流情况、哪些还没录」，所以列表列出**所有已发货及之后的订单**，已录物流的显示运单和状态，未录的显示「未录入」并给一个「补录」按钮。

**成功标准**（可验收）：

1. 管理端出现第 6 个导航项「物流管理」，页面分页列出所有已发货及之后的订单
2. 已录物流的行显示运单号/承运商/物流状态；未录的行显示「未录入」+「补录」按钮
3. 点「补录」能建运单并填轨迹；**轨迹按 `YYYY-MM-DD HH:MM | 地点 | 描述` 逐行录入，格式不对会被拦下并指明第几行**；之后该行变成已录状态
4. 只能给「已发货」及之后状态、**且还没建过运单**的订单建运单，否则拒绝并给出可读提示
5. 删订单时它的运单一并消失，不留孤儿
6. **订单建过运单后被改回「处理中」，该行仍然出现在列表里**（不隐身）
7. `shipments.order_no` 上有唯一索引（按订单号查物流不走全表扫）

## 3. 数据模型

### 3.1 关键前提：`orders` 表完全不动（已实测）

`orders.order_no` 已经满足外键目标的两个条件，**不需要加索引、不需要迁移**：

实测证据（连真实库 `smartcs_agent` 查询 `pg_constraint`）：

```
orders_order_no_key  | u | UNIQUE (order_no)
orders_pkey          | p | PRIMARY KEY (id)
orders_user_id_fkey  | f | FOREIGN KEY (user_id) REFERENCES users(id) ON DELETE SET NULL
```

`contype = 'u'` 说明它是 **UNIQUE 约束**（不只是唯一索引）—— PostgreSQL 的外键只能指向唯一约束或主键，所以这一列可以直接当外键目标。

实测验证（建带 FK 的临时探针表，成功后退掉）：

```sql
CREATE TABLE _fk_probe (
    id serial PRIMARY KEY,
    order_no varchar(32) REFERENCES orders(order_no) ON DELETE CASCADE
);
-- 结果：创建成功 → orders.order_no 可直接作为外键目标
```

> ⚠️ 用户原始需求里的「给订单表的 order_no 建索引」**已经存在**，重复建是多余的。真正缺索引的是**运单表引用侧的那一列**（见 §3.2）—— PostgreSQL 的外键**不会**自动给引用侧建索引。

### 3.2 `shipments` 运单表（唯一一张新表）

新建 `llm_backend/app/models/shipment.py`：

```python
from sqlalchemy import Column, Date, DateTime, ForeignKey, Integer, String, Text, func

from app.core.database import Base


class Shipment(Base):
    """运单表:一个订单一个运单(1:1),轨迹以文本存本表。数据由管理端手工录入或 seed_shipments.py 生成"""

    __tablename__ = "shipments"

    id = Column(Integer, primary_key=True, index=True)
    tracking_no = Column(String(50), nullable=False, unique=True)  # 运单号,来自承运商,手工录入
    # 关联订单用业务单号而非 order_id:orders.order_no 已是 UNIQUE 约束,可直接当外键目标(§3.1 实测)
    # unique=True 不能省 —— 这是"一单一个运单"的强制点,且它自带唯一索引(正是本项目要的那个索引:
    # PostgreSQL 不给外键的引用侧自动建索引,漏了按订单号查物流就全表扫)
    order_no = Column(
        String(32),
        ForeignKey("orders.order_no", ondelete="CASCADE"),
        nullable=False,
        unique=True,
    )
    carrier = Column(String(50), nullable=False)                  # 8 选 1,见 §3.3
    status = Column(String(20), nullable=False, default="待揽收")   # 6 选 1,见 §3.3
    shipped_at = Column(Date, nullable=True)                      # 发货时间
    # 签收时间:仅 status='已签收' 时有值;其余状态由接口强制置 NULL(与 orders.signed_date 同款规则)
    signed_at = Column(Date, nullable=True)
    # 轨迹:一行一个节点,格式强制为「YYYY-MM-DD HH:MM | 地点 | 描述」(§4.5 规则 C)。
    # 入库前由接口校验并规范化(去空行 / 统一 LF / 统一分隔符两侧空格),本列不做约束;
    # 前端按行拆开渲染(§5.4)
    trace = Column(Text, nullable=True)
    created_at = Column(DateTime, server_default=func.now())
    updated_at = Column(DateTime, server_default=func.now(), onupdate=func.now())
```

> **删订单的级联靠 DB 层**：`Order` 模型**没有**反向 relationship（本模块不碰 `orders.py`），所以 `await db.delete(order)` 时 ORM 不知道运单存在，只能由 `ON DELETE CASCADE` 兜住。这一层不能省。

### 3.3 取值集合（封闭枚举）

**运单状态 `shipments.status`（6 值）**：

| 值 | 徽章颜色 | 说明 |
|---|---|---|
| `待揽收` | gray | 建单默认值 |
| `已揽收` | blue | |
| `运输中` | green | |
| `派送中` | amber | |
| `已签收` | teal | 唯一允许有 `signed_at` 的状态 |
| `异常` | red | 拒收/丢件/退回等 |

**承运商 `shipments.carrier`（8 值，固定下拉）**：

`京东物流` / `顺丰速运` / `中通快递` / `圆通速递` / `申通快递` / `韵达快递` / `邮政EMS` / `德邦快递`

> 固定集合而非自由文本：手工录入的数据要靠人去保持一致，自由文本会让「京东物流」「京东」「jd」散成三个值，关键字检索和聚合统计都没法做。

**可建运单的订单状态**：`已发货` / `已送达` / `已签收`

这组值是**本模块自有的业务规则**（定义位置见 §4.2 的「常量单一出处」），不改 `orders.py` 里的任何东西。

**「未录入」**：不是一个数据库值，是列表里的一个**展示态**（`shipments` 里没有对应行）。它同时是列表筛选 `status` 参数的一个合法取值（§4.2）。

### 3.4 索引清单

| 表.列 | 索引类型 | 来源 | 本次动作 |
|---|---|---|---|
| `orders.order_no` | UNIQUE 约束 `orders_order_no_key` | 已存在（`unique=True`） | **不动** |
| `shipments.order_no` | **UNIQUE** | `unique=True` | **新建 ← 用户要的索引** |
| `shipments.tracking_no` | UNIQUE | `unique=True` | 新建 |
| `shipments.id` | PK 索引 + `ix_shipments_id` | `primary_key=True, index=True` | 新建（冗余，见下） |

> `id = Column(Integer, primary_key=True, index=True)` 会额外建一条 `ix_shipments_id`，与主键索引重复。这是**沿用既有写法**（`orders` 上同样有冗余的 `ix_orders_id`），无害，不为本模块单独改。

**建表方式**：`shipments` 是新表，`init_db.py` 里 `Base.metadata.create_all` 会在建表时连同索引一起建出来（`checkfirst=True` 只跳过已存在的表，对新表是全量创建）。因此 `init_db.py` **不需要**额外写 `CREATE INDEX IF NOT EXISTS`。

**已用探针表逐项实测**（与 §3.2 的模型定义逐字同构，跑完回滚）：

```
索引:
  CREATE UNIQUE INDEX _probe_shipments_order_no_key    ON ... USING btree (order_no)   ← 用户要的索引
  CREATE UNIQUE INDEX _probe_shipments_tracking_no_key ON ... USING btree (tracking_no)
  CREATE UNIQUE INDEX _probe_shipments_pkey            ON ... USING btree (id)
  CREATE INDEX        ix__probe_shipments_id           ON ... USING btree (id)         ← 与 PK 重复(既有写法)
约束:
  _probe_shipments_order_no_fkey | f | FOREIGN KEY (order_no) REFERENCES orders(order_no) ON DELETE CASCADE
  _probe_shipments_order_no_key  | u | UNIQUE (order_no)
[TEST1] 同订单号插第二条       -> PASS:被 IntegrityError(UniqueViolation) 拦住
[TEST2] DELETE orders 一条     -> PASS:运单数减少,该订单名下剩 0(级联生效)
[TEST3] trace 存两行文本再读回 -> PASS:读回仍是 2 行(换行原样保留)
```

> ⚠️ **`Shipment` 必须与 `Order` 共用同一个 `Base`（`app.core.database.Base`）**。实测：若把 `Shipment` 挂在另一个独立 `Base` 上，`create_all` 会抛 `NoReferencedTableError: could not find table 'orders'` —— SQLAlchemy 要在同一个 `MetaData` 里解析外键目标。
>
> 实际实现天然满足（两者都 `from app.core.database import Base`），**但 `init_db.py` 的 import 必须同时含 `Order` 和 `Shipment`**，缺任一个都可能让 FK 解析失败或表不被创建。

> ⚠️ **`default="待揽收"` 是 SQLAlchemy 的 Python 端默认值，不是数据库默认值**（与现有 `Order.status` 的 `default="处理中"` 同款写法；实测 `information_schema.columns.column_default` 为 `None`）。
>
> 后果分两种，**边界不在「ORM vs 裸 SQL」而在「SQLAlchemy 构造的语句 vs `text()` 字面 SQL」**（实测校正）：
>
> | 写入方式 | 不赋 `status` 的结果 |
> |---|---|
> | ORM（`db.add(Shipment(...))`） | 自动填 `待揽收` |
> | **Core（`pg_insert(Shipment).values([...])`）** | **也自动填 `待揽收`** ← 种子脚本走这条，**不必**显式给 |
> | `text("INSERT INTO shipments (...) VALUES (...)")` 字面 SQL | **NotNullViolation** |
>
> 所以 §6 的种子脚本用 `pg_insert` 不写 `status` 是安全的；但写测试若用 `text()` 造数据，必须显式给。

`init_db.py` 的改动只有一行 —— 在顶部 import 里加上新模型（不 import 的话 `create_all` 看不见它，表根本不会建）：

```python
from app.models import (User, Conversation, Message, DocumentChunk, Document,
                        ProductPriceStock, Order, Ticket, Shipment)
```

`app/models/__init__.py` 同步加 import 与 `__all__`（照现有写法带 `# noqa: F401`）。

### 4.2 `GET /api/admin/logistics` — 列表

**常量单一出处**：三个枚举**只定义一次**，不要 schema 写一份正则、接口再写一份列表（两份同义集合必然漂移）。

**定义在 `schemas/admin.py`**（不是 `logistics.py`），`logistics.py` 反向 import —— 方向是 `api/admin/logistics.py` → `schemas/admin.py`，单向下行，**无循环导入**（`logistics.py` 本来就要 import 那几个 schema）：

```python
# llm_backend/app/schemas/admin.py
import re

SHIPPABLE_ORDER_STATUSES = ["已发货", "已送达", "已签收"]
SHIPMENT_STATUSES = ["待揽收", "已揽收", "运输中", "派送中", "已签收", "异常"]
CARRIERS = ["京东物流", "顺丰速运", "中通快递", "圆通速递",
            "申通快递", "韵达快递", "邮政EMS", "德邦快递"]
UNRECORDED = "未录入"          # 列表筛选用的展示态,不是 shipments.status 的取值
TRACE_MAX = 2000              # 轨迹文本上限,与前端 textarea 的 maxlength 对齐

# re.escape 是必须的:取值里若出现 | ( ) 等正则元字符,不加转义会把一个值
# 静默拆成多个分支(实测 "空运|海运" 会让 "空运"/"海运" 双双被接受),语义悄悄放宽
SHIPMENT_STATUS_PATTERN = "^(" + "|".join(re.escape(s) for s in SHIPMENT_STATUSES) + ")$"
CARRIER_PATTERN = "^(" + "|".join(re.escape(c) for c in CARRIERS) + ")$"
```

> ⚠️ **不要在这里再定义 `ORDER_STATUSES`。** `llm_backend/app/api/admin/console.py:18` 已经有一份同值定义，且控制台的状态分布图真的在用它 —— 在这里再定义一份正是本节开头要防的「两份同义集合必然漂移」。本模块的列表端点把 `order_status` 当**自由字符串**直接透传给 `Order.status ==`，**不需要**这份枚举做校验。前端 `LogisticsView.vue` 里的那份是 JS 副本，跨语言没法共享，属于合理重复。

> 反方向（定义在 `logistics.py`、schema 反向 import）**会循环导入**：schema 依赖 logistics，logistics 又依赖 schema。别那么写。

**⚠️ 驱动表是 `orders` 不是 `shipments`**（v3 的结构性变化）。用 `OUTER JOIN` 而不是 v2 的 `INNER JOIN`：

```python
stmt = (
    select(Order, Shipment)
    .outerjoin(Shipment, Shipment.order_no == Order.order_no)
    .where(*conds)
    .order_by(Shipment.shipped_at.desc().nullslast(), Order.order_no.desc())
)
```

**最基础的那个条件**（保证「没隐身」）：

```python
conds = [or_(
    Order.status.in_(SHIPPABLE_ORDER_STATUSES),   # 已发货/已送达/已签收 —— 含还没录物流的
    Shipment.id.isnot(None),                      # ∪ 任何已有运单的订单,哪怕订单状态被改回处理中
)]
```

### 4.3 `POST /api/admin/logistics` — 建运单

**请求体**（`order_no` 由前端从被点「补录」的那一行带入，不经过下拉）：

```json
{
  "order_no": "ORD-006",
  "tracking_no": "JDV0000000006",
  "carrier": "京东物流",
  "status": "待揽收",
  "shipped_at": "2026-09-20",
  "signed_at": null,
  "trace": "2026-09-20 14:32 | 广州市 | 已揽收\n2026-09-21 08:05 | 广州转运中心 | 到达转运中心"
}
```

**处理步骤**（顺序不能乱）：

1. 查订单：`select(Order).where(Order.order_no == payload.order_no)`
   - 不存在 → `400 "订单不存在: {order_no}"`
2. 校验该订单还没有运单（`select(Shipment.id).where(Shipment.order_no == ...)`）
   - 已有 → `409 f"订单 {order_no} 已有运单，请勿重复创建"`
   - **放在状态校验之前**：一条订单被改回`处理中`但已有运单时，真实原因是「已有运单」，报「状态不对」会误导
3. 校验订单状态 ∈ `SHIPPABLE_ORDER_STATUSES`
   - 不满足 → `400 f"订单 {order_no} 当前状态为「{status}」，只有已发货及之后的订单才能建运单"`
4. 处理 `signed_at` 与 `status` 的绑定（§4.5 规则 A）
5. 校验 `shipped_at` / `signed_at`（§4.5 规则 B）
6. 校验并规范化 `trace`（§4.5 规则 C）→ 得到规范化文本或 `None`（空白/空串统一存 `NULL`，避免库里同时存在 `''` 和 `NULL` 两种"空"）
7. `db.add(shipment)`；**`await db.flush()`**
8. `except IntegrityError` → 按约束名分支返回 409（§4.4）

> 🔴 **步骤 7 的 `await db.flush()` 不能漏。** `db.add()` 本身不抛异常，冲突要到 `flush()`／autoflush／commit 才暴露。漏了 flush 会出现两种坏结果：冲突由**下面那次重取 SELECT 的 autoflush** 抛出（在 try 之外 → 未捕获 → 500），或由 `get_db` yield 之后的隐式 commit 抛出（响应已生成 → 500）。
>
> `tracking_no` 撞号**没有任何前置查重**（步骤 1–6 里没有），完全依赖这个兜底 —— 漏 flush 时「运单号重复」会变成 500 而不是 409。`orders.py:126-148` 就是这个写法（`db.add()` + `await db.flush()` 一起包在 try 里）。

**响应**：与列表项同结构的完整对象（含 join 出来的 `order_status`/`product_name`/`category`/`buyer_name`）。HTTP 200，与现有端点一致（项目不用 201）。

写入后用一次查询重取：

```python
row = (await db.execute(
    select(Order, Shipment)
    .join(Shipment, Shipment.order_no == Order.order_no)
    .where(Shipment.id == shipment.id)
)).one()
return _serialize(*row)
```

> ⚠️ **这次重取对 POST 而言不是必需的 —— 实测证伪了原稿给的理由。**
>
> 原稿写的是「不要在 ORM 对象上手工拼 join 字段」，但 `_serialize(order, shipment)` **正是列表端点在做的事**，不是手工拼。实测把它换成 `return _serialize(order, shipment)` 后：建单的 21 条用例全绿，且响应体与重取版**逐字段相同**（`shipment.id` 在 `flush()` 后已回填，`order` 是步骤 1 查出来的、没被改过；成功路径上没有 rollback，`expire_on_commit=False` 也不会让它过期）。
>
> **保留它的真实理由**：与 PUT 保持同一形状。**PUT 必须重取** —— 它只 `select(Shipment)`，手上没有 `Order` 对象。两个写端点用同一种收尾，读代码的人不用记「这个有、那个没有」。代价是一次主键查询，管理端手工录入的量级下可以忽略。
>
> 若将来想省掉这一次查询：POST 可以直接 `return _serialize(order, shipment)`，PUT 不行。**那不是一致的简化，是给两个端点制造差异**，所以没做。

### 4.4 `IntegrityError` 的 409 兜底与文案

1:1 之后 `shipments` 上有**两条**唯一键，撞哪条都是 `UniqueViolation`，**只能靠约束名区分**：

| 撞的约束 | 含义 | 文案 |
|---|---|---|
| `shipments_order_no_key` | 该订单已有运单 | `f"订单 {order_no} 已有运单，请勿重复创建"` |
| `shipments_tracking_no_key` | 运单号已存在 | `f"运单号已存在: {tracking_no}"` |
| 其它（如外键违规） | 极窄的并发窗口 | 通用 409 文案 |

```python
except IntegrityError as e:
    await db.rollback()                     # 必须显式回滚,否则后续查询在同一事务里全废
    name = getattr(getattr(e.orig, "diag", None), "constraint_name", "") or ""
    if "order_no_key" in name:
        raise HTTPException(status_code=409, detail=f"订单 {order_no} 已有运单，请勿重复创建")
    if "tracking_no_key" in name:
        raise HTTPException(status_code=409, detail=f"运单号已存在: {tracking_no}")
    raise HTTPException(status_code=409, detail="运单写入冲突，请重试")
```

**实测证据**（同一张探针表，三条插入）：

```
a) dup order_no, 不同 tracking_no : orig = UniqueViolation        diag.constraint = _probe_shipments_order_no_key
b) dup tracking_no, 不同 order_no : orig = UniqueViolation        diag.constraint = _probe_shipments_tracking_no_key
c) FK 违规(order_no 不存在)       : orig = ForeignKeyViolation    diag.constraint = _probe_shipments_order_no_fkey
```

> v2 的 §9⑥ 把「无法区分」的对象写错了：外键违规与撞号是**不同**的异常类，本来就能区分；真正同类的是上面两条唯一键。按约束名分支即可，不是「只能吞掉」。

### 4.5 跨端点的三条校验规则

**规则 A：`signed_at` 与 `status` 强绑定**（与 `orders.signed_date` 完全同款，`orders.py:179-183` 是原型）

| `status` | `signed_at` 取值 |
|---|---|
| 非 `已签收` | **一律置 `NULL`**（状态改回其它即为清空） |
| `已签收`，**显式传了值** | 用传的 |
| `已签收`，**显式传 `null`** | `NULL`（= 日期不详，见下） |
| `已签收`，**没传**，且有原值 | 沿用原值 |
| `已签收`，**没传**，无原值，**刚变成已签收** | 补当天（UTC，`datetime.now(timezone.utc).date()`） |
| `已签收`，**没传**，无原值，**本来就是已签收** | **保持 `NULL`** ← 见下 |

> 服务端兜底，直调接口也造不出「未签收却带签收时间」的数据。
>
> 反过来「`已签收` 但 `signed_at` 为空」是**可达状态**（前端把签收时间输入框清空 → 显式传 `null` → 落库 NULL），是**有意的**：允许「已知签收、日期不详」。§3.2 里那句「仅 `已签收` 时有值」是在说规则 A 的**写入方向**，不是双向约束。
>
> ⚠️ **这一条要在代码里显式支持，不能靠 `given or existing` 自然实现**：后者会把「显式传 `None`」和「没传」当成同一件事，于是管理员清空输入框后旧日期原样回来，那个可清空的日期框就成了摆设。所以 `_resolve_signed_at` 需要一个 `explicit_clear` 参数（由调用方用 `exclude_unset` 的语义判断「键在不在」）。
>
> ⚠️ **「补当天」只适用于「刚变成 `已签收`」，所以还需要一个 `fill_today` 参数。** 少了它会出现**凭空造数据**：一张 `已签收、日期不详` 的运单，管理员**只改了个承运商**（没传 `signed_at`），`given or existing or today` 会把 `signed_at` 填成今天 —— 没人录入这个日期。
>
> 编辑路径必须传 `fill_today=(effective_status == "已签收" and 原状态 != "已签收")`；建单路径恒为 `True`（没有旧状态，管理员选了已签收又没给日期，补当天是唯一合理的解释）。
>
> **判据**：`fill_today` 问的是「**这个日期是这次操作新产生的吗**」，不是「它现在是不是空的」。上一行那个「本来就是已签收」的格子之所以要保持 `NULL`，正是因为那个状态是**上一次操作有意留下的**，不该被一次无关编辑改写。
>
> ⚠️ **`fill_today` 的默认值是 `False`，不是 `True`** —— 安全的那个方向。两个调用点都已显式传参，行为与默认值无关；但万一将来有人漏传：「不填」只留下一个可见的「日期不详」，「填今天」则是凭空造一条**看起来合理**的假数据。**默认值应该站在能被发现的那一侧。**
>
> ⚠️ **这一点与订单模块不一致，是有意的**：`orders.py:179-183` 处理 `signed_date` 用的是 `data.get(...) or today`，**清不掉**。订单模块没为此开小灶，物流模块开了 —— 因为运单侧「已知签收、日期不详」比订单侧更常见（承运商只报了签收、日期漏在轨迹里）。不要为了「与订单模块一致」把这条删掉，那会同时删掉前端那个输入框的意义。

**规则 B：时间先后 + 已签收必须有发货时间**

| 判据 | 结果 |
|---|---|
| `shipped_at` 与 `signed_at` 都有值，且 `signed_at < shipped_at` | `400 "签收时间不能早于发货时间"` |
| `status == 已签收` 且 `shipped_at` 为空 | `400 "已签收的运单必须有发货时间"` |

> 只挡顺序是不够的：v2 的条件是「都有值」，于是「已签收 + 发货时间为空」会放行，详情页出现「发货 —　签收 2026-09-27」。手工录入是唯一数据来源，这条一行代码就能挡掉一类明显漏填。
>
> `shipped_at` 为空在非`已签收`状态下是合法的（待揽收的运单还没发货）。

**规则 C：轨迹必须按格式录入**（v4 新增，用户决策）

**格式：一行一个节点，每行三段，用 `|` 分隔**

```
2026-09-20 14:32 | 广州市 | 已揽收
2026-09-21 08:05 | 广州转运中心 | 到达转运中心
```

| 段 | 要求 |
|---|---|
| 1 | 时间，严格 `YYYY-MM-DD HH:MM`（24 小时制，到分钟） |
| 2 | 地点，非空 |
| 3 | 描述，非空 |

分隔符两侧的空格可有可无（`14:32|广州市|已揽收` 同样合法）。

> **为什么用 `|` 而不是空格**：地点（「广州转运中心」）和描述本身都可能含空格，靠空格切列不可靠；`|` 在中文物流文本里几乎不出现，是干净的分隔符。这也是 §9① 那条「将来可结构化迁移」成立的前提。

**校验 + 规范化**（`logistics.py` 内的模块级函数，POST 与 PUT 共用）：

以下这段追加到 `logistics.py` 的 `router = APIRouter()` 之后（两个 import 要并进文件顶部的 import 块，不是贴在这里）：

```python
class TraceFormatError(Exception):
    """轨迹文本不合格式。line_no 供接口拼错误文案。"""

    def __init__(self, line_no: int, reason: str):
        self.line_no, self.reason = line_no, reason
        super().__init__(f"第 {line_no} 行：{reason}")


class TraceNode(NamedTuple):
    """一个已解析的轨迹节点。

    用具名字段而不是裸元组:下面 `nodes[-1].dt.date()` 与 `nodes[-1].line_no`
    在裸元组里只差一个下标数字(`[1]` vs `[0]`),手滑写反不会报语义错 ——
    `int > date` 会抛 TypeError,把一个本该 400 的路径变成 500。
    """

    line_no: int
    dt: datetime
    loc: str
    desc: str


def parse_trace(raw: str | None, shipped_at: date | None,
                signed_at: date | None) -> str | None:
    """校验并规范化轨迹文本。空文本返回 None;不合格式抛 TraceFormatError。

    ⚠️ 两条容易写错的细节:

    1. **行号必须按管理员在 textarea 里看到的行来数**。先带原行号落表、再丢空行 ——
       如果反过来(丢完空行才 enumerate),"多敲回车"这个本格式明确允许的写法会让
       空行之后的所有行号前移,报错就指到空行上,而行号是这条错误唯一的定位手段。
    2. **按 `\\r\\n|\\r|\\n` 显式拆行**,与前端 LogisticsView 的拆法一致。
       `str.splitlines()` 还会按 U+2028 / U+2029 等 Unicode 分隔符拆(从 Word /
       微信粘贴时会出现),前端不认这些,会造成前后端对"第几行"的判定不一致。
    """
    text = (raw or "").replace("\r\n", "\n").replace("\r", "\n")
    numbered = [(i, line.strip()) for i, line in enumerate(text.split("\n"), 1)]

    nodes: list[TraceNode] = []
    for line_no, line in numbered:
        if not line:                              # 空行直接忽略,不算错
            continue
        parts = line.split("|")
        if len(parts) != 3:
            raise TraceFormatError(
                line_no, f'应为「YYYY-MM-DD HH:MM | 地点 | 描述」三段，实际 {len(parts)} 段')
        ts, loc, desc = (p.strip() for p in parts)
        if not loc:
            raise TraceFormatError(line_no, "地点不能为空")
        if not desc:
            raise TraceFormatError(line_no, "描述不能为空")
        try:
            dt = datetime.strptime(ts, "%Y-%m-%d %H:%M")
        except ValueError:
            raise TraceFormatError(line_no, f'时间「{ts}」不是 YYYY-MM-DD HH:MM')
        nodes.append(TraceNode(line_no, dt, loc, desc))

    if not nodes:
        return None

    # 时间必须严格递增(相同也不行 —— 同一时刻的两个节点排不出先后)
    for prev, cur in pairwise(nodes):
        if cur.dt <= prev.dt:
            raise TraceFormatError(
                cur.line_no, f"时间必须比上一行晚（上一行 {prev.dt:%Y-%m-%d %H:%M}）")

    # 节点必须落在 [shipped_at, signed_at] 内(两端各自有值时才检查,边界相等算通过)
    if shipped_at and nodes[0].dt.date() < shipped_at:
        raise TraceFormatError(nodes[0].line_no, f"首节点日期不能早于发货时间 {shipped_at}")
    if signed_at and nodes[-1].dt.date() > signed_at:
        raise TraceFormatError(nodes[-1].line_no, f"末节点日期不能晚于签收时间 {signed_at}")

    return "\n".join(f"{n.dt:%Y-%m-%d %H:%M} | {n.loc} | {n.desc}" for n in nodes)
```

**这条函数的输出是幂等的**（`parse_trace(parse_trace(x)) == parse_trace(x)`，已实测）—— 这个性质不是巧合，是 §4.8 那条长度不变式成立的前提：**存下来的值必须能原样再提交**。

调用方把 `TraceFormatError` 转成 `400`：

```python
try:
    trace = parse_trace(payload.trace, effective_shipped, effective_signed)
except TraceFormatError as e:
    raise HTTPException(status_code=400, detail=f"轨迹格式不对：{e}")
```

> ⚠️ **必须传 effective 的 `shipped_at`/`signed_at`**（见下方 PUT 那段），否则「只改轨迹」这条路径上窗口校验拿不到值，形同失效。

**设计阶段已实测的 19 个用例**（下表是当时的记录，保留原文；实现阶段又补了 5 条回归用例，见实现记录）：

```
[OK ] 正常 / 无空格 / CRLF / 含空行        -> 规范化后统一为 '\n' 连接、无空行、无首尾空格
[OK ] 空文本 / 只有空白                    -> None
[OK ] 窗口内 / 边界相等 / 两端都为空        -> 通过
[400] 两段 / 四段                          -> 第 N 行：应为「…」三段，实际 M 段
[400] 时间格式错 2026/09/20 14:32          -> 第 N 行：时间「…」不是 YYYY-MM-DD HH:MM
[400] 非法日期 2026-13-45 14:32            -> 同上(strptime 同时校验语义,不只是正则)
[400] 地点为空                             -> 第 N 行：地点不能为空
[400] 时间倒序 / 时间相同                  -> 第 N 行：时间必须比上一行晚（上一行 …）
[400] 首节点早于发货时间 / 末节点晚于签收时间 -> 第 N 行：首/末节点日期不能早/晚于 …
```

**规范化的三条副作用（都要接受）**：

1. **存进去的文本可能与输入不完全一样**（去空行、统一 LF、统一分隔符两侧为 ` | `、去首尾空格）。这是有意的 —— 库里永远是规整格式，前端可以直接渲染不用防御
2. **CRLF 在写入时就被统一成 LF**，所以 §5.4 拆行时不再需要处理 `\r`（那边仍写成 `/\r\n?/g` 只是双保险）
3. **空行不算错**（管理员多敲一个回车不该被拦），规范化时直接丢掉

**⚠️ PUT 里三条规则都必须用「有效值」**，不能直接读 `data` —— 管理员最常见的操作是「只把状态改成已签收」，此时 `shipped_at` 根本没传：

```python
# ✅ PUT 里统一取 effective 值(没传就沿用库里的)
effective_status  = data.get("status", shipment.status)
effective_shipped = data.get("shipped_at", shipment.shipped_at)
effective_signed  = data.get("signed_at", shipment.signed_at)
# 规则 A 用 effective_status
# 规则 B 用 effective_shipped / effective_signed
# 规则 C 的 parse_trace(..., effective_shipped, effective_signed) 同样用这两个
```

照 `orders.py:179-183` 的 `effective_status` 写法。漏了 `shipped_at` 的 effective 取值，规则 B 在「只改状态」这条路径上形同失效。

### 4.6 `PUT /api/admin/logistics/{shipment_id}` — 编辑

**可改字段**：`tracking_no` / `carrier` / `status` / `shipped_at` / `signed_at` / `trace`

**不可改**：`order_no`（schema 里根本没有这个字段，与订单页「编辑不给换商品」同理）

**处理要点**：

- 运单不存在 → `404 f"运单不存在: {shipment_id}"`
- `data = payload.model_dump(exclude_unset=True)` 区分「没传」与「传了 null」
- 🔴 **三个 NOT NULL 列传显式 `null` → 400**：`tracking_no` / `carrier` / `status` 都是 `nullable=False`，放行的话 `setattr(None)` 会在 flush 时抛 `NotNullViolation`，落进 §4.4 那个**为 UniqueViolation 写的** `except IntegrityError` 兜底，拿到空的 `constraint_name` → 返回「运单写入冲突，请重试」。
  - 那是**请求错误**而不是冲突 —— 管理员照着文案重试一万次也不会成功
  - schema 层拦不住：三个字段都是 `Optional[...] = Field(None, ...)`，`None` 是合法值
  - 所以要在 `model_dump` 之后显式挡掉：`for f in ("tracking_no","carrier","status"): if f in data and data[f] is None: raise HTTPException(400, f"{f} 不能为 null")`
  - **不要改成「静默丢弃 null」** —— 那会变成「保存了但没生效」，比 409 更难查
- `trace` 就是个标量列：`"trace" in data` 时走 §4.5 规则 C 的 `parse_trace(..., effective_shipped, effective_signed)`，然后 `setattr`。**注意用 effective 的日期**，否则「只改轨迹、不动状态」这条路径上窗口校验拿不到值
- `signed_at` 与 `status` 用 §4.5 的 effective 值规则，**`fill_today` 传 `became_signed`**
- 冲突分支（`_conflict_409`）要用的 `order_no` / `tracking_no` **必须在 `try` 之前取成局部变量** —— `await db.rollback()` 会让 ORM 对象过期，之后再读属性会抛 `MissingGreenlet`（预审实测确认本机真实存在；已有一条用例钉住它）
- **不重复校验订单状态、也不重复校验「该订单已有运单」**：`order_no` 改不了，这两条在编辑路径上不可能被触发
- `tracking_no` 撞别人的号 → 409（§4.4 同一套兜底）

### 4.7 `DELETE /api/admin/logistics/{shipment_id}` — 删除

运单不存在 → `404`。成功返回照抄 `orders.py:191-201`：

```python
return {"id": shipment_id, "deleted": True}
```

> 删除运单后，该订单会重新变回列表里的「未录入」行（因为列表由 orders 驱动，不依赖 shipments 有行）。这是 v3 设计的自然结果，也正好让「删掉重录」变成一条可用路径。

### 4.8 schema（追加到 `llm_backend/app/schemas/admin.py`）

```python
TRACE_MAX = 2000          # 与前端 textarea 的 maxlength 对齐,两端同一个上限


class ShipmentCreate(BaseModel):
    order_no: str = Field(..., min_length=1, max_length=32)
    tracking_no: str = Field(..., min_length=1, max_length=50)
    carrier: str = Field(..., pattern=CARRIER_PATTERN)
    status: str = Field("待揽收", pattern=SHIPMENT_STATUS_PATTERN)
    shipped_at: Optional[date] = None
    signed_at: Optional[date] = None
    trace: Optional[str] = Field(None, max_length=TRACE_MAX)


class ShipmentUpdate(BaseModel):
    tracking_no: Optional[str] = Field(None, min_length=1, max_length=50)
    carrier: Optional[str] = Field(None, pattern=CARRIER_PATTERN)
    status: Optional[str] = Field(None, pattern=SHIPMENT_STATUS_PATTERN)
    shipped_at: Optional[date] = None
    signed_at: Optional[date] = None
    trace: Optional[str] = Field(None, max_length=TRACE_MAX)
    # ⚠️ 没有 order_no:订单号不可改
```

> 🔴 **`trace` 必须有 `max_length`**。v2 只在前端 `maxlength=2000`，后端裸 `Optional[str]` —— 实测 **3,000,000 字符被照单全收**，且 `main.py` 没有任何 body 大小中间件（只有 `LoggingMiddleware` 与 CORS）。更麻烦的是列表**每行都返回完整 `trace`**，一条超长文本会让之后每次翻页/筛选的响应都带上它。上限放在 schema 才是源头。

> 🔴 **`max_length` 管的是「录入长度」，但存下来的是「规范化后的长度」—— 后者可能更长，必须单独再卡一次。**
>
> 规范化会把 `14:32|广州|已揽收` 变成 `14:32 | 广州 | 已揽收`，**每行 +4 字符**。实测：1974 字符的紧凑写法能通过 `max_length=2000`，规范化后变成 **2290** —— **存的比允许提交的长**。
>
> 后果在编辑路径上爆发（Task 7 + §5.3 的前端 `maxlength`）：管理员打开编辑弹窗，库里 2290 字符的轨迹被塞进 `maxlength=2000` 的 textarea（`v-model` 程序赋值**不受** `maxlength` 约束，实测），他只想改个承运商、原样保存 → 2290 > 2000 → **422**，而 `api.js:42` 把 detail 数组塞进 `Error` → 界面显示 `[object Object]`。
>
> **修法**：接口侧在 `parse_trace` **之后**再查一次规范化长度。别加第二个 schema 常量 —— `max_length=TRACE_MAX` 保留作为录入侧护栏，真正的上限落在 `_parse_trace_or_400` 里（POST 与 PUT 共用同一个包装函数）：
>
> ```python
> def _parse_trace_or_400(raw, shipped, signed):
>     try:
>         normalized = parse_trace(raw, shipped, signed)
>     except TraceFormatError as e:
>         raise HTTPException(status_code=400, detail=f"轨迹格式不对：{e}")
>     if normalized and len(normalized) > TRACE_MAX:
>         raise HTTPException(
>             status_code=400,
>             detail=f"轨迹规范化后 {len(normalized)} 字，超过上限 {TRACE_MAX} 字")
>     return normalized
> ```
>
> **为什么这样就不再有洞**：`parse_trace` 的输出是**幂等**的（§4.5 已实测），所以「存下来的值」再提交时规范化结果就是它自己 —— 只要它当初通过了这个检查，之后每次都能通过。**不变式：任何被接受过的值，都能被原样再提交一次。**
>
> 前端侧同步加一条预校验（§5.3），把 400 挡在网络往返之前。

**`schemas/admin.py` 不需要新增任何 import**：`trace` 是 `Optional[str]`，日期是 `Optional[date]`，现有顶部已有 `from datetime import date` 与 `from typing import Optional`。

`Text` 只出现在**模型文件** `app/models/shipment.py` 的 import 里，schema 层用不到。

### 4.9 前端空串约定（既有坑，新接口必须遵守）

`<input type="date">` 留空时给的是 `''`，`JSON.stringify` 后是 `""`，pydantic 对 `Optional[date]` 收到 `""` 一律 422（实测确认）。

**⚠️「清空一个字段」必须显式送 `null`，不能送 `''` —— 三个可空字段（`shipped_at` / `signed_at` / `trace`）全都适用：**

`cleanBody`（`api.js:12-16`）的实现是：

```js
Object.entries(body).filter(([, v]) => v !== '' && v !== undefined)
```

它会把 `''` 整个键**删掉**，而 PUT 端点的 `exclude_unset` 把它判定为「没传」= **保留旧值**。所以这三个字段一旦填过，用 `''` 是永远清不掉的。

```js
// ❌ 清不掉:'' 被 cleanBody 摘掉 → 后端认为"没传" → 保留旧值
shipped_at: form.shipped_at,
// ✅ 正确:cleanBody 保留 null(实测 cleanBody({shipped_at:null}) === {shipped_at:null})
shipped_at: form.shipped_at || null,
signed_at:  form.signed_at  || null,
trace:      form.trace      || null,     // ← textarea 同样,别以为"送空串后端会归一化"
```

实测对照：

```
cleanBody({shipped_at:null}) = {"shipped_at":null}     ← 保留,null 是唯一可行的清空通道
cleanBody({trace:''})        = {}                       ← 键被删除,PUT 变成"不改动轨迹"
cleanBody({trace:null})      = {"trace":null}           ← 保留 ✓
```

> 🔴 **v2 在这里自相矛盾过**：它一边讲对了 `cleanBody` 的机制，一边又说 `trace`「没有 exclude_unset 语义问题，原样送即可」—— 照做的后果是**管理员清空轨迹文本框后旧轨迹原封不动回来**，而且列表不显示轨迹、肉眼看不出来。
>
> ⚠️ **后端测试抓不到这个缺口**：§7 用例「传空串 → 清成 NULL」是直调接口，绕过了 `cleanBody`，会通过。所以这条必须在前端代码注释里钉死（§5.3）。

订单页正是靠 `|| null` 这一点清空 `signed_date` 的（`OrderView.vue:411-413`），照抄。

```js
// 本地日期助手:必须用本地年月日,不要用 toISOString().slice(0,10)
// (那是 UTC,国内晚上 8 点后会差一天)——照抄 OrderView.vue:325-329
function todayStr() {
  const d = new Date();
  const p = (n) => String(n).padStart(2, '0');
  return `${d.getFullYear()}-${p(d.getMonth() + 1)}-${p(d.getDate())}`;
}

// filling 标记:打开弹窗回填时短路 watcher 一次,否则回填的 signed_at 会被覆盖成今天
let filling = false;
watch(() => form.status, (next, prev) => {
  if (filling) return;
  if (next === '已签收' && prev !== '已签收') form.signed_at = todayStr();
  else if (next !== '已签收') form.signed_at = '';
});

function openEdit(row) {
  filling = true;
  Object.assign(form, { /* …含 status 与 signed_at… */ });
  nextTick(() => { filling = false; });
}
```

> 这段修正写法经**真实浏览器全场景验证**：① 打开补录 → 关闭 → 打开编辑（已签收，库值 2026-09-01）→ 回填得 `2026-09-01` ✓；② 用户手动「运输中 → 已签收」→ 带出今天 ✓（**没把功能修没**）；③ 手动切回运输中 → 清空 ✓；④ 连续编辑两条已签收分别得 09-01 / 09-02 ✓。
>
> 替代写法：把联动挂到下拉框的 `@change` 上（只有用户手动改才触发），彻底避开 watcher。

**删除确认文案**（§6.4.8 模板「确定删除{对象}「{名称}」？{后果说明}」）：

```js
if (!window.confirm(`确定删除运单「${row.tracking_no}」？该订单会回到「未录入」状态，可重新补录。`)) return;
```

  <span class="ml-1">{{ (form.trace || '').length }} / {{ TRACE_MAX }}</span>
</p>

```js
const TRACE_MAX = 2000;   // 与后端 schemas/admin.py 的 TRACE_MAX 保持一致
const TRACE_PLACEHOLDER =
  '一行一个节点，例如：\n' +
  '2026-09-20 14:32 | 广州市 | 已揽收\n' +

**前端逐行校验**（格式清单与 §4.5 规则 C 完全一致，提交前挡住，别等 400）：

```js
// 返回第一条错误的中文描述;全部通过返回 ''
// ⚠️ 行号口径必须与后端 parse_trace 一致:按用户在 textarea 里看到的行数编号
//    (空行占位),不能先丢空行再编号 —— 否则空行之后的所有行号前移,红字指到空行上
function validateTrace(raw, shippedAt, signedAt) {
  const lines = (raw || '').replace(/\r\n?/g, '\n').split('\n');
  const nodes = [];
  for (let i = 0; i < lines.length; i++) {
    const n = i + 1;
    const line = lines[i].trim();
    if (!line) continue;                       // 空行忽略,不算错
    const parts = line.split('|');
    if (parts.length !== 3) return `第 ${n} 行：应为「时间 | 地点 | 描述」三段，实际 ${parts.length} 段`;
    const [ts, loc, desc] = parts.map((p) => p.trim());
    if (!loc) return `第 ${n} 行：地点不能为空`;
    if (!desc) return `第 ${n} 行：描述不能为空`;
    if (!/^\d{4}-\d{2}-\d{2} \d{2}:\d{2}$/.test(ts)) return `第 ${n} 行：时间要写成 2026-09-20 14:32 这样`;
    nodes.push({ lineNo: n, ts, loc, desc, day: ts.slice(0, 10) });
  }
  if (!nodes.length) return '';
  for (let i = 1; i < nodes.length; i++) {
    if (nodes[i].ts <= nodes[i - 1].ts) return `第 ${nodes[i].lineNo} 行：时间要比上一行晚`;
  }
  if (shippedAt && nodes[0].day < shippedAt) {
    return `第 ${nodes[0].lineNo} 行：不能早于发货时间 ${shippedAt}`;
  }
  if (signedAt && nodes[nodes.length - 1].day > signedAt) {
    return `第 ${nodes[nodes.length - 1].lineNo} 行：不能晚于签收时间 ${signedAt}`;
  }
  // 长度按【规范化之后】算:规范化每行加 4 个字符(`|` -> ` | `),后端也是这么卡的(§4.8)。
  // 上面的正则已保证 ts 是规范形态,所以这里拼出来的就是后端会存下来的那个字符串。
  const normalized = nodes.map((x) => `${x.ts} | ${x.loc} | ${x.desc}`).join('\n');
  if (normalized.length > TRACE_MAX) {
    return `轨迹规范化后 ${normalized.length} 字，超过上限 ${TRACE_MAX} 字`;
  }
  return '';
}
```

- **前端只做「挡一下」，权威判定在后端**：前端用字面量比较字符串（`2026-13-45` 这种非法日期前端看不出来，后端 `strptime` 会拦），所以是**互补**不是重复。前端拦住的错误不用往返一次网络，体验更好
- 校验时机：`watch(() => form.trace)` 实时跑 + 保存前再跑一次。**校验不通过时红框 + 下方红字，并禁用保存按钮**
- **不要试图在 textarea 里逐行标红**（原生 textarea 做不到）；错误只在下方显示一行「第 N 行：…」，够用了
- `maxlength` 是**硬截断**（实测：输入 2500 字符只剩 2000，粘贴同理且**界面无任何提示**），所以配一个字数计数器，别让用户以为写进去了
- `v-model` 回填走的是程序赋值，**不受 `maxlength` 约束**（实测 `.value = 3000 字符` 会原样保留）—— 所以后端 schema 的 `max_length` 才是真源头（§4.8），前端这个只是顺手挡一下
- `font-mono` 让用户自己对齐。Tailwind 默认主题有 `mono`，JIT 会为新 `.vue` 生成（已核对 `tailwind.config.cjs` 的 `content` 含 `./src/**/*.{vue,js}`）

> 🔴 **必须在保存函数里钉死这一行**（注释写明理由，因为后端测试抓不到）：
>
> ```js
> trace: form.trace || null,   // 空串会被 cleanBody 摘掉 → 后端认为"没传" → 轨迹永远清不掉(§4.9)

## 6. 种子数据

新建 `llm_backend/scripts/seed_shipments.py`，照 `seed_orders.py` 的写法（`pg_insert` + `on_conflict_do_update` 幂等 upsert）。

**覆盖范围：只给「已送达」和「已签收」的订单建运单，「已发货」的故意不建。**

| 订单状态 | 条数 | 是否建运单 | 页面上看到 |
|---|---|---|---|
| 已发货 | 6 | **不建** | 「未录入」+ 补录按钮 ← 演示 v3 的新功能 |
| 已送达 | 4 | 建 | 派送中 |
| 已签收 | 3 | 建 | 已签收 |

> ⚠️ **不能给所有可开单订单都建运单**。v2 是「13 条全建」，后果是页面上一条「未录入」都看不到 —— 新加的补录流程演示不了，且依赖「有空闲订单」的测试会红（审计实测：13 条全建后，需要空闲订单的用例直接失败）。
>
> 这 13 条（6 + 4 + 3）是**运行期实测值**，不是常量：管理员改订单状态后这个数会漂移。脚本按当下查询结果生成，不写死。

**字段生成规则**：

| 字段 | 规则 |
|---|---|
| `tracking_no` | `JDV{order_no 的数字部分:010d}`，如 `ORD-003` → `JDV0000000003`。确定性生成 |
| `order_no` | 直接取订单号（作为幂等键，见下） |
| `carrier` | 京东物流为主（京东自营），按 index 轮转掺入顺丰/中通 |
| `status` | 按订单状态推导：已送达→`派送中`；已签收→`已签收` |
| `shipped_at` | `order_date + 1 天`，用 `min(..., today)` 兜住未来日期 |
| `signed_at` | 仅`已签收`时有值：**`order_date + 2 天`**，同样 `min(..., today)` |
| `trace` | 按运单状态生成递进的文本行，见下 |

> ⚠️ `signed_at` 必须跟 `seed_orders.py:73` 的订单签收日**取同一个偏移（+2 天）**。写成 +3 天会让同一条已签收订单出现「订单签收日 9-22、运单签收日 9-23」的自相矛盾演示数据。

**`trace` 文本生成**：按运单状态生成递进的节点行，**每行必须是 §4.5 规则 C 的三段式 `YYYY-MM-DD HH:MM | 地点 | 描述`** —— 种子是直接写库的，绕过了接口校验，所以**格式正确性由脚本自己保证**。生成后建议在脚本里断言一次 `parse_trace(...)` 不抛异常（或直接复用那个函数生成），否则会往库里塞进接口自己都不认的数据。

| 运单状态 | 轨迹行（5 个节点的是已签收） |
|---|---|
| 派送中 | 已揽收 → 到达转运中心 → 运输中 → 派送中（4 行） |
| 已签收 | 已揽收 → 到达转运中心 → 运输中 → 派送中 → 已签收（5 行） |

节点时间从 `shipped_at` 当天 09:00 起，**按 `+0h / +6h / +12h / +18h / +22h` 递进**。

> 🔴 **偏移必须 ≤ `signed_at`，且行数与节点数一一对应。**
>
> v2 写的是 `+0h / +18h / +30h / +42h`（4 个偏移），有两个错：① 已签收有 **5** 个节点，4 个偏移不够，实现者只能猜；② `+42h` 从 `shipped_at 09:00` 起算落在 `signed_at` **之后一天**，轨迹末行「已签收」比表头「签收」还晚 —— 正是它自己警告的那类自相矛盾演示数据。实测：
>
> ```
> shipped=2026-09-21  base=09:00
>   +0h → 2026-09-21 09:00     +6h → 2026-09-21 15:00
>   +12h → 2026-09-21 21:00    +18h → 2026-09-22 03:00
>   +22h → 2026-09-22 07:00    ← 末节点(signed_at=2026-09-22)落在当天内 ✓
> ```
>
> **生成规则的不变式：所有节点时间必须落在 `[shipped_at, signed_at]` 区间内**（`signed_at` 为空时只要求 ≥ `shipped_at`）。

> ⚠️ **不能直接对 `shipped_at`（`Date`）加 `timedelta(hours=N)`** —— `date + timedelta(hours=N)` 返回的**还是 `date`，小时部分被直接截断**。实测：
>
> ```
> date(2026,9,20) + timedelta(hours=0)  = date(2026, 9, 20)
> date(2026,9,20) + timedelta(hours=18) = date(2026, 9, 20)   ← 和 +0h 撞了
> date(2026,9,20) + timedelta(hours=30) = date(2026, 9, 21)
> date(2026,9,20) + timedelta(hours=42) = date(2026, 9, 21)   ← 和 +30h 撞了
> ```
>
> 4 个偏移只会塌成 2 个不同值 → 轨迹行时间重复，看着像数据错了。
>
> **正确做法**：先把 `Date` 升成 `datetime` 再加偏移：
>
> ```python
> from datetime import datetime, time, timedelta
> base = datetime.combine(shipped_at, time(hour=9))   # 9 点起揽收,比 0 点自然
> line = f"{(base + timedelta(hours=offset)):%Y-%m-%d %H:%M} | {loc} | {desc}"
> ```

**幂等策略**（与 `seed_orders.py` 同款「upsert 覆盖」而非「存在则跳过」）：

```python
stmt = pg_insert(Shipment).values(rows)
stmt = stmt.on_conflict_do_update(
    index_elements=[Shipment.order_no],      # 1:1 之后的天然幂等键
    set_={"status": stmt.excluded.status,
          "shipped_at": stmt.excluded.shipped_at,
          "signed_at": stmt.excluded.signed_at,
          "trace": stmt.excluded.trace},
)
```

**这个幂等策略的三个后果，必须写进注释**（实测确认）：

1. **覆盖对象是「所有订单号落在种子范围内的运单」，不只种子自己插的那些** —— 管理员手工给这些订单建的运单，`status/shipped_at/signed_at/trace` 四个字段同样会被覆盖（`tracking_no`/`carrier` 因为不在 `set_` 里而**保留**）
2. `tracking_no` 不在 `set_` 里 → §6 那句「确定性生成」**只在首次插入成立**，重跑不会把漂移的运单号改回来。这是有意的：管理员手改的运单号应该被尊重
3. **跨订单撞号会让整个脚本中止**：若种子要用的 `JDV...` 运单号已被另一个订单占用，`ON CONFLICT (order_no)` 拦不住它，整条多行 `INSERT` 抛 `UniqueViolation`，单语句单事务 → 全脚本失败。概率极低（`JDV` 前缀是种子专用），但注释里要写明排查方向

20. `status != '已签收'` 传了 `signed_at` → 落库为 `null`
21. `signed_at < shipped_at` → 400
22. **`status='已签收'` 但 `shipped_at` 为空 → 400**（§4.5 规则 B 的第二条）
23. `status` / `carrier` 非法值 → 422
24. `trace` 传空串 / 纯空白 → 落库为 `NULL`
25. `trace` 超 `TRACE_MAX` → 422（钉住 §4.8 新增的 `max_length`）

**轨迹格式（§4.5 规则 C）—— 建单与编辑两条路径都要覆盖**

26. 合法轨迹 → 200，且落库文本是规范化的
27. **空行被忽略**：`"A...\n\nB..."` → 200，落库无空行
28. **CRLF 被规范化**：输入 `\r\n` → 落库为 `\n`
29. 段数不对（2 段 / 4 段）→ 400，`detail` 含「三段」
30. 时间格式不对（`2026/09/20 14:32`）→ 400，`detail` 含行号
31. **非法日期（`2026-13-45 14:32`）→ 400**（这条只有后端能拦，前端正则放行 —— 钉住「权威判定在后端」）
32. 地点或描述为空 → 400
33. **时间倒序 → 400**；**时间相同 → 400**（`detail` 指明是哪一行）
34. **首节点早于 `shipped_at` → 400**
35. **末节点晚于 `signed_at` → 400**
36. **编辑时不传 `shipped_at`/`signed_at`，但轨迹越界 → 400**（钉住 §4.6 那句「必须传 effective 值」—— 漏了这句这条路径上窗口校验会静默失效）
37. 两边日期都为空（如`待揽收`）→ 窗口校验不触发，格式合法即通过

**编辑 `PUT /api/admin/logistics/{id}`**

38. 运单不存在 → 404
39. 改 `status` 为`已签收` → `signed_at` 补当天
40. 从`已签收`改回`运输中` → `signed_at` 被清成 `null`
41. `trace` 传新文本 → 覆盖；传 `null` → 清成 `NULL`；**不传** → 原样不动
42. 传 `order_no` → **不生效**（schema 里没有该字段，pydantic 默认忽略额外字段；断言订单号未变）
43. `tracking_no` 撞别人的号 → 409 且 `detail` 含「运单号已存在」

> ⚠️ **用例 41 的「传 `null` → 清成 NULL」抓不到前端那个 bug**（它是直调接口，绕过了 `cleanBody`）。前端路径只能在 §5.3 的代码注释里钉死。这里加一条注释说明该用例的覆盖面边界，别让人以为 UI 路径已被覆盖。

**删除 `DELETE /api/admin/logistics/{id}`**

44. 运单不存在 → 404
45. 删除成功 → 返回 `{"id": ..., "deleted": True}`，且运单没了
46. **删除后该订单回到「未录入」**：再查列表，该行仍在，`id` 变回 `null`（v3 新增的对称性）

**级联（跨模块）**

47. **删订单 → 它的运单一并消失**。用新建的测试订单 + 测试运单做，不碰种子数据
48. 删订单级联**不影响**其它订单的运单

**索引与模型**

49. `shipments` 表上存在 `order_no` 的**唯一**索引（查 `pg_indexes`，断言 `indexdef` 同时含 `UNIQUE` 与 `order_no`）
50. `shipments` 表上存在 `tracking_no` 的唯一索引

> 🔴 **49/50 必须连库查 `pg_indexes`，不能照抄 `test_product_price_stock_model.py`。** 那个文件是 **DB-free** 的：它走 `__table__.constraints` 读 `UniqueConstraint.name`，而 `unique=True` 生成的约束在 Python 侧 **name 是 `None`**（实测 `UniqueConstraint names: [None, None]`）—— 照抄会写出一个**永远断言不到任何索引**的测试（空断言，静默通过）。
>
> 参考写法：
>
> ```python
> r = await conn.execute(text(
>     "SELECT indexdef FROM pg_indexes WHERE tablename='shipments' AND indexdef ILIKE '%order_no%'"
> ))
> defs = [row[0] for row in r]
> assert any("UNIQUE" in d for d in defs)
> ```
>
> 这两条是本模块**唯一能证明「索引真的建出来了」**的断言。

## 9. 已知取舍与风险

**① 轨迹仍是「一个 TEXT 列」，但格式被强制**（v4 定案）

v3 曾把这条摆成明牌取舍：不强制格式（录入自由、将来要人工清洗）vs 强制格式（将来可迁移、录入要守规矩）。**用户选了强制**，所以现在是：一张表一个 TEXT 列 + §4.5 规则 C 的强校验。

**换来的**：`split('\n')` → `split('|')` 就能可靠还原出「时间 / 地点 / 描述」三列，将来要加 `shipment_tracks` 子表（或三个独立列）时是一次**脚本化回填**，不是人工清洗。连带好处是详情弹窗现在能拆三列渲染（§5.4），不用整行原样显示。

**代价**：管理员录入时必须守格式，写错了会被 400 拦下。空白/CRLF/空行这类无害差异由后端规范化吸收（§4.5 规则 C），不会为难人。

**仍然做不了的事**：跨运单的结构化查询（「查所有卡在某个转运中心的运单」「统计平均运输时长」）。因为轨迹在**同一个 TEXT 列里**，SQL 层没法直接按节点过滤/聚合 —— 那是 `LIKE` 全文匹配，不是索引查询。**要真做这类查询，必须先把它拆成列或子表**（那时候格式已就绪，拆起来是纯脚本活）。

**为什么不干脆现在就拆？** 用户明确要求「一张表 + 文本」。格式强制已经消掉了将来迁移的最大障碍，剩下的拆表工作随时可以做，不必现在付这个复杂度。

**② 一对一：一单只能一个运单**

真实场景里一个订单可能拆多个包裹（多个运单）。本次按用户决策收敛成 1:1，用 `shipments.order_no` 的唯一约束强制。

**将来若要放开**：删掉该列的 `unique=True`、去掉 §4.3 步骤 2 的「已有运单」校验、把 §4.4 的 `order_no_key` 分支去掉、列表的行 key 从 `order_no` 改回 `shipment.id` 即可。

**③ 「订单状态」与「物流状态」解耦 —— 但有两条护栏**

用户明确选择「只在建运单时校验订单状态」。因此：订单建好运单后被改回`处理中`，运单仍然存在且可正常编辑，接口不报错。

理由：订单状态现在是任意跳转、无状态机约束的（`docs/diagrams/spec/60-order-lifecycle.json` 已记录这一点）。如果编辑运单时也校验，管理员会被「先改订单状态才能改运单」卡住，规则更绕。**这是有意的设计，不是遗漏。**

**护栏一（v3 新增）：列表不由订单状态单独决定。** `conds` 里那个 `OR Shipment.id IS NOT NULL` 保证了「任何已有运单的订单」都会出现。少了它，订单状态一回退，那条运单就从页面上彻底消失 —— 编辑不了也删不掉。**这是 v2 的漏洞，v3 修掉。**

**护栏二：订单状态下拉含`处理中`。** 因为上面那类行只可能靠它筛出来。接口本来就接任意值，是 UI 侧不能只给 3 个。

**已知局限（明说）**：这个模块**看不到「两个签收日」的差异**。`orders.signed_date` 归订单模块写，`shipments.signed_at` 归本模块写，两者**没有任何一致性校验**。管理员把某个仍是`已发货`（订单侧 `signed_date` 为 NULL）的订单的运单改成`已签收`，订单页显示「未签收」、物流页显示「签收 = 今天」。

这是解耦的直接后果，与上面的状态解耦是同一件事。§6 的种子故意把两者对齐（都取 +2 天）只是为了看数据顺眼，**不是约束** —— 别被演示数据误导成「有校验」。

**另一个已知局限**：物流页**无法从订单管理页跳转进入**（没要求）。管理员在订单页看不出某单有没有录物流，得切到物流页搜订单号。

**④ 种子脚本重跑会覆盖种子范围内订单的运单数据**

见 §6 幂等策略结尾的三条后果。最关键的一条：**覆盖对象包括管理员手工给这些订单建的运单**（`status/shipped_at/signed_at/trace` 会被覆盖，`tracking_no`/`carrier` 保留）。

**⑤ 既有 bug：`OrderView.vue:339-342` 的签收日期 watcher 会在回填时覆盖库值**

**这是既有代码的 bug，不在本模块范围内，本次不修** —— 但本模块的签收时间联动**不能照抄它**（§5.2 已给出修正写法，且经真实浏览器全场景验证）。

- **成因**：`watch(() => form.status)` 无法区分「用户手动切换」与「`openEdit` 回填」，回填也会触发它。而 `prev` 拿到的是**上一次表单**的状态，不是这条记录的旧状态
- **触发条件**：上一次表单的 `status` 不是`已签收`（例如刚点过「新增」、或刚编辑过一条其它状态的记录），此时再编辑任意一条已签收记录 → 签收日期被改成今天
- **后果**：界面上看不出异常（显示的就是"今天"），一保存就把错误的签收日期写进库；后端规则是「显式传了用传的」，会照单全收
- **实测复现**（`frontend/node_modules` 的 vue 包，逐字照抄那 4 行 watcher）：

  ```
  场景A 上次停在「处理中」→ 回填 signed_date 应为 2026-09-01,实际得到 2026-09-27  ★
  场景B 上次停在「已签收」→ 回填 signed_date = 2026-09-02                      正常
  ```

- **建议**：作为独立 bug 单处理（改动落在 `OrderView.vue`）

**⑥ `min_length=1` 挡不住纯空格**

实测 `tracking_no = " "`、`order_no = " "` 都能通过 pydantic 校验 —— `min_length` 数的是字符数，空格算字符。

**处理**：不需要额外 strip（前端预校验已挡；纯空格是管理员手滑，不是攻击面）。

**⑦ 枚举 pattern 不需要防御换行**

实测 pydantic 2.13 走 Rust regex，**没有** Python `$` 匹配末尾换行的怪癖：`'京东物流\n'` 被正确拒绝。不用加防御。

## 11. 审计记录（v3–v4）

**⑧ 列表的 `count(*)` 精确性依赖 `shipments.order_no` 的 UNIQUE 不变式**

§4.2 的 `total` 用的是 `select(func.count()).select_from(Order).outerjoin(Shipment, ...)`。今天算出来是对的，因为 1:1 由 `shipments.order_no` 的 UNIQUE 约束在 DB 层强制 —— 一条订单最多配一条运单，`count(*)` 不会被放大。

**代价**：将来若把「一单一运单」放宽成 1:N（§9② 描述了怎么放），`total` 会**静默放大**（每单多算几条），前端会出现翻不到内容的空页、HTTP 仍是 200。放开 1:1 时**必须同时**把 count 改成 `count(distinct orders.id)`。

**为什么不现在就写成 `count(distinct ...)`**：那会让最常用的路径多一个聚合，而 1:1 是 DB 强制的、不会漂移。记在这里，作为放开 1:1 时的检查项。

**⑨ `keyword` 不转义 `%` 与 `_`**

`ilike(f"%{kw}%")` 里用户输入的 `%` / `_` 会被当通配符 —— 搜 `%` 会返回全部行。

这与 `orders.py` / `products.py` 的既有 `keyword` 语义完全一致（本仓库既有范式），且参数是绑定的、**不是注入**。规模小、无索引压力，不值得为它开小灶。**记录，不改。**

**⑩ `elif status:` 是个静默兜底**

列表的物流状态筛选写成 `if status == UNRECORDED: ... elif status: ...`。今天只有一个展示态哨兵，语义正确。

**将来若加第二个展示态哨兵**（比如「异常待办」），它会落进 `elif status:` 变成 `Shipment.status == '异常待办'` → 永远 0 行、**HTTP 200 不报错、页面空白**。届时改成显式映射（`{UNRECORDED: Shipment.id.is_(None), ...}`）或把 `status` 校验进 `SHIPMENT_STATUSES + [UNRECORDED]` 并 422 —— 从「静默空」变成「响亮错」。**今天只有一个哨兵，按不过度设计不动。**

> 分支顺序（哨兵必须在 `elif status:` 之前）今天由 `test_filter_unrecorded` 保护 —— 谁把两个分支调换，那条会立刻红。

**⑪ `_check_time_order` 的名字比它实际做的窄**（Task 6 代码质量审查提出，未改）

它管两件事：`signed < shipped`（名副其实的「顺序」）与 **`已签收` 必须有 `shipped_at`**（这是完整性检查，与先后顺序无关）。名字只覆盖了前者。

**未改的理由**：纯可读性收益，代价是重命名一个既有函数 + 改两个调用点。按「不重构没坏的东西」不动。

**什么时候该改**：如果将来再加第三条时间规则，或有人因为名字没找到「已签收必须有发货时间」这条检查 —— 改成 `_check_time_fields` 或拆成两个一行函数。

**⑫ `_resolve_signed_at` 的 `explicit_clear` 与 `given` 存在矛盾组合**（Task 6 代码质量审查提出，未改）

`explicit_clear=True` 配上非 `None` 的 `given` 会**静默丢掉 `given`**、返回 `None`。这个不变量（`explicit_clear` ⟹ `given is None`）只在调用点靠 `and payload.signed_at is None` 维持。

审查者给的替代形状更稳：把 `explicit_clear: bool` 换成 `provided: bool`，三种状态只由 `provided` + `given` 表达，矛盾组合不存在，调用点那句 88 字符的表达式也缩到 45 字符：

```python
def _resolve_signed_at(status, given, existing, *, provided: bool):
    if status != "已签收":
        return None
    if provided:                      # 显式给了值（可能是 None = 清空）
        return given
    return existing or datetime.now(timezone.utc).date()
```

**未改的理由**：当前两个调用点都传对了，是**潜在陷阱不是活 bug**；改签名要同时动 Task 6/7 两个调用点。按「不重构没坏的东西」不动。

**⚠️ 触发条件已更新（Task 7 代码质量审查提出，我采纳）：**

原触发条件写的是「出现**第三个**调用点」。审查者的判断是「**按字面没触发，按实质已经触发了**」—— 我认同：

> 第三条调用点没出现（全仓始终只有 2 处），但那条触发条件**想防的东西已经兑现两次**，每个布尔值各一次：
> - Task 6：建单站点**漏传** `explicit_clear` → 管理员清空的日期被回填（真 bug）
> - Task 7：编辑站点 `fill_today` **传错** → 已签收/日期不详被凭空填今天（真 bug）

原判据是「靠每个调用点自己传对参数」这个假设该放弃。现在调用方要传对的是**两个**布尔，且失败模式已在两个站点各兑现一次 —— **这个假设已经被证伪了，不是"将来可能被证伪"**。

**现在仍不重开 `provided` 重构**（理由同上，且 Task 8 之后本模块冻结）。但已做三件最小补偿：

1. **`fill_today` 的默认值改成 `False`** —— 安全的那个方向。两个调用点都已显式传参、行为零变化；但万一将来有人漏传：「不填」只留下一个可见的「日期不详」，「填今天」则是凭空造一条**看起来合理**的假数据。**默认值应该站在能被发现的那一侧。**
2. **给 `_resolve_signed_at` 加了直接单测**（按 §4.5 那张真值表参数化）。它是纯函数、本来就该独立可测 —— 而 Task 7 暴露的正是「只经 HTTP 间接覆盖会漏掉整条输入维度」（显式传日期那条路径两个变异存活）。
3. 本条触发条件的文字已更新。

**什么时候该改**：出现**第三个**调用点的时候 —— 那时「靠每个调用点自己传对三个参数」的假设就该放弃了。

**⑬ 建单端点末尾那次重取查询，对 POST 而言不是必需的**（Task 6 代码质量审查提出，未删）

实测把它换成 `return _serialize(order, shipment)`：建单 21 条用例全绿、响应体逐字段相同（`shipment.id` 在 `flush()` 后已回填，`order` 是步骤 1 查出来的、没被改过，成功路径上没有 rollback）。

**保留的理由**：**与 PUT 同形**。PUT 只 `select(Shipment)`，手上没有 `Order` 对象，**必须**重取。两个写端点用同一种收尾，读代码的人不用记「这个有、那个没有」，代价是一次主键查询。

**什么时候该改**：不要只简化 POST —— 那会制造两个写端点的差异；要省就两个一起省（PUT 需要先把 `Order` 查出来，等于把查询挪到前面，收益为零）。**所以实际上不该改。**

**与设计的偏差**（逐条：设计是什么 / 实际怎么做 / 为什么）：

1. **Task 2 — schema 三处清理**。设计是照抄既有 `orders.py` 的形状；实际做了三件事：① 删掉 `admin.py` 里新加的 `ORDER_STATUSES` —— 它与 `console.py:18` 的同名常量重复且**无人消费**，是死代码；② 枚举 pattern 的 `join` 加 `re.escape`，防止将来往取值集合里加含正则元字符的项时静默失配；③ 模块 docstring 的「5 个模块」改成 6。
2. **Task 2 — 否决项：`validate_default=True` 不采纳**。审查者建议给 `status` 字段加 `validate_default=True`，让默认值也走 pattern 校验。判断为**投机性加固** —— 默认值是代码里写死的字面量、不可能不合规，加上只是给未来的自己加一道没有信息量的门。**不采纳，记为已知取舍。**
3. **spec 校正 — 默认值生效边界的判据写错了**（提交 `017ad74`）。原稿把边界写成「ORM vs 裸 SQL」；实测的边界是「**SQLAlchemy 构造的语句 vs `text()` 字面 SQL**」—— 前者由 SQLAlchemy 渲染，Python 端默认值会生效；后者是字面 SQL，默认值不会生效。结论没变，变的是判据划在哪。
4. **Task 3 — `parse_trace` 四处修正**。① 行号改为按**原文本行号**编号（空行占位）—— 原实现先丢空行再编号，空行之后的报错行号会**前移**，而行号是这类错误唯一的定位手段；② 拆行从 `str.splitlines()` 改为 `\r\n|\r|\n` —— 前者会把 U+2028 等 Unicode 分隔符也当换行，与前端 `/\r\n?/g` 对「行」的定义不一致（补 `test_parse_trace_does_not_split_on_unicode_separators`）；③ `parsed` 从裸 dict 改成 `TraceNode` NamedTuple；④ 错误文案按「格式错 / 时间不递增 / 超出窗口」拆分。
5. **Task 3 — 跨任务约束：`TRACE_MAX` 的检查点必须挪到规范化之后**（`_parse_trace_or_400`）。设计把长度上限写在入参 schema 上（`max_length`），但**规范化每行会加 4 个字符**（`HH:MM` → `YYYY-MM-DD HH:MM`、`|` → ` | `）—— 一个刚好卡在 2000 的合法输入，规范化后会**超过 `max_length`**，存下来的值突破上限。故长度检查放在规范化之后（`test_trace_length_is_checked_after_normalization` 钉住）。
6. **Task 4 — 计划里的验证写法是假通过**。计划 Step 3 用 `for r in app.routes` 遍历找路径；本机 FastAPI **0.141.1** 的 `include_router` 放进 `app.routes` 的是**没有 `.path` 属性的包装对象**，那个循环一条也匹配不到却**不会报错**。改用 `app.openapi()['paths']`。
7. **Task 4 — `_serialize` 判空从 `if s` 改成 `is not None`**。对象真值判断是**静默全量故障**的隐患：实测构造 `bool()` 为假的对象（`__bool__` / `__len__` 返回假）会让整条记录被当成「不存在」而返回空值，页面上看不出任何报错。参数名 `o` / `s` 一并改成 `order` / `shipment` 自解释。
8. **Task 5 — Step 4 的「全部 PASS」不可能达成**。计划原预期是「跑完 Step 4 全部用例 PASS」，但那批里**有 8 条要先建一条运单**（打 `POST /api/admin/logistics`），而该端点在 Task 6 才实现，在 Task 5 的时点必然红。改成精确的**预期 `27 passed, 8 failed`**，并显式指定由 Task 6 承接这 8 条。（不是缺陷，是已知的跨任务依赖 —— 让它们红得明明白白，好过伪装成绿。）
9. **Task 5 — 补分页覆盖 + `_list` 改用 `params=`**。① 原来 13 条列表用例**一条都不带 `page`**（`_list` 把 `page_size` 默认压成 100），分页切片逻辑等于零覆盖 —— 补 `test_pagination_slices_without_overlap`；② `_list` 原来手工拼查询串，值里含 `&` / `#` 会**静默改变语义**（`&` 直接切断参数），改用 `params=` 交给 httpx 编码。
10. **Task 6 — 404/405 的判据被推翻（重要）**。计划原来把「未注册路径 → 404、方法不匹配 → 405」归因于「路径是否注册过」。真实机制是 **`main.py:434` 挂的 `StaticFiles` 只服务 `GET` / `HEAD`**：静态挂载对所有未匹配路径生效 —— GET 找不到文件 → **404**，其它方法（POST/PUT/DELETE…）→ **405**。**与路径是否注册过无关。**（Task 8 里我曾按错的判据「修反」了方向，`0c39401` 又改回来。）
11. **Task 6 — 建单路径补 `explicit_clear` + 补「②先于③」的顺序测试**。① 漏传 `explicit_clear` 会让管理员**显式清空的签收日期被补成今天**（真 bug，`0ac7b1b`）；② 补 `test_create_duplicate_beats_processing_status` 钉住「重复单校验（②）先于订单状态校验（③）」—— 这个顺序原本只写在散文里，**把两块对调后其余 21 条仍然全绿**（实测确认），说明没有测试看着它。
