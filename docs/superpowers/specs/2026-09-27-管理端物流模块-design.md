## 1. 背景与目标

管理端目前有 5 个模块（控制台 / 商品 / 订单 / 知识库 / 工单），订单能改状态但**看不到物流**。本模块补上物流的录入与查看：管理员手工维护运单（含轨迹文本），并在一个页面上看到「已发货订单现在到哪了」。

**成功标准**（可验收）：

1. 管理端出现第 6 个导航项「物流管理」，页面能分页列出运单
2. 能新增/编辑/删除运单，轨迹在一个多行文本框里编辑
3. 只能给「已发货」及之后状态、**且还没建过运单**的订单开运单，否则拒绝并给出可读提示
4. 删订单时它的运单一并消失，不留孤儿
5. `shipments.order_no` 上有唯一索引（按订单号查物流不走全表扫）

## 3. 数据模型

### 3.1 关键前提：`orders` 表完全不动（已实测）

`orders.order_no` 已经满足外键目标的两个条件，**不需要加索引、不需要迁移**：

实测证据（连真实库 `smartcs_agent` 查询 `pg_constraint`）：

```
orders_order_no_key  | u | UNIQUE (order_no)
orders_pkey          | p | PRIMARY KEY (id)
orders_user_id_fkey  | f | FOREIGN KEY (user_id) REFERENCES users(id) ON DELETE SET NULL
```

`contype = 'u'` 说明它是 **UNIQUE 约束**（不只是唯一索引）—— PostgreSQL 的外键只能指向唯一约束或主键，所以这一列可以直接当外键目标。

实测验证（建带 FK 的临时探针表，成功后退掉）：

```sql
CREATE TABLE _fk_probe (
    id serial PRIMARY KEY,
    order_no varchar(32) REFERENCES orders(order_no) ON DELETE CASCADE
);
-- 结果：创建成功 → orders.order_no 可直接作为外键目标
```

> ⚠️ 用户原始需求里的「给订单表的 order_no 建索引」**已经存在**，重复建是多余的。真正缺索引的是**运单表引用侧的那一列**（见 §3.2）—— PostgreSQL 的外键**不会**自动给引用侧建索引。

### 3.2 `shipments` 运单表（唯一一张新表）

新建 `llm_backend/app/models/shipment.py`：

```python
from sqlalchemy import Column, Date, DateTime, ForeignKey, Integer, String, Text, func

from app.core.database import Base


class Shipment(Base):
    """运单表:一个订单一个运单(1:1),轨迹以文本存本表。数据由管理端手工录入或 seed_shipments.py 生成"""

    __tablename__ = "shipments"

    id = Column(Integer, primary_key=True, index=True)
    tracking_no = Column(String(50), nullable=False, unique=True)  # 运单号,来自承运商,手工录入
    # 关联订单用业务单号而非 order_id:orders.order_no 已是 UNIQUE 约束,可直接当外键目标(§3.1 实测)
    # unique=True 不能省 —— 这是"一单一个运单"的强制点,且它自带唯一索引(正是本项目要的那个索引:
    # PostgreSQL 不给外键的引用侧自动建索引,漏了按订单号查物流就全表扫)
    order_no = Column(
        String(32),
        ForeignKey("orders.order_no", ondelete="CASCADE"),
        nullable=False,
        unique=True,
    )
    carrier = Column(String(50), nullable=False)                  # 8 选 1,见 §3.3
    status = Column(String(20), nullable=False, default="待揽收")   # 6 选 1,见 §3.3
    shipped_at = Column(Date, nullable=True)                      # 发货时间
    # 签收时间:仅 status='已签收' 时有值;其余状态由接口强制置 NULL(与 orders.signed_date 同款规则)
    signed_at = Column(Date, nullable=True)
    # 轨迹:自由文本,约定「一行一个节点」。本表不解析内容,前端按 \n 拆行渲染(§5.3)
    trace = Column(Text, nullable=True)
    created_at = Column(DateTime, server_default=func.now())
    updated_at = Column(DateTime, server_default=func.now(), onupdate=func.now())
```

> **删订单的级联靠 DB 层**：`Order` 模型**没有**反向 relationship（本模块不碰 `orders.py`），所以 `await db.delete(order)` 时 ORM 不知道运单存在，只能由 `ON DELETE CASCADE` 兜住。这一层不能省 —— 实测已确认二级行为正常（单表场景更简单）。

### 3.4 索引清单

| 表.列 | 索引类型 | 来源 | 本次动作 |
|---|---|---|---|
| `orders.order_no` | UNIQUE 约束 `orders_order_no_key` | 已存在（`unique=True`） | **不动** |
| `shipments.order_no` | **UNIQUE** | `unique=True` | **新建 ← 用户要的索引** |
| `shipments.tracking_no` | UNIQUE | `unique=True` | 新建 |

**建表方式**：`shipments` 是新表，`init_db.py` 里 `Base.metadata.create_all` 会在建表时连同索引一起建出来（`checkfirst=True` 只跳过已存在的表，对新表是全量创建）。因此 `init_db.py` **不需要**额外写 `CREATE INDEX IF NOT EXISTS`。

**已用探针表逐项实测**（与 §3.2 的模型定义逐字同构，跑完回滚）：

```
索引:
  CREATE UNIQUE INDEX _probe_shipments_order_no_key   ON ... USING btree (order_no)   ← 用户要的索引
  CREATE UNIQUE INDEX _probe_shipments_tracking_no_key ON ... USING btree (tracking_no)
  CREATE UNIQUE INDEX _probe_shipments_pkey           ON ... USING btree (id)
约束:
  _probe_shipments_order_no_fkey | f | FOREIGN KEY (order_no) REFERENCES orders(order_no) ON DELETE CASCADE
  _probe_shipments_order_no_key  | u | UNIQUE (order_no)
[TEST1] 同订单号插第二条          -> PASS:被 IntegrityError(UniqueViolation) 拦住
[TEST2] DELETE orders 一条        -> PASS:运单 2 -> 1,该订单名下剩 0 条(级联生效)
[TEST3] trace 存两行文本再读出    -> PASS:读回仍是 2 行(换行原样保留)
```

> ⚠️ **`Shipment` 必须与 `Order` 共用同一个 `Base`（`app.core.database.Base`）**。实测：若把 `Shipment` 挂在另一个独立 `Base` 上，`create_all` 会抛 `NoReferencedTableError: could not find table 'orders'` —— SQLAlchemy 要在同一个 `MetaData` 里解析外键目标。
>
> 实际实现天然满足（两者都 `from app.core.database import Base`），**但 `init_db.py` 的 import 必须同时含 `Order` 和 `Shipment`**，缺任一个都可能让 FK 解析失败或表不被创建。

> ⚠️ **`default="待揽收"` 是 SQLAlchemy 的 Python 端默认值，不是数据库默认值**（与现有 `Order.status` 的 `default="处理中"` 同款写法，DB 列上没有 DEFAULT）。后果：走 ORM 插入且不赋 `status` 时会自动填；**裸 SQL INSERT 不给 `status` 会触发 NotNullViolation**（实测踩到）。写测试若用原生 SQL 造数据，记得显式给 `status`。

`init_db.py` 的改动只有一行 —— 在顶部 import 里加上新模型（不 import 的话 `create_all` 看不见它，表根本不会建）：

```python
from app.models import (User, Conversation, Message, DocumentChunk, Document,
                        ProductPriceStock, Order, Ticket, Shipment)
```

`app/models/__init__.py` 同步加 import 与 `__all__`（照现有写法带 `# noqa: F401`）。

### 4.2 `GET /api/admin/logistics` — 列表

**查询参数**：

| 参数 | 类型 | 默认 | 约束 | 说明 |
|---|---|---|---|---|
| `page` | int | 1 | `ge=1` | 页码 |

**实现要点**：

```python
stmt = (
    select(Shipment, Order)
    .join(Order, Order.order_no == Shipment.order_no)   # 内连接安全:FK 保证订单必存在
    .where(*conds)
    .order_by(Shipment.shipped_at.desc().nullslast(), Shipment.id.desc())
)
```

- **内连接安全**：`shipments.order_no` 是外键，不可能指向不存在的订单
- **排序**：`shipped_at` 降序、`nullslast()` 把「待揽收还没发货」的排最后；同日期用 `id` 兜底保证稳定分页
- ⚠️ **`total` 的 count 必须带同一个 join**。只写 `select_from(Shipment)` 会静默算错：

  ```python
  # ❌ where 里含 Order.product_name / Order.status 时不带 join:
  #    SQLAlchemy 把 orders 补进 FROM 形成笛卡尔积 —— 不报错,只发一条 SAWarning
  #    实测:1 条运单 + 18 条订单 → total = 18(而不是 1)
  # ✅ 正确写法
  total = (await db.execute(
      select(func.count()).select_from(Shipment)
      .join(Order, Order.order_no == Shipment.order_no)
      .where(*conds)
  )).scalar_one()
  ```

  同时也不能取 `len(items)`（分页下 total 恒等于 page_size，且不报错 —— `orders.py:76-77` 记着那个坑）。**两个坑都要防**

### 4.3 `GET /api/admin/logistics/shippable-orders` — 订单下拉

```python
@router.get("/shippable-orders")
async def list_shippable_orders(db: AsyncSession = Depends(get_db)):
    """给「新增运单」的订单下拉用:状态为已发货/已送达/已签收,且还没建过运单的订单。"""
    rows = (await db.execute(
        select(Order.order_no, Order.product_name, Order.buyer_name, Order.status)
        .where(Order.status.in_(SHIPPABLE_ORDER_STATUSES))
        # 1:1 之后必须排除已建过运单的订单,否则管理员选中后提交必撞 409
        .where(~exists(select(Shipment.id).where(Shipment.order_no == Order.order_no)))
        .order_by(Order.order_no)
    )).all()
    return {"items": [{"order_no": r[0], "product_name": r[1],
                       "buyer_name": r[2], "status": r[3]} for r in rows]}
```

SQL 编译结果（已实测）：

```sql
SELECT orders.order_no, orders.product_name, orders.buyer_name, orders.status
FROM orders
WHERE orders.status IN (...)
  AND NOT (EXISTS (SELECT shipments.id FROM shipments WHERE shipments.order_no = orders.order_no))
ORDER BY orders.order_no
```

> 初稿里「已建过运单的订单仍然出现在下拉里（一单可多运单）」这条**已失效**，一对一之后反过来：必须排除。

**为什么单开一个端点而不是复用 `GET /api/admin/orders`**：现有订单列表的 `status` 参数只收单个值，要拿三个状态得调三次；而且「排除已建过运单的订单」这个 join 逻辑订单接口根本没有。给 `orders.py` 加多值支持 + 关联排除会动到订单模块（本模块明确不碰）。规则（哪些订单能开运单）属于物流模块，端点也放在物流模块里，归属干净。

**不分页**：当前订单量级 18 条。订单量上到几千条时需要改成分页或远程搜索，列入 §9③。

### 4.4 `POST /api/admin/logistics` — 新增运单

**请求体**：

```json
{
  "order_no": "ORD-005",
  "tracking_no": "JDV0000000005",
  "carrier": "京东物流",
  "status": "待揽收",
  "shipped_at": "2026-09-20",
  "signed_at": null,
  "trace": "2026-09-20 14:32 广州市 已揽收\n2026-09-21 08:05 广州转运中心 到达转运中心"
}
```

**处理步骤**：

1. 查订单：`select(Order).where(Order.order_no == payload.order_no)`
   - 不存在 → `400 "订单不存在: {order_no}"`
2. 校验订单状态 ∈ `SHIPPABLE_ORDER_STATUSES`
   - 不满足 → `400 f"订单 {order_no} 当前状态为「{status}」，只有已发货及之后的订单才能建运单"`
3. **校验该订单还没有运单**（1:1 的业务前置）
   - 已有 → `409 f"订单 {order_no} 已有运单，请勿重复创建"`
4. 处理 `signed_at` 与 `status` 的绑定（§4.6 规则 A）
5. 校验 `shipped_at` / `signed_at` 的先后（§4.6 规则 B）
6. `trace` 归一化：`(payload.trace or "").strip() or None`（空白/空串统一存 `NULL`，避免库里同时存在 `''` 和 `NULL` 两种"空"）
7. 插运单
8. 捕获 `IntegrityError` → `409`（并发下步骤 1–3 的先查后插仍可能撞；`orders.py:126-148` 是同款兜底写法）

>     select(Shipment, Order)

### 4.5 `PUT /api/admin/logistics/{shipment_id}` — 编辑

**可改字段**：`tracking_no` / `carrier` / `status` / `shipped_at` / `signed_at` / `trace`

**不可改**：`order_no`（schema 里根本没有这个字段，与订单页「编辑不给换商品」同理）

**处理要点**：

- 运单不存在 → `404 f"运单不存在: {shipment_id}"`
- `data = payload.model_dump(exclude_unset=True)` 区分「没传」与「传了 null」
- `trace` **没有特殊处理** —— 它就是个标量列，`setattr` 即可。传 `null` / 传 `""` 都走 §4.4 步骤 6 的同一条归一化（→ `NULL`），传了就覆盖，没传就不动。
  > 初稿里那套「没传 / `[]` / `null` 三种形态」的复杂度**已随轨迹表消失**。
- `signed_at` 与 `status` 用 §4.6 的 effective 值规则
- **不重复校验订单状态、也不重复校验"该订单已有运单"**：`order_no` 改不了，这两条在编辑路径上不可能被触发
- `tracking_no` 撞别人的号 → `409`

### 4.6 跨端点的两条校验规则

**规则 A：`signed_at` 与 `status` 强绑定**（与 `orders.signed_date` 完全同款，`orders.py:179-183` 是原型）

| `status` | `signed_at` 取值 |
|---|---|
| 非 `已签收` | **一律置 `NULL`**（状态改回其它即为清空） |
| `已签收` | 显式传了用传的 → 没传沿用原值 → 原值也没有则补当天（UTC，`datetime.now(timezone.utc).date()`） |

> 服务端兜底，直调接口也造不出「未签收却带签收时间」的数据。

**规则 B：时间先后**（手工录入的数据质量护栏）

若 `shipped_at` 与 `signed_at` **都有值**且 `signed_at < shipped_at` → `400 "签收时间不能早于发货时间"`。

> 手工录入是唯一数据来源，这条一行代码就能挡掉一类明显错数据。允许 `shipped_at` 为空（待揽收的运单还没发货）。

**⚠️ PUT 里两条规则都必须用「有效值」**，不能直接读 `data` —— 管理员最常见的操作是「只把状态改成已签收」，此时 `shipped_at` 根本没传：

```python
# ✅ PUT 里统一取 effective 值(没传就沿用库里的)
effective_status = data.get("status", shipment.status)
effective_shipped = data.get("shipped_at", shipment.shipped_at)
effective_signed = data.get("signed_at", shipment.signed_at)
# 规则 A 用 effective_status;规则 B 用 effective_shipped / effective_signed
```

照 `orders.py:179-183` 的 `effective_status` 写法。漏了 `shipped_at` 的 effective 取值，规则 B 在「只改状态」这条路径上形同失效。

### 4.8 前端空串约定（既有坑，新接口必须遵守）

`<input type="date">` 留空时给的是 `''`，`JSON.stringify` 后是 `""`，pydantic 对 `Optional[date]` 收到 `""` 一律 422（实测确认）。

**两端都要处理**：

- 前端：所有 body 走 `cleanBody()`（`api.js:12-16` 已有）把空串摘掉
- 后端：`Optional[date]` 不额外加 validator（现有端点也没加，保持一致）

**⚠️「清空一个字段」必须显式送 `null`，不能送 `''`：**

`cleanBody` 会把 `''` 整个键**删掉**，而 PUT 端点的 `exclude_unset` 把它判定为「没传」= **保留旧值**。所以 `shipped_at` / `signed_at` 一旦填过，用 `''` 是永远清不掉的。

```js
// ❌ 清不掉:'' 被 cleanBody 摘掉 → 后端认为"没传" → 保留旧值
shipped_at: form.shipped_at,
// ✅ 正确:cleanBody 保留 null(实测 cleanBody({shipped_at:null}) === {shipped_at:null})
shipped_at: form.shipped_at || null,
```

订单页正是靠这一点清空 `signed_date` 的（`OrderView.vue:411-413`），照抄。

> `trace` 是 `<textarea>`，空值给的是 `''` 而不是 `undefined`。由于它**没有 exlude_unset 语义问题**（§4.5 说了传 `''` 也会被归一化成 `NULL`），`trace: form.trace` 原样送即可 —— 清空轨迹靠的是「送空串 → 后端归一化成 NULL」，与上面两个日期字段的规则不同，**别混**。

## 6. 种子数据

新建 `llm_backend/scripts/seed_shipments.py`，照 `seed_orders.py` 的写法（`pg_insert` + `on_conflict_do_update` 幂等 upsert）。

**覆盖范围**：库里所有 `status ∈ {已发货, 已送达, 已签收}` 的订单（当前 6 + 4 + 3 = 13 条）。**一对一，每单恰好一个运单。**

**字段生成规则**：

| 字段 | 规则 |
|---|---|
| `tracking_no` | `JDV{order_no 的数字部分:010d}`，如 `ORD-003` → `JDV0000000003`。确定性生成 |
| `order_no` | 直接取订单号（作为幂等键，见下） |
| `carrier` | 京东物流为主（京东自营），按 index 轮转掺入顺丰/中通 |
| `status` | 按订单状态推导：已发货→`运输中`；已送达→`派送中`；已签收→`已签收` |
| `shipped_at` | `order_date + 1 天`，用 `min(..., today)` 兜住未来日期 |
| `signed_at` | 仅`已签收`时有值：**`order_date + 2 天`**，同样 `min(..., today)` |
| `trace` | 按运单状态生成递进的文本行，见下 |

> ⚠️ `signed_at` 必须跟 `seed_orders.py:73` 的订单签收日**取同一个偏移（+2 天）**。写成 +3 天会让同一条已签收订单出现「订单签收日 9-22、运单签收日 9-23」的自相矛盾演示数据。

**`trace` 文本生成**：按运单状态生成递进的节点行

| 运单状态 | 轨迹行 |
|---|---|
| 待揽收 | `NULL`（还没有轨迹） |
| 运输中 | 已揽收 → 到达转运中心 → 运输中 |
| 派送中 | 已揽收 → 到达转运中心 → 运输中 → 派送中 |
| 已签收 | 已揽收 → 到达转运中心 → 运输中 → 派送中 → 已签收 |

每行格式：`YYYY-MM-DD HH:MM 地点 描述`，行间用 `\n` 连接。

节点时间从 `shipped_at` 当天 09:00 起按小时递进（`+0h / +18h / +30h / +42h`）。

> ⚠️ **不能直接对 `shipped_at`（`Date`）加 `timedelta(hours=N)`** —— `date + timedelta(hours=N)` 返回的**还是 `date`，小时部分被直接截断**。实测：
>
> ```
> date(2026,9,20) + timedelta(hours=0)  = date(2026, 9, 20)
> date(2026,9,20) + timedelta(hours=18) = date(2026, 9, 20)   ← 和 +0h 撞了
> date(2026,9,20) + timedelta(hours=30) = date(2026, 9, 21)
> date(2026,9,20) + timedelta(hours=42) = date(2026, 9, 21)   ← 和 +30h 撞了
> ```
>
> 4 个偏移只会塌成 2 个不同值 → 轨迹行时间重复，看着像数据错了。
>
> **正确做法**：先把 `Date` 升成 `datetime` 再加偏移：
>
> ```python
> from datetime import datetime, time, timedelta
> base = datetime.combine(shipped_at, time(hour=9))   # 9 点起揽收,比 0 点自然
> line = f"{(base + timedelta(hours=offset)):%Y-%m-%d %H:%M} {loc} {desc}"
> ```

**幂等策略**（与 `seed_orders.py` 同款「upsert 覆盖」而非「存在则跳过」）：

```python
stmt = pg_insert(Shipment).values(rows)
stmt = stmt.on_conflict_do_update(
    index_elements=[Shipment.order_no],      # 1:1 之后的天然幂等键
    set_={"status": stmt.excluded.status,
          "shipped_at": stmt.excluded.shipped_at,
          "signed_at": stmt.excluded.signed_at,
          "trace": stmt.excluded.trace},

```

## 9. 已知取舍与风险

**① 轨迹是自由文本，不可结构化查询**（本次简化的主要代价）

`shipments.trace` 是一整块文本，后端不解析。因此做不了「查所有卡在某个转运中心的运单」「统计平均运输时长」「按节点时间排序」这类查询，也没法校验节点时间是否递增。

换来的是：少一张表、少一层级联、接口和页面都短一截。

**将来若要结构化**：加一张 `shipment_tracks`（时间/地点/描述三列）并把现有文本按月一次性解析回填，`trace` 列保留为「原文」即可平滑迁移。

**② 一对一：一单只能一个运单**

真实场景里一个订单可能拆多个包裹（多个运单）。本次按用户决策收敛成 1:1，用 `shipments.order_no` 的唯一约束强制。

**将来若要放开**：删掉该列的 `unique=True`（连同唯一索引）、把 `/shippable-orders` 的 `NOT EXISTS` 去掉即可，表结构其余部分不用动。

**③ 「订单状态」与「物流状态」完全解耦**

用户明确选择「只在开运单时校验订单状态」。因此：订单建好运单后被改回`处理中`，运单仍然存在且可正常编辑，接口不报错。

理由：订单状态现在是任意跳转、无状态机约束的（`docs/diagrams/spec/60-order-lifecycle.json` 已记录这一点）。如果编辑运单时也校验，管理员会被「先改订单状态才能改运单」卡住，规则更绕。**这是有意的设计，不是遗漏。**

**④ 种子脚本重跑会覆盖手工改过的种子运单的轨迹**

见 §6 幂等策略。订单号在种子 13 条之外的手工运单不受影响。

**⑤ 既有 bug：`OrderView.vue:339-342` 的签收日期 watcher 会在回填时覆盖库值**

**这是既有代码的 bug，不在本模块范围内，本次不修** —— 但本模块的签收时间联动**不能照抄它**（§5.2 已给出修正写法）。

- **成因**：`watch(() => form.status)` 无法区分「用户手动切换」与「`openEdit` 回填」，回填也会触发它。而 `prev` 拿到的是**上一次表单**的状态，不是这条记录的旧状态
- **触发条件**：上一次表单的 `status` 不是`已签收`（例如刚点过「新增」、或刚编辑过一条其它状态的记录），此时再编辑任意一条已签收记录 → 签收日期被改成今天
- **后果**：管理端界面上看不出异常（显示的就是"今天"），一保存就把错误的签收日期写进库；后端规则是「显式传了用传的」，会照单全收
- **实测复现**（`frontend/node_modules` 的 vue 包，逐字照抄那 4 行 watcher）：

  ```
  场景A 上次停在「处理中」→ 回填 signed_date 应为 2026-09-01,实际得到 2026-09-27  ★
  场景B 上次停在「已签收」→ 回填 signed_date = 2026-09-02                      正常
  ```

- **建议**：作为独立 bug 单处理（改动落在 `OrderView.vue`）。本模块的 `LogisticsView.vue` 从一开始就用 §5.2 的 `filling` 标记写法，不引入同样的坑

**⑥ `IntegrityError → 409` 会把外键违规也误标**

实测：插一个不存在的 `order_no` 抛的是 `IntegrityError(ForeignKeyViolation)`，与撞号是**同一个异常类**。因为 §4.4 步骤 1 已经先查过订单，实际风险很低（只有「查完之后订单被并发删掉」这个极窄窗口）。按「低风险 + 简单优先」处理：保留现方案，仅在此记录。

**⑦ `min_length=1` 挡不住纯空格**

实测 `tracking_no = " "`、`order_no = " "` 都能通过 pydantic 校验 —— `min_length` 数的是字符数，空格算字符。

**处理**：不需要额外 strip（前端预校验已挡；纯空格是管理员手滑，不是攻击面）。

**⑧ `shippable-orders` 不分页**

当前订单量级 18 条，一次性返回无压力。订单量上到几千条时需要改成分页或远程搜索下拉，届时改这一个端点即可。
